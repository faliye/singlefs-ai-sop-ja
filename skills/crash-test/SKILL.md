# 検証スイート

規則は `rules/test-discipline.md` と `rules/show-me-test.md`。

## 検証の分担

| 手段 | 何を検証するか | 誰が用意するか |
|---|---|---|
| クラッシュ点リプレイ | 任意の断電点から復帰できるか | プロジェクト |
| モデル対照テスト | 機能的正しさ：操作列の結果が正しいか | プロジェクト |

クラッシュ点リプレイは被検対象自身の書き込み記録と checker を、モデル対照テストはその理想モデルを要するので、どちらも共有ゲートには載せられない。
プロジェクトが `.claude/gate.d/` でその一つをつないだら、その段階の冒頭に、どの項目を覆うのかを書く：

```bash
# gate-stage: 層 0 クラッシュ点リプレイ（最初のトランザクションの全クラッシュ状態）
# gate-covers: 崩溃点重放
```

書けるキーは `gate.sh` の未実装一覧にあるもの——`模型对拍`（モデル対照）、`崩溃点重放`（クラッシュ点リプレイ）、
`最终判据`（最終判定基準）、`命名纪律（shell）`（shell の命名規律）——だけで、`gate.sh` の綴りのまま写す。一字違えば赤になる。
その段階がこの回に走って通ったときだけ、`gate.sh` 末尾の未実装一覧はその項目を「プロジェクト固有段階が覆う」の下へ移す。
覆うというのは「ある段階がこれをやっていて、今回は通った」というだけで、どこまで届くかはその段階自身の名前と説明を見る。
この回に判定対象が無い段階は終了コード 77 を返す：「今回は走らず」と記録され、通過にも覆いにも数えない。

## 判読の規律

- **「再現しなかった」は「問題が無い」ではない。** クラッシュ一貫性が成立すると言うには、
  この回でクラッシュ点をいくつ列挙したのか、それが全部なのかを述べること。
- **checker が無報告なのは、その検査が未実装なだけかもしれない。** 先に
  `kb/invariants.md` の状態列を見る。
- **判定が読めないときはその回を破棄**し、決して通過扱いにしない。プロジェクトの装置が終了マーカーを読めない場合も同じである。

並行のメモリ順序、仮想機での実負荷とクラッシュ注入は被検対象といっそう強く結びついているので、
プロジェクトが自分で決め、自分でテストし、自分で検証する。この共有 skill には載せない。
