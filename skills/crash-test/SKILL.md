# 検証スイート

規則は `rules/test-discipline.md` と `rules/show-me-test.md`。

## 四つの手段の分担

| 手段 | 何を検証するか | 誰が用意するか |
|---|---|---|
| **LKMM（herd7）** | 並行経路のメモリ順序：ロックフリー構造、バリア、コア間の可視性 | 共有スクリプト `lkmm.sh`、ゲートの「LKMM」段階 |
| **QEMU/KVM** | 実負荷での端から端までの挙動。受入の最終判定基準 | プロジェクト：仮想機械の装置もゲート段階もプロジェクトにある |
| クラッシュ点リプレイ | 任意の断電点から復帰できるか | プロジェクト |
| モデル対照テスト | 機能的正しさ：操作列の結果が正しいか | プロジェクト |

後の三つは被検対象自身の書き込み記録・イメージ書式・checker を要するので、共有ゲートには載せられない。
プロジェクトが `.claude/gate.d/` でその一つをつないだら、その段階の冒頭に、どの項目を覆うのかを書く：

```bash
# gate-stage: 層 0 クラッシュ点リプレイ（最初のトランザクションの全クラッシュ状態）
# gate-covers: 崩溃点重放
```

書けるキーは `模型对拍`（モデル対照）、`崩溃点重放`（クラッシュ点リプレイ）、`QEMU 真实负载`（QEMU 実負荷）、
`QEMU 崩溃注入`（QEMU クラッシュ注入）だけで、`gate.sh` の綴りのまま写す。一字違えば赤になる。
その段階がこの回に走って通ったときだけ、`gate.sh` 末尾の未実装一覧はその項目を「プロジェクト固有段階が覆う」の下へ移す。
覆うというのは「ある段階がこれをやっていて、今回は通った」というだけで、どこまで届くかはその段階自身の名前と説明を見る。
この回に判定対象が無い段階は終了コード 77 を返す：「今回は走らず」と記録され、通過にも覆いにも数えない。

## LKMM

```bash
bash .claude/scripts/lkmm.sh
SINGLEFS_KERNEL_TREE=/path/to/linux bash .claude/scripts/lkmm.sh   # カーネルツリーを指定
bash .claude/scripts/lkmm.sh --static-only    # herd7 の要らない検査だけ。全部通っても 3 で終わり、通過ではない
```

`litmus/*.litmus` は期待する判定を宣言しなければならない。スクリプトは herd7 の
`Observation` 行と突き合わせる：

```
(* singlefs-expect: Never *)      悪い結果は起こり得てはならない
(* singlefs-expect: Sometimes *)  悪い結果は起こり得る（対照群）
```

### 対照群：同じテストからバリアを外したもの

**Never の一本ごとに対照群を付ける。** 無ければ、Never が出ても「バリアが止めたのか」
「そのパターンが元々当たらないのか」を区別できない。

対応付けはまずファイル名で探す：`x.litmus` の対照群は `x-<接尾辞>.litmus`（慣例は `x-nofence.litmus`）で、
Sometimes を宣言する。次に中身で見る：コメントと一行目を除いてから一行ずつ比べ、対照群に許されるのは、
元のテストからバリアの行（`smp_wmb`・`smp_rmb`・`smp_mb` など）を抜くこと、または `smp_store_release` /
`smp_load_acquire` を `WRITE_ONCE` / `READ_ONCE` に緩めることだけで、少なくとも一か所。
exists・init・読み手は一字も変えてはならない。変えれば、それは別の問いに答えている。
他所の Sometimes が何本あっても、なおさら数に入らない。

### コードに結びつける

herd7 が判定するのは litmus に書かれた形である。コードが公開順序を変えたのに litmus が追いつかなければ、
判定は Never のままで、ゲートも緑のままになる。だから Never の一本ごとに、どのコードを模しているかをファイル冒頭に書く。
一行に一つのアンカーで、アンカーの後ろに空白一つを置けば注釈を書いてよい：

```
(*
 * singlefs-expect: Never
 * singlefs-models: crates/<crate>/src/transaction.rs::publish_first_file 書き手
 * singlefs-models: crates/<crate>/src/recovery.rs::choose_root 読み手
 *)
```

スクリプトが確かめるのは三つ：ファイルが在ること、その中にその `fn` が在ること、
`crates/` のどこかの `.rs` がこの litmus のファイル名を書いていること。
最後のものが結びつけのテストで、この litmus を読み、その書き手／読み手の順序を、コードが今日実際に出す順序と突き合わせる
（例：書き込み要求の列を記録し、段階に分類してから一項ずつ比べる）。
ゲートはファイル名でそれを見分けるだけで、正しいものを測っているかは人が見る。

どのコードにも対応しない Never（テンプレートの一対など）は `singlefs-models: none —— <理由>` と書く。理由は空にできない。

### klitmus7 でしか露見しない落とし穴二つ

スクリプトが手前で止める：`rN` を使うなら `int rN;` が要る。init ブロックで `atomic_t` の仮引数に初期値を与えるなら型が要る。

## QEMU

共有ゲートは仮想機械の装置を持たない。何本のディスクを繋ぐか、どのバイナリを入れるか、結果をどう取り込むか、
デバイス側で独立に記録するか——どれも被検対象と結びついているので、装置もそのゲート段階もプロジェクトに置く。

装置が守る規則は `rules/command-safety.md` にある：仮想機械の pid はファイルに書き、片付けはその固定の pid で殺す。
結果の取り込みには件数の関門を置く。終了コードは宿主へ正直に戻らなければならない——
装置は必ず失敗する用例を一つ持ち、それを失敗と見分けられなければ装置が壊れている。
読めるカーネルが無ければそのまま失敗し、ソフトウェアエミュレーションへは降格しない。
動いているように見えて、使い物にならない遅さになる。

ゲート段階をつないだら、実負荷を走らせるだけのものは `# gate-covers: QEMU 真实负载` と書く。
クラッシュ注入までやり、checker が全緑で終わるものは `# gate-covers: QEMU 崩溃注入` も書く——それが受入の最終判定基準である。

## クラッシュ点リプレイを他で代替できない理由

**単体テストが全緑、モデル対照が全通過、checker が無報告——三つ足してもクラッシュ一貫性の根拠にならない。**

それらが検証するのは「正常経路での状態が正しいか」である。クラッシュ一貫性が問うのは別の問いだ：
**任意の書き込み要求のあとで断電したとき、再起動して収拾がつくか。**
これは各クラッシュ点を一つずつ試す以外に答えようがない。

実装に必要なもの（依存順）：ディスク書式の第一版（プロジェクトの `kb/decisions.md` の
ディスク書式に関する項目を見る）→ mkfs + checker → トランザクションのコミット経路 →
ブロック層の書き込み記録（`dm-log-writes`）。

## 判読の規律

- **「再現しなかった」は「問題が無い」ではない。** クラッシュ一貫性が成立すると言うには、
  この回でクラッシュ点をいくつ列挙したのか、それが全部なのかを述べること。
- **checker が無報告なのは、その検査が未実装なだけかもしれない。** 先に
  `kb/invariants.md` の状態列を見る。
- **判定が読めないときはその回を破棄**し、決して通過扱いにしない——`lkmm.sh` が
  `Observation` を読めなければ即失敗であり、プロジェクトの仮想機械の装置が終了マーカーを読めない場合も同じである。
