# 設計判断を一件記録する

規則は `rules/doc-discipline.md`、およびプロジェクト側の書式・構造進化に関する規則（あれば）。

## 状態は三つだけ

| 状態 | 意味 |
|---|---|
| **確定** | 方向も細部も決まった。これに沿ってコードを書いてよい |
| **半確定** | 方向は決まり、細部は未定。**どの一点が未定かを書く**。書かなければ未定と同じ |
| **未定** | 決まっていない。「決めるには何に先に答える必要があるか」を書く |

## `kb/decisions.md` に書く書式

```markdown
## D<n> <判断名> —— <状態>

<結論を一文で。命令形か断定で。「〜かもしれない」は使わない。>

根拠：<なぜそうするか。他所の実測値は出典と計測条件を添え、本工程では未検証と明記する。>

**未定**：<半確定なら必須。欠けている点を書く。>
```

## 硬い要件

1. **判断を変えたら覆した根拠を書く**。古い結論は文末の「改訂履歴」へ移す——本文に旧結論を残さない。
2. **書式を変えたら `kb/invariants.md` と checker を同じ変更で更新する。** 三者が食い違うコミットは受け取らない。
3. **判断を決める前に `kb/pitfalls.md` を一通り照合し**、同じ落とし穴に戻っていないことを確認する。
4. 判断どうしが連鎖するなら**双方に相互に注記する**。片方だけにしない。
5. **確定後に、実際に支えている理由が変わったと分かったら、それも判断変更である。**
   実験は「確定時に挙げた理由」を別の決定的な理由に置き換えることがよくある。
   本文の根拠を実測のほうに差し替え、変更履歴に記す——状態が動かなくても記す。
   確定時の一文だけを残すと、三か月後に何が実際に支えているのか誰にも分からない。
6. **人が裁定した一文を動かしたら、`kb/checks-owed.md` に未返済の一件を記す。**
   本文に「要再確認」と書くだけでは、それが誰かの目に入る保証は何も無い——
   裁定した本人は、自分の決定が変わったことを知らない。
   どの決定のどの項目かを名指しし、再確認が済んでから返済する。

## いつ決め、いつ待つか

判定基準は：**この判断は「最初のコードがどう見えるか」を変えるか。**

変える → 今決める。先送りは手戻りになる。
変えない → 待ってよい。未定と記し、「決めるには何に先に答える必要があるか」を書く。
