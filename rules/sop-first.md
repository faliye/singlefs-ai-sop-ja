# SOP はコードに優先する

**規範とゲートは、いかなる実装コードよりも優先度が高い。**

どの回の作業でも、「ゲートを一条足す」と「機能を一段書く」が衝突したら、
先にゲートを足す。

## 帰結

- **スクリプトが被験対象より先に存在するのは正常**であり、本末転倒ではない。
  ハーネスは負荷がない段階で書いて自己検査までできる。実装が出来たら繋ぐだけである。
- **新しい落とし穴を見つけた時の第一反応は「これをどうゲートの赤い一項に変えるか」**であり、
  「これをどの文書に書くか」ではない。注意書きは人を止めないが、失敗する検査は止める。
- **ゲートのスクリプト自体にもテストが要る**：`scripts/` を変えたら、
  弾かれるべき入力を一つ作り、本当に赤になることを確かめる。
  自己検査できないゲートは飾りである。
- SOP を変えたら `VERSION` を上げる。プロジェクトは次にゲートを走らせた時点で規則の変化を知る。

# ゲートは教育の道具であって、ふるいではない

**提出者は自分のパッチを通したいと思っている、と既定で仮定する。**

弾かれた時、多くの場合それはテストしたくなかったからではなく、
**どうテストすればよいか分からなかった**からである。
この前提に立てば、ゲートの職責は「悪いものを外に締め出す」ことではなく、
**「何をもって完了とするか」を、推測が要らない程度まで明示すること**である。

## 拒否には必ず次の一手を添える

「不合格」としか言わない失敗メッセージは、「どうすれば正しかったのか」を
推測に委ねることになる——推測しかできない人はゲートを迂回するか、そもそも提出しなくなる。
**どちらの結果も、通してしまうより悪い。**

したがって：**拒否する時は次に何をするかを述べる。**
`scripts/gate-lint.sh` が強制し、拒否の形態はどれも見る：

| 形態 | 対処をどこに書くか | 判定 |
|---|---|---|
| `bad` | 直後の `howto` | その `bad` 自身を含め 5 行以内に `howto` があること（コメント行は数えない）|
| `die` | **自身の第二引数**（`die "何で止まったか" "次に何をするか"`）| 一文しか持たない `die` は赤 |
| 直に印字される `✗`（`echo`、あるいは埋め込み python の `print`）| 次の拒否までの間にある `→` の行 | その間に `→` が一行も無ければ赤 |

`die` の行は付け足しではない。`die` は `bad` + `exit`、すなわち拒否そのものである：
`die "単体テスト失敗"` のような次の一手が一切無い拒否は、`bad` だけを見ていては見つからない。

三行目が扱うのは**プロジェクト固有の段階**である。それらの多くは `lib.sh` を
source せず、直に `echo "  ✗ …"` と書くか、判定を埋め込み python の
`print('  ✗ …')` に書く——前二行はどちらもそこに届かない。

窓は 5 行では取らない。python は往々にして先に `✗` を一行印字し、次に該当項目を
繰り返しで並べ、最後に対処を書く——5 行ではこの一群をまとめて誤判定する。
そこで判定は「**次の拒否より前に**対処が現れること」とする。二つの免除は
どちらも**明示的に書くこと**。推測はしない：繰り返しの中で一件ずつ並べる行には
`# gate-lint:detail`（対処はその要約行に書く）、要約行には `# gate-lint:summary` を付ける。

`howto` が書けない時は、**その検査をまだ足さない**：
次の一手が書けないなら、その検査の判定基準が自分でも定まっていない。

## 良いゲートの三条件

1. **手元で走り、リモートと同じ判定を返す。** 提出者は送る前に自分で結果を見られなければならず、
   拒否されてから知るのでは遅い。
2. **失敗メッセージは症状だけでなく規則を指す。** その一箇所を糊塗させるのではなく、
   規則そのものを学ばせる——さもなければ同じ問題がまた来る。
3. **正しいやり方を容易にする。** テンプレート、骨組み、そのまま真似できる実例は
   すべてゲートの一部である。

## これがもたらす複利

規則が十分に明示されていれば、新しく来た人は数回でこの流儀を掴み、
その後の開発はむしろ速くなる——**「これで完了と言えるのか」を推測しなくて済む**からである。
同時にコード品質も全体的に押し上がる。
自分の成果を拒否されたい人はおらず、彼らに欠けていたのは明確な道筋だけだからである。

## 境界

SOP 優先は SOP の無限膨張を意味しない。
**一条を規則として入れる前に「これは失敗しうる検査に変えられるか」を問う**——
変えられないものは、たいていまだ考え切れていない。
kb に検討中として残し、規則としては書かない。

## ゲートやフックを足す前に、既存のものを探す

ゲートやフックを一つ新しく足す前に、同じ事柄・同じ対象・同じトリガーを扱うものが既にないかを調べる：

1. `python3 scripts/gate-overlap.py --list` を実行する（プロジェクトでは取り込んだ写しを使う：`python3 .claude/singlefs-ai-sop/scripts/gate-overlap.py --list`）。既存のゲートとフックがそれぞれ何を判定し、フックがどのトリガーに掛かっているかを見る。
2. 同じ事柄を扱うものがあれば、新しい判定基準をそこへ追記する。同じ対象を同じ入力から判定する二つは、一つに統合する。
3. 二つが共有するのが処理の一部だけなら（同じ表を読む、同じ基準を使う）、共通ライブラリに抜き出して両方から呼ぶ。二つ目の写しは作らない。
4. どうしても独立させる必要があるなら、新しいファイルに比べた既存のものと、そこへ統合しない理由を一つずつ書く：`# gate-similar: <既存のファイル名> <そこへ統合しない理由>`。似たものが一つもなければ `# gate-similar: 无 <何を調べたか>` と書く。
   同じイベントに掛かり matcher が重なる既存フックと、字面がよく似た既存のゲート・フックは、一つ残らず名指しする。これらについて `无` は認めない。
5. 同じ一節をどうしても二つのファイルに残すなら、片方に `# gate-overlap:copy-kept <もう一方のファイル名> <共通化しない理由>` と書く。
6. 新しいフックはファイル冒頭に `# hook-events: <イベント> …` を書いて掛けるイベントをすべて並べ、`.claude/settings.json` にイベントごとに一度ずつ登録する。

### 誰が検査するか

- **agent の作業終了時**：終了フック `scripts/claude-hooks/gate-reuse-check.sh` が、その agent 自身が新しく作った、または変更したゲートとフックを調べる。`gate-similar` か `hook-events` がない、名指しすべきものを名指ししていない、既存のファイルを一節まるごと写している、のどれかに当たれば終了を止め、まず自己点検させる。
  停止フックに差し戻された続きの作業の中では、同じ判定結果で止めるのは一度だけ。判定結果が変われば再び止める。
  メイン agent もサブ agent も対象になる：プロジェクトは `.claude/settings.json` の `Stop` と `SubagentStop` にそれぞれ一度ずつ登録する。書き方はそのフックの冒頭にある。
- **コミット前**：ゲート段階「ゲート重複検査」（`门禁查重`、`scripts/gate-overlap.py`）が、diff の窓で新しく足された、または変更されたゲートとフックを判定する：`gate-similar` と `hook-events` を書いたか、名指ししたものが既存のゲートかフックか、理由の長さは足りるか、名指しすべきものを残らず名指ししたか、足した行が既存のファイルと一節まるごと同じでないか、`copy-kept` の書き方は正しいか。
  「一節まるごと」のしきい値は、そのスクリプトの `CLONE_MINIMUM_LINES` に従う。
- ゲート段階「ツール層の関門」（`工具层的闸`、`scripts/hooks-registered.sh`）が、終了フックが登録されているか、`hook-events` のイベントにすべて掛かっているかを判定する。

名指ししたものが本当に一番近いか、統合しない理由が成り立つかは、ゲートには判定できない。レビューに任せる。
