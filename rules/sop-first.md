# SOP はコードに優先する

**規範とゲートは、いかなる実装コードよりも優先度が高い。**

どの回の作業でも、「ゲートを一条足す」と「機能を一段書く」が衝突したら、
先にゲートを足す。

## なぜか

このプロジェクトは多くの人（と多くのモデル）が手を入れる。
**各人の上限はそれぞれ違うが、下限は縛れる。**
下限を縛るものが SOP である：何をもって完了とするかをルールが述べ、
「未完了」をその場で赤にするのがスクリプトである。

コードは間違えても次の回で捨てて書き直せる。その代償は有界である。
**SOP が一枚欠けると、その一枚については全員が足場を失う**——
誤りは誰にも気づかれずに積み上がり、気づいた時には数十コミットに染み込んでいる。
この代償は線形ではない。

## 帰結

- **スクリプトが被験対象より先に存在するのは正常**であり、本末転倒ではない。
  ハーネスは負荷がない段階で書いて自己検査までできる。実装が出来たら繋ぐだけである。
- **新しい落とし穴を見つけた時の第一反応は「これをどうゲートの赤い一項に変えるか」**であり、
  「これをどの文書に書くか」ではない。注意書きは人を止めないが、失敗する検査は止める。
- **ゲートのスクリプト自体にもテストが要る**：`scripts/` を変えたら、
  弾かれるべき入力を一つ作り、本当に赤になることを確かめる。
  自己検査できないゲートは飾りである。
- SOP を変えたら `VERSION` を上げる。プロジェクトは次にゲートを走らせた時点で規則の変化を知る。

# ゲートは教育の道具であって、ふるいではない

**提出者は自分のパッチを通したいと思っている、と既定で仮定する。**

弾かれた時、多くの場合それはテストしたくなかったからではなく、
**どうテストすればよいか分からなかった**からである。
この前提に立てば、ゲートの職責は「悪いものを外に締め出す」ことではなく、
**「何をもって完了とするか」を、推測が要らない程度まで明示すること**である。

## 拒否には必ず次の一手を添える

「不合格」としか言わない失敗メッセージは、「どうすれば正しかったのか」を
推測に委ねることになる——推測しかできない人はゲートを迂回するか、そもそも提出しなくなる。
**どちらの結果も、通してしまうより悪い。**

したがって：**拒否する時は次に何をするかを述べる。**
`scripts/gate-lint.sh` が強制し、拒否の二つの形態のどちらも見る：

| 形態 | 対処をどこに書くか | 判定 |
|---|---|---|
| `bad` | 直後の `howto` | その `bad` 自身を含め 5 行以内に `howto` があること（コメント行は数えない）|
| `die` | **自身の第二引数**（`die "何で止まったか" "次に何をするか"`）| 一文しか持たない `die` は赤 |
| 直に印字される `✗`（`echo`、あるいは埋め込み python の `print`）| 次の拒否までの間にある `→` の行 | その間に `→` が一行も無ければ赤 |

`die` の行は付け足しではない。`die` は `bad` + `exit`、すなわち拒否そのものである。
ゲートが `bad` しか見ていなかった間、`die "単体テスト失敗"` のような対処のない拒否が
ゲートの経路上に置かれ、17 箇所の `die` がまとめて検査を免れていた。

三行目が扱うのは**プロジェクト固有の段階**である。それらの多くは `lib.sh` を
source せず、直に `echo "  ✗ …"` と書くか、判定を埋め込み python の
`print('  ✗ …')` に書く——前二行はどちらもそこに届かない。
singlefs のローカル段階で実測：この形の拒否が 46 箇所あり、これまで全て検査を免れており、
そのうち 14 箇所は次の一手が一言も書かれていなかった。

窓は 5 行では取らない。python は往々にして先に `✗` を一行印字し、次に該当項目を
繰り返しで並べ、最後に対処を書く——5 行ではこの一群をまとめて誤判定する。
そこで判定は「**次の拒否より前に**対処が現れること」とする。二つの免除は
どちらも**明示的に書くこと**。推測はしない：繰り返しの中で一件ずつ並べる行には
`# gate-lint:detail`（対処はその要約行に書く）、要約行には `# gate-lint:summary` を付ける。

`howto` が書けない時は、**その検査をまだ足さない**：
次の一手が書けないなら、その検査の判定基準が自分でも定まっていない。

## 良いゲートの三条件

1. **手元で走り、リモートと同じ判定を返す。** 提出者は送る前に自分で結果を見られなければならず、
   拒否されてから知るのでは遅い。
2. **失敗メッセージは症状だけでなく規則を指す。** その一箇所を糊塗させるのではなく、
   規則そのものを学ばせる——さもなければ同じ問題がまた来る。
3. **正しいやり方を容易にする。** テンプレート、骨組み、そのまま真似できる実例は
   すべてゲートの一部である。`litmus/` にある一対の litmus は、真似させるために置いてある。

## これがもたらす複利

規則が十分に明示されていれば、新しく来た人は数回でこの流儀を掴み、
その後の開発はむしろ速くなる——**「これで完了と言えるのか」を推測しなくて済む**からである。
同時にコード品質も全体的に押し上がる。
自分の成果を拒否されたい人はおらず、彼らに欠けていたのは明確な道筋だけだからである。

## 境界

SOP 優先は SOP の無限膨張を意味しない。
**一条を規則として入れる前に「これは失敗しうる検査に変えられるか」を問う**——
変えられないものは、たいていまだ考え切れていない。
kb に検討中として残し、規則としては書かない。
