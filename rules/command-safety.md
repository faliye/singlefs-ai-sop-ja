# プロセスとコマンドの規範

八条は赤くなる検査であり、`scripts/shell-lint.sh` が判定する：
**パターン一致でプロセスを殺すこと**（`pkill -f`、`killall`）、**`pgrep -f`**、**サブシェル内の代入で値を外に持ち出すこと**、
**スクリプト内で git の取り消し系コマンドを使うこと**、
**`rm -rf` を守りのない変数パスに当てること**、**引数のない `wait`**、**`pipefail` を設定したスクリプトで `grep -q` で終わるパイプ**、**`/proc`・`/sys`・cgroupfs 配下のファイルが空かどうかをファイルサイズで判定すること**。
テスト装置が終わるときに自分で作ったイメージを消したかどうかは、`gate.sh` の「走り終えて一時ファイルを残していない」（`跑完没留下临时文件`）が判定する。

リポジトリ内の登録のないシンボリックリンクは、`gate.sh` の「ソフトリンク」（`软链接`）が判定する。
残りはまだ文章のままである。機械判定の基準が定まっていない（`show-me-test.md`「ゲートが証明できること・できないこと」）。

## 取り消せない操作は、手を出す前にもう一度考える

判定基準：**この一歩を踏んだあと、戻れるか。**

| 種類 | 例 | どうするか |
|---|---|---|
| **未コミットの変更を捨てる** | `git checkout <ファイル>`、`git restore`、`git reset --hard`、`git clean` | 先に `git stash` するか `cp` で外に控えを取る。そのファイルの未コミット変更を**全部**捨てると分かっているときだけ使う |
| **データを直接消す** | `rm -rf`、`> ファイル`、`sed -i`、`rsync --delete`、`mkfs`、`dd` | 先に対象を見る（`ls` / `git status` / `lsblk`）。変数のパスには `${VAR:?}` の守りを付ける |

**使い捨ての実験は副本でやる。** 作業ツリーで書き換えてから戻そうとしない。

**スクリプトの中に git の取り消し系コマンドを書いてはならない。** スクリプト内できれいな状態に戻したいなら、先に `git stash` するか、
リポジトリごと複製して副本の上でやる。

**`rm -rf` を変数のパスに当てるときは空値の守りを付ける**：`rm -rf "$build_directory/cache"` ではなく `rm -rf "${build_directory:?}/cache"` と書く。
`rm -rf "$build_directory"` のように後ろにパスが続かないものは不要。

## プロジェクトのルートにファイルやディレクトリを新しく作らない

プロジェクトのルート（リポジトリの最上位）にファイルやディレクトリを新しく作らない。新しいものは既存のディレクトリに入れる：下書きとログは `$TMPDIR` かセッションの作業ディレクトリに、スクリプト・記録・産物はプロジェクトが決めたディレクトリに置く。
消したあとで作り直すのも新規作成に数える。`.gitignore` で無視されるものも同じ。このパッケージ自身がルートに置く `.git`・`.claude`・`CLAUDE.md`・`.singlefs-ai-sop-version` は登録しなくてよい。

どうしてもルートに作るとき：

1. まずユーザーに申請する：作る名前、中に何を置くか、なぜ既存のディレクトリに入れられないかを言う。
2. ユーザーが同意したら、プロジェクトルートの `.claude/root-entries` に `<名前>  # 理由` を一行登録する：名前はルート直下の一階層だけで、ほかに `/` を含めない。理由には何を置くか、なぜルートなのかを 4 文字以上で書く。一つの名前は一行だけ。
3. それから作る。登録表と新しい項目は同じコミットに入れる。
4. 項目を消したら、登録表のその行も同じ変更で消す。

ツールが毎回作り直すもの（ビルドディレクトリなど）は一度登録すればよい。

| 誰が判定するか | 何を判定するか |
|---|---|
| フック `scripts/claude-hooks/root-entry-guard.sh` | Write・Edit・NotebookEdit がルート直下のまだ存在せず登録もない項目に書こうとしたら、実行前に拒否する。登録表を変えるとき（これらのツール、または Bash コマンドがそこに書くとき）は、ユーザーが画面で確認する。Bash コマンドが走り終えてルートに登録のない項目が増えていたら、エージェントに報告し、移すか申請させる |
| ゲート段階「プロジェクトルートの新しい項目」（`项目根的新条目`、`scripts/root-entries.py`） | diff の基準に対してルートに新しく加わった項目（追跡されているもの、無視されていない未追跡のもの）は、どれも登録が要る。理由のない行、理由が短すぎる行、名前が一階層を超える行、重複、登録した項目が存在せず `.gitignore` にも覆われていないものは赤 |

フックは `.claude/settings.json` に登録する。書き方はそのファイル冒頭にある。

判定できないこと：ユーザーが同意したか、理由が成り立つかはレビューに任せる。無視される項目はゲートが判定せず、フックにしか見えない。Bash で作ったものは、フックがコマンドの走り終えたあとにしか報告しない。Bash で登録表に書くときに、パスを変数で組み立てたりインタプリタから書いたりしたものは見分けられず、確認を求めない。

## リポジトリにシンボリックリンクを置かない

リポジトリ（プロジェクトルートから下、`.git` を除く）にはシンボリックリンクを置かない。追跡されているもの、未追跡のもの、`.gitignore` で無視されるもの、どれも数える。よそのファイルを使うときは、コピーを持ち込むか、使う箇所に実際のパスを書く。
本パッケージのリポジトリも、本パッケージを入れた各プロジェクトもこれに従い、それぞれ自分のプロジェクトルートの下に登録する。

どうしても残すシンボリックリンク：

1. プロジェクトルートの `.claude/soft-link-exempt` に `<プロジェクトルートからの相対パス>  # 理由` を一行登録する：先頭に `/` を付けず、`.` と `..` を含めない。理由には何を指しているか、なぜコピーや実際のパスに置き換えられないかを 4 文字以上で書く。一つのパスは一行だけ。
2. リンクを消したとき、または普通のファイルに置き換えたときは、同じ変更でその行も消す。

ゲート段階「ソフトリンク」（`软链接`、`scripts/soft-links.py`）が判定する：作業ツリーのシンボリックリンクと、インデックスでモードが `120000` の項目のうち、登録のないものをパスごとに挙げて赤にする。`gate.sh --staged` のときは元のリポジトリの作業ツリーもあわせて判定する。
免除表の行に理由が無い、理由が短すぎる、パスがプロジェクトルートからの相対でない、重複している、登録したパスがシンボリックリンクでない、のどれも赤。

判定できないこと：理由が成り立つかはレビューに任せる。`.git` の中は判定しない。

## `pkill -f` / `killall` は一律禁止

プロセスを止めるには：まず `ps` で列挙して目で確かめ、
二つ目のコマンドで**リテラルの pid** を指定して殺す。
`scripts/proc.py stop プロセス番号` に任せてもよい：TERM を送り、`--grace` 秒（既定 10）経ってもまだいれば KILL を送り、止める対象がコマンドを発したプロセス自身かその祖先なら拒む。
数を数える用途には `/proc` の構造化された判定を使い、自分のプロセスツリーを除外する。

**待ちループの中でも `pgrep -f` を使わない**（`until ! pgrep -f "プロセス名"; do sleep 5; done` のような形）。
プロセスの終了を待つには、その**リテラルの pid** を使う：`until ! kill -0 "$pid" 2>/dev/null; do sleep 5; done`。
自分で起こした裏のジョブは `wait` で待つ。自分で起こしていないもの（別のスクリプトが起動したデーモンなど）は、起動する側に pid をファイルへ書かせてから待つ。
pid を控えていなければ、`scripts/proc.py find 実行ファイル名 [--argument 引数]` でプロセス番号を探す：実行ファイル名を一字一句比べ、パターン文字列をコマンドライン全体と照合することはせず、このコマンドを発したプロセスの系統も列挙しない。
プロセス番号が手に入ったら `scripts/proc.py wait プロセス番号 --timeout 秒` で終了を待つ。時間切れまでに終わらなければ、まだ生きているものを列挙して終了コード 3 で返る。
`scripts/shell-lint.sh` の S3 は、スクリプト中のコマンド位置にある `pgrep -f` を一箇所残らず赤にする（`if` / `while` / `until` / `!` / `coproc` の後ろもコマンド位置に数える）。
同じ行に `kill` があるかどうかは見ない。
手で打つコマンドは `scripts/claude-hooks/pattern-process-guard.sh` が実行前に拒む。判定基準は shell-lint の S2（パターン照合でプロセスを殺す）・S3（`pgrep -f`）と同じ一つのもの（`scripts/lib.sh` の `PATTERN_KILL_RE`・`PATTERN_PGREP_RE`）で、
拒むときはプロセス番号で事を運ぶ書き方を示す。これは Claude Code の PreToolUse フックで、プロジェクトは `.claude/settings.json` の `hooks.PreToolUse` に一度登録する：

```json
{"matcher": "Bash", "hooks": [{"type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/.claude/singlefs-ai-sop/scripts/claude-hooks/pattern-process-guard.sh"}]}
```

登録していないセッションでは、手で打つコマンドは依然としてこの条の文面だけが頼りである。

## 装置が起こすサンプルのプロセスは、それ専用のプロセスグループに入れる

装置・判定スクリプト・再実行スクリプトがサンプルのプロセス（本物の shell、テスト対象のプログラム、サンプルのコマンド）を起こすとき、判定基準は：**サンプルが一つ終わるたびに、それが起こしたプロセスが一つも残っていないこと。**

- サンプルは一つずつ専用のプロセスグループに入れる：shell では `setsid` で起こし、Python の `subprocess` には `start_new_session=True` を付ける。
- タイムアウト時と終了時にはグループ全体にシグナルを送る。まず TERM、猶予を過ぎたら KILL：Python は `os.killpg(<プロセスグループ番号>, <シグナル>)`、shell は `kill -TERM -- -<プロセスグループ番号>`。直接起こした一つだけを止めない。
- 走り終えたらプロセスグループ番号で `/proc` を一通り確かめ、グループにプロセスが残っていないことを見る。残ったものは止め、そのサンプルの失敗メッセージに書く。
- 直接の子プロセスだけを止めると孫プロセスが残る：プロセス置換で起きた `cat` がパイプの書き込み端を握ったままになり、そのパイプを読む側はいつまでも EOF を受け取れない。

これはまだ検査になっていない：起こしたものがサンプルかどうか、タイムアウト時と後始末でグループ全体を止めたかどうかは、スクリプトからは確実に見分けられないので、レビューに頼る。

## バックグラウンドのタスクやサブエージェントを起こしたら、定期的に見直す。振った側が応答しないときに限って終わらせる

長い仕事は待ってよい。ただし誰かが見ていること：

- **起こしたものは見直す。** バックグラウンドで起こしたタスクや送り出したサブエージェントは、振った側が定期的に見る。最後の動作からどれだけ経ったか、
  待ちループで止まっていないか、同じコマンドが同じ出力のまま繰り返されていないか、書いているファイルがまだ伸びているか。
- **検出と処置を分ける。** 詰まりや空回りを検出する道具（hook、見張りのスクリプト）は記録と報告だけをし、コマンドを止めない。プロセスを殺さず、サブエージェントを止めない。例外は振った側が応答しないときだけ。
  終わらせるかどうか、どう処置するかは、振った側が見てから決める。報告したあと振った側が応答しなければ（同じことを続けて何度報告しても、処置も確認もない）、報告した側（人、エージェント、検出した道具）が終わらせてよい：プロセスは `scripts/proc.py stop <プロセス番号>`、サブエージェントはそれを止める道具で止める。終わらせたらそれを報告する。
  ある一種類の危険な書き方を拒否するフックはここに含まれない（`session-wrapup.md` 第 4 条「同じリポジトリで別のセッションが動いていないか」：書き込む前に、追跡されていないファイルの上書きを拒否する）。
- **サブ agent を止めたら、その変更と手元の作業をその場で決める。** 書きかけのファイルは一つずつ、残すか、戻すか、誰に続きを渡すかを決め、やり終えていない作業は誰が引き継ぐかを決める。
  決めたことは記録に書いて引き継ぐ側に伝え、持ち主のない書きかけの変更を残さない。
- **バックグラウンドのタスクとスクリプトのタスクの名前は使用者と話している言語で書き、それが何か、どの件を待っているかを書く。** 同時に走っているものは同じ名前にしない。名前だけで何をしているか言えないものは、名前を変えてから起動する。
- **ログの一行を待つ前に、その行が本当にそのファイルに書かれるかを確かめる。**
- Claude Code のようなセッションでは、長い仕事はバックグラウンドに置いて定期的に戻って見直し、フォアグラウンドで待ち続けない。

## 問題に当たったら、まずその部分を受け持つ別のエージェントがいないかを探す

対象は、作業中に当たった問題のうち、自分の今回のタスクでは解決できないもの、または自分の今回のタスクの受け持ちでないもの：自分が変えていないファイルでゲートが赤い、変えたいファイルを別のセッションが変えている、使いたいものを別のタスクが作っている、直せない、または直し方に自信がない。

直す、迂回する、止まって待つ、の前に、順に行う：

1. **まず誰が受け持っているかを調べる。** 動いているエージェントとセッションを一覧にし（Claude Code では `ListAgents`）、タスク名、変えているファイル、直近の動作から、問題のある部分を受け持っているものがいるかを判定する。受け持ちかどうか自信がなければ、メッセージを送って尋ねる。
2. **受け持っているものがいれば、そこにメッセージを送り**（Claude Code では `SendMessage`）、その受け持ちの部分を自分では変えない。メッセージには、どのファイル、どの行、何が見えるか、どう再現するか、自分の今回の変更が持ち込んだものか、何をしてほしいか、または何を尋ねたいかを書く。
3. **自分では直せない、または他人の手元にある情報や権限が足りないときは、自分から助けを求めるメッセージを送る。** 黙って迂回しない。待ち続けもしない。
4. **受け持つものが一つもいない場合**：自分の今回のタスクに属するなら自分で処理する。属さないなら、使用者か振った側に報告し、問題がどこにあるか、誰に渡すのを勧めるかを書く。
5. **送ったあとは、それに依存しない手元の作業を続け**、返事が来たらその部分に戻る。相手がずっと応答しなければ、使用者か振った側に報告し、相手の受け持ちの部分を勝手に引き取らない。

自分が変えていないファイルでの赤の判定は `session-wrapup.md` 第 4 条「同じリポジトリで別のセッションが動いていないか」を、メッセージでよそのやり方を伝えるときは `verify-before-claiming.md`「よそのやり方を伝えるときは、出所か原文を付ける」に従う。

これはまだ検査になっていない：受け持ちを調べたか、送るべきものを送ったかは review に任せる。

## 一つのスクリプトの中の検査項目は、並行にできるなら並行にする

**判定基準：この一群の検査項目が互いに依存せず、かつ各項目がサブプロセスを起こして仕事をする
（ビルド、テスト実行、仮想機の起動、python の起動）のなら、一つずつ待たずに並行で走らせる。**

速くなったら、残りの時間がどこへ行っているかをもう一度見る：意図的に空待ちする用例（例えば、検証しているのがまさに「時間切れの論理を壊すと `wait` が返らない」ことである用例）は、並行にしても縮まない。

**次の三つは並行にしない**：

- 後の項目が前の項目の産物を読む。
- 書き込み可能な状態を共有している（同じ一時ディレクトリ、同じ target ディレクトリ、同じ装置）。並行にするなら各項目に一つずつ与える。
- 各項目がそもそも速く、数ミリ秒しか走らない。

並行度（プロセス数、およびプロセス内のスレッド数）は引数か環境変数から取り、与えられなければ `nproc` から取る。決め打ちしない。

## 並行が失敗を飲み込んではならない

回収の書き方は二つしかない：起こすときに `pids+=($!)` を控え、回収時に `wait "$pid"` で一つずつ終了コードを取るか、
並行する各項目が自分の終了コードファイルを書き、回収は仕事を配ったときのあの表の順に一つずつ判定するかである。
引数のない `wait` は使わず、バックグラウンドの本体に `|| bad=1` と書いて親が `$bad` を読むこともしない。

`scripts/shell-lint.sh` の S6 がこれを判定する。コマンド位置にある引数のない `wait` は赤になる。
終了コードを本当に別の場所で回収しているなら、その行に `# shell-lint:exit-collected <どう回収しているか>` と書く。理由の省略は許されない。

**並行する各項目は、出力を直接 stdout へ書いてはならない。** 各項目は自分のファイルに書き、回収は仕事を配った順に読み戻す。

**配った項目の数だけ、回収されなければならない。** 回収時に数を数え、配った数と合わなければ全体を赤にする。

**並行にしたあとは、赤くなれることを証明し直す。** `show-me-test.md` の通りにする。必ず赤くなる入力を与え、並行版でもなお赤くなるかを見る。

## echo で成功を装わない

`コマンド 2>/dev/null; echo "完了"` のような成功の報じ方をしない。
状態を変えるコマンドは必ず**実際の状態を読み戻して**検証する：判定するのは読み戻した内容であって、そのコマンドの終了コードではない。

## `/proc`・`/sys`・cgroupfs 配下のファイルは中身を読んで空かどうかを判定する

これらの場所のファイルサイズは中身を反映しない。procfs と cgroupfs は 0、sysfs は 4096 を報告する。
空かどうか、プロセスがいるかどうかは中身を読んでから判定する：`[[ -n "$(< "$cgroup_directory/cgroup.procs")" ]]`。`[ -s ファイル ]`、`stat` の `%s`、`find` の `-size` と `-empty` は使わない。

`scripts/shell-lint.sh` の S8 がこれを判定する。この三つの書き方が、字面で `/proc/`・`/sys/` から始まるパス、またはファイル名が `cgroup.<名前>` のパスに当たっていれば赤になる。
パスがすべて変数の中にあり、ファイル名も見分けられないものは判定しない。shell 以外の言語（python の `os.path.getsize`、`st_size` など）は判定せず、review に任せる。

## 結果の回収には完全性のゲートを設ける

**やり方**：被テストプログラムが最終行で「合計何件出したか」を申告し、
回収側は件数を突き合わせ、合わなければその回を破棄する。
このゲート自体も先に赤くなることを証明しておく——
申告する件数が実際に出した件数より一件多い偽プログラムを食わせ、赤にならねばならない。

## ゲート付きのスクリプトは、判定し終えてから産物を渡す

一つのスクリプトが結果を出し、それが使えるかどうかの判定も受け持つなら、**産物は判定が済んでから呼び出し側に渡す**。

**やり方**：結果はまず一時ファイルに書き、ゲートを通ってから出力する。赤判定のときは stdout を空のままにする。
このゲートも赤くなることを示す：スクリプトを「先に出力、後で判定」に戻したら、自己検査が赤くならねばならない。

## サブシェル内の代入は親プロセスに戻らない

`exit_code="$(run_one ...)"` の形では、`run_one` が変数に代入しても**親では空**である。
**値を渡すならファイルに落とすか引数で渡すこと。変数に頼らない。** これは `scripts/shell-lint.sh` の中の赤くなる一項目である。

## スクリプトでファイルを書き換えたら読み戻して確認する。警告はタダで得られる信号である

スクリプトで文字列置換を使ってコードや文書を書き換えるときのやり方は二つ：

1. **置換は命中数を検証すること**：置換件数が 0 ならエラーで終了する。「書き換えたつもり」で済ませてはならない。
2. **書き換えた後に読み戻す**：新しい内容が入っているか grep するか、実際に一度動かして挙動が変わったか確認する。

**コンパイラや linter の警告を見過ごしてはならない。**

## プロセス境界で起きる三つの沈黙した失敗

| 形態 | どう書くか |
|---|---|
| `set -e` の下で `内側; exit_code=$?` と書く | 終了コードは `if` の中で取る：`if 内側; then exit_code=0; else exit_code=$?; fi` |
| `export 変数名="$(コマンド)"` / `local 変数名="$(コマンド)"` | 先に代入し、それから `export` する。二行に分けて書く |
| ハンドシェイク用の環境変数が子プロセスに漏れる | 読んだらすぐ `unset` する。子プロセスを起こすときは `env -u` で消す |

**判定基準は「この値はプロセスを何段またいだか」**である：一段またいだら、次の段でまだ在るのか、在ってよいのかを問う。

## パイプの終了コードは、欲しいものではない

`コマンド | head` の後の `$?` も、`コマンド | grep パターン && 後続の処理` も、判定しているのはパイプの最後の段であって `コマンド` ではない。

**やり方**：前段の成否を判定するには `${PIPESTATUS[0]}` を使うか、
そもそもパイプでつながない——先に出力を変数かファイルへ落とし、終了コードを判定してから処理する。

`scripts/shell-lint.sh` の S7 がそのうちの一つを判定する。`pipefail` を設定したスクリプトで `grep -q` で終わるパイプ（`… | grep -q パターン`）は赤になる。
直し方：前段の出力を先に変数へ落とし、`grep -q パターン <<<"$変数"` とする。前段のないこの書き方は判定しない。

## テストイメージは必ず一時ディレクトリに置く

リポジトリ内には置かない。イメージのパスは環境変数から取り、既定は `${TMPDIR:-/tmp}` とする。

**イメージを作った装置は、テストが終わるときに自分で消す**：成功でも失敗でも panic でも消す。Rust は Drop ガード、shell は `trap … EXIT` を使う。
現場を見るために残すのは明示的なスイッチ（環境変数）で有効にし、残したときはパスを印字する。有効にしていなければ消す。
ゲート段階が赤になったときは、現場を `$TMPDIR` に残し、対処の中でそのパスを示してよい。
実行をまたいで再利用するつもりのキャッシュ（ビルド成果物の類）はイメージではない：`$TMPDIR` ではなく `${GATE_CROSS_RUN_TMPDIR:-${TMPDIR:-/tmp}}` の下かプロジェクトの定めた場所に置く。

`gate.sh` がこれを判定する：実行のたびに各段階へその実行専用の `TMPDIR` を渡し、最後に中に何が残っているかを見る（段階「走り終えて一時ファイルを残していない」、`跑完没留下临时文件`）。
ほかの段階がすべて緑なら、残ったものを赤にして名前と大きさを並べ、終了時に代わりに消す。どれかの段階が赤なら、この項目は今回判定せずと記録し、その実行の一時ディレクトリを丸ごと残してパスを印字する。見終わったら自分で消す。
赤のときにこうして残したものは最新の 3 つだけ残し、それより古いものは後で走った実行が消す。
これに見えないもの：パスを `/tmp` に決め打ちして `TMPDIR` を通さない装置、ゲートの外で手で走らせたテスト、ゲートが中断された後もまだ走っている子プロセスが作ったもの。

## 破壊的な操作は、動かす前に目で確かめる

`mkfs` / `dd` / `dmsetup remove` のようなコマンドは、**対象デバイスを変数から取り、先に `lsblk` で印字して確認すること。**
`/dev/sdX` のリテラルをハードコードしてはならない。
