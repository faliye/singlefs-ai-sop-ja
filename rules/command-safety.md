# プロセスとコマンドの規範

このうち六条は赤くなる検査であり、`scripts/shell-lint.sh` が判定する：
**パターン一致でプロセスを殺すこと**（`pkill -f`、`killall`）、**`pgrep -f`**、**サブシェル内の代入で値を外に持ち出すこと**、
**スクリプト内で git の取り消し系コマンドを使うこと**、
**`rm -rf` を守りのない変数パスに当てること**、**引数のない `wait`**。
残りはまだ文章のままである。機械判定の基準が定まっていないからだ
（`show-me-test.md`「ゲートが証明できること、できないこと」——
やっていないことは、ぼかさず言う）。

## 取り消せない操作は、手を出す前にもう一度考える

判定基準は一つだけ：**この一歩を踏んだあと、戻れるか。**

戻れないものは二種類あり、扱いが違う：

| 種類 | 例 | どうするか |
|---|---|---|
| **未コミットの変更を捨てる** | `git checkout <ファイル>`、`git restore`、`git reset --hard`、`git clean` | 先に `git stash` するか `cp` で外に控えを取る。そのファイルの未コミット変更を**全部**捨てると分かっているときだけ使う |
| **データを直接消す** | `rm -rf`、`> ファイル`、`sed -i`、`rsync --delete`、`mkfs`、`dd` | 先に対象を見る（`ls` / `git status` / `lsblk`）。変数のパスには `${VAR:?}` の守りを付ける |

**実際に踏んだ**：一時的な `sed` を取り消したいだけで `git checkout <ファイル>` を使い、
同じファイルのその回の未コミット変更を丸ごと消してしまった。
そのときは reflog に残っていた直前の commit から拾えたが、
その commit が無ければ失われていた。

**だから、使い捨ての実験は副本でやる。** 作業ツリーで書き換えてから戻そうとしない。

**スクリプトの中に git の取り消し系コマンドを書いてはならない。**
スクリプトが走っている間、誰も `git status` を見ていない。そしてこれらに undo は無い。
スクリプト内できれいな状態に戻したいなら、先に `git stash` するか、
リポジトリごと複製して副本の上でやる。

**`rm -rf` を変数のパスに当てるときは空値の守りを付ける。**
`rm -rf "$d/x"` は `$d` が空だと `rm -rf /x` になる。`rm -rf "${d:?}/x"` と書けば、
`rm` が動く前にシェルがエラーで止まる。
（`rm -rf "$d"` のように後ろにパスが続かないものは不要：空なら `rm -rf ""` となり、`rm` 自身が拒む。）

## `pkill -f` / `killall` は一律禁止

パターン文字列はラッパー自身のコマンドラインにも現れるため、
**自分のシェルを殺す。**

プロセスを止めるには：まず `ps` で列挙して目で確かめ、
二つ目のコマンドで**リテラルの pid** を指定して殺す。
`scripts/proc.py stop プロセス番号` に任せてもよい：TERM を送り、`--grace` 秒（既定 10）経ってもまだいれば KILL を送り、止める対象がコマンドを発したプロセス自身かその祖先なら拒む。
数を数える用途には `/proc` の構造化された判定を使い、自分のプロセスツリーを除外する。

**同じパターン文字列を待ちループに入れると別の形になる：誤って殺しはしないが、永遠に空回りする。**
`until ! pgrep -f "X"; do sleep 5; done` のような待ち方では、パターンがこのループ自身の走っているシェルのコマンドラインに当たり、
`pgrep` は常に当たりを返してループは決して抜けず、しかもエラーも出ない——外から見えるのは「まだ待っている」だけである。
⇒ プロセスの終了を待つには、その**リテラルの pid** を使う：`until ! kill -0 "$pid" 2>/dev/null; do sleep 5; done`。
自分で起こした裏のジョブは `wait` で待つ。自分で起こしていないもの（別のスクリプトが起動したデーモンなど）は、起動する側に pid をファイルへ書かせてから待つ。
pid を控えていなければ、`scripts/proc.py find 実行ファイル名 [--argument 引数]` でプロセス番号を探す：実行ファイル名を一字一句比べ、パターン文字列をコマンドライン全体と照合することはせず、このコマンドを発したプロセスの系統も列挙しない。
プロセス番号が手に入ったら `scripts/proc.py wait プロセス番号 --timeout 秒` で終了を待つ。時間切れまでに終わらなければ、まだ生きているものを列挙して終了コード 3 で返る。
`scripts/shell-lint.sh` の S3 は、スクリプト中のコマンド位置にある `pgrep -f` を一箇所残らず赤にする（`if` / `while` / `until` / `!` の後ろもコマンド位置に数える）。
同じ行に `kill` があるかどうかは見ない：先に変数へ代入して次の行で kill しても、ただ数えるだけでも、パターンは自分自身のコマンドラインに同じように当たる。
手で打つコマンドは `scripts/claude-hooks/pattern-process-guard.sh` が実行前に拒む。判定基準は shell-lint の S2・S3 と同じ一つのもの（`scripts/lib.sh` の `PATTERN_KILL_RE`・`PATTERN_PGREP_RE`）で、
拒むときはプロセス番号で事を運ぶ書き方を示す。これは Claude Code の PreToolUse フックで、プロジェクトは `.claude/settings.json` の `hooks.PreToolUse` に一度登録する：

```json
{"matcher": "Bash", "hooks": [{"type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/.claude/singlefs-ai-sop/scripts/claude-hooks/pattern-process-guard.sh"}]}
```

登録していないセッションでは、手で打つコマンドは依然としてこの条の文面だけが頼りである。

## バックグラウンドのタスクやサブエージェントを起こしたら、定期的に見直す。強制的に終わらせない

長い仕事は待ってよい。ビルド、全件の再実行、サブエージェントに渡した仕事が何時間かかっても普通のことだ。防ぐべきは**誰も見ていない待ち**である。
待っている条件が決して成り立たず、外からは「まだ動いている」としか見えない。


だから：

- **起こしたものは見直す。** バックグラウンドで起こしたタスクや送り出したサブエージェントは、振った側が定期的に見る。最後の動作からどれだけ経ったか、
  待ちループで止まっていないか、同じコマンドが同じ出力のまま繰り返されていないか、書いているファイルがまだ伸びているか。
- **検出と処置を分ける。** 詰まりや空回りを検出する道具（hook、見張りのスクリプト）は記録と報告だけをし、コマンドを止めず、プロセスを殺さず、サブエージェントを止めない。
  終わらせるかどうか、どう処置するかは、振った側が見てから決める。道具が「時間切れなら殺す」と決めると、まだ前に進んでいた仕事まで一緒に殺してしまう。
  ある一種類の危険な書き方を拒否するフックはここに含まれない（`session-wrapup.md` 第 4 条：書き込む前に、追跡されていないファイルの上書きを拒否する）。
- **ログの一行を待つ前に、その行が本当にそのファイルに書かれるかを確かめる。**
- Claude Code のようなセッションでは、モデル呼び出しの間隔が空きすぎるとプロンプトキャッシュが切れ、文脈全体を書き直すことになる。

## 一つのスクリプトの中の検査項目は、並行にできるなら並行にする

**判定基準：この一群の検査項目が互いに依存せず、かつ各項目がサブプロセスを起こして仕事をする
（ビルド、テスト実行、仮想機の起動、python の起動）のなら、一つずつ待たずに並行で走らせる。**

一つずつ走らせる代償は実時間が項目ごとに積み上がることであり、ゲートが遅くなれば誰も手元で走らせなくなる。
提出する側は押し上げてリモートに赤か緑かを教えてもらう方へ切り替え、
`sop-first.md` の求める「手元で走り、リモートと同じ判定を出す」がその場で失われる。


**速くなったら、残りの時間がどこへ行っているかをもう一度見る。** 同じ実測で、並行後の 21.4 秒のうち 10 秒は
**一件**の用例が空待ちしていた（それが検証しているのは、まさに「時間切れの論理を壊すと `wait` が返らない」ことである）。
その待ちは意図的なものであって並行度の問題ではなく、機械を足しても消えない——
**並行が治すのは「サブプロセスを一つずつ待つこと」であり、「その待ちに理由があるか」は治さない。**

**次の三つは並行にしない**：

| 状況 | 理由 |
|---|---|
| 後の項目が前の項目の産物を読む | 前後の依存があり、並行では書き終わっていないものを読む |
| 書き込み可能な状態を共有している | 同じ一時ディレクトリ、同じ target ディレクトリ、同じ装置。並行にするなら各項目に一つずつ与える |
| 各項目がそもそも速い | プロセスを一つ起こすのに数ミリ秒かかる。項目が数ミリ秒しか走らないなら並行は差し引き損である |

並行度は `nproc` から取り、決め打ちしない。仮想機やビルドのような重い仕事には、記憶容量と装置から別に上限を定める。

## 並行が失敗を飲み込んではならない

**引数のない `wait` の終了コードは常に 0 である。** バックグラウンドのその一群で何件赤くなっても、一言も言わない。


| 書き方 | 親プロセスに見えるもの |
|---|---|
| `for …; do 検査 & done; wait` | **0** |
| バックグラウンドの本体に `\|\| bad=1` と書き、親が `$bad` を読む | **0**。バックグラウンドの本体はサブシェルであり代入は戻らない。「サブシェル内の代入は親プロセスに戻らない」がそれである |
| 起こすときに `pids+=($!)` を控え、回収時に `wait "$pid"` を一つずつ | **7** |
| 各項目が終了コードを自分のファイルに書き、回収時に一つずつ読む | 読める |

したがって回収の書き方は二つしかない。`wait "$pid"` で一つずつ終了コードを取るか、
各項目が終了コードを自分のファイルに落とし、回収時に決まった順で一つずつ読むかである。
singlefs の `.claude/gate.d/55-qemu-first-transaction.sh` は後者であり、仮想機三台が同時に走り、
それぞれが終了コードを `$work/<モード>/vm-exit` に書き、回収はモード表の順に一つずつ判定する。

`scripts/shell-lint.sh` の S6 がこれを判定する。コマンド位置にある引数のない `wait` は赤になる。
終了コードを本当に別の場所で回収しているなら、その行に `# shell-lint:exit-collected <どう回収しているか>` と書く。
理由の省略は許されない——`.claude/abbreviations` や `.claude/naming-lint-exclude` と同じ規矩であり、
通してほしいなら終了コードの行き先を書き出すこと。

**出力を直接 stdout へ書いてはならない。** バックグラウンドのジョブ二つが同時に印字すると、
パイプの緩衝を超えた行は互いを断ち切り、`✗` とその後ろに続く出口が引き裂かれる。
`sop-first.md` が拒否のたびに求めているのは、まさにその出口である。
順序も走らせるたびに変わり、同じ入力で二回走らせて出力が違えば、どちらが本当かは誰にも言えない。
だから各項目は自分のファイルに書き、回収は仕事を配った順に読み戻す。

**配った項目の数だけ、回収されなければならない。** 並行にしたあと、一項目が走らなかったことは誤りとして現れない。
その項目のファイルが無く、ループが一回少なく回り、末尾は変わらず緑を報じる。
回収時に数を数え、配った数と合わなければ全体を赤にする
（「結果の回収には完全性のゲートを設ける」の項が同じことを扱っている）。

**並行にしたあとは、赤くなれることを証明し直す。** 並行にすること自体が、
それまで赤くなっていた検査を緑にしてしまう——上の表の最初の二行がまさにそれである。
`show-me-test.md` の通りにする。必ず赤くなる入力を与え、並行版でもなお赤くなるかを見る。
証明し直していない並行化は、その検査を切ったのと同じである。

## echo で成功を装わない

`cmd 2>/dev/null; echo "完了"` のその echo は**無条件に実行される**——
sudo が失敗していても「完了」と出る。

状態を変えるコマンドは必ず**実際の状態を読み戻して**検証する：
`systemctl stop X` の後は `is-active` で確認する。`stop` の終了コードだけでは足りない。

## 結果の回収には完全性のゲートを設ける

被テストプログラムが結果を印字し、外側のスクリプトが回収する——
**この経路で一行落ちるのは無言で起きる。**
出力には別のものが混ざり込む（ほかのプロセスが書き込んだ文字、エスケープシーケンス、改行されていない直前の一文）。
行頭で錨を打つ（`grep '^ANCHOR'`）と、行頭を上書きされた行を黙って取りこぼす。
外から見えるのは「一項目少ない」であって「失敗した」ではない。

**やり方**：被テストプログラムが最終行で「合計何件出したか」を申告し、
回収側は件数を突き合わせ、合わなければその回を破棄する。
このゲート自体も先に赤くなることを証明しておく——
N 件出したと称して N−1 件しか出さない偽プログラムを食わせ、赤にならねばならない。

## ゲート付きのスクリプトは、判定し終えてから産物を渡す

一つのスクリプトが結果を出し、それが使えるかどうかの判定も受け持つなら、**産物は判定が済んでから呼び出し側に渡す**。
先に結果を stdout に出してからゲートを走らせると、呼び出し側のリダイレクト先ファイルには、無効と判定された出力がもう保存されている——
ファイル名は呼び出し側が付けたもので、正当な産物と見分けがつかない。終了コードはエラーを報告しても、ファイルは残る。
次にディレクトリを見て回る人は、そのときの終了コードまでは確かめない。


**やり方**：結果はまず一時ファイルに書き、ゲートを通ってから出力する。赤判定のときは stdout を空のままにする。
このゲートも赤くなることを示す：スクリプトを「先に出力、後で判定」に戻したら、自己検査が赤くならねばならない。

## サブシェル内の代入は親プロセスに戻らない

`rc="$(run_one ...)"` の形では、`run_one` が変数に代入しても**親では空**である。
結果の回収がその変数（ログのパスなど）に依存していれば、
回収件数は永遠にゼロのまま、終了コードは 0——またひとつ、緑のまま誤る。
**値を渡すならファイルに落とすか引数で渡すこと。変数に頼らない。**

`set -u` の下ではさらに悪い。参照した側は空値を得るのではなく、その場で
「unbound variable」となり、**診断を出力する前にスクリプトを道連れにする**。

## スクリプトでファイルを書き換えたら読み戻して確認する。警告はタダで得られる信号である

スクリプトで文字列置換を使ってコードや文書を書き換えるとき、
**マッチしなければエラーにはならず、ただ何も起きないだけである。**
インデントが半角スペース一つずれている、引用符の種類が違う、行末に余分な空白がある——
置換は無言で失敗し、終了コードは 0 のままである。

**やり方は二つ**：
1. **置換は命中数を検証すること**：置換件数が 0 ならエラーで終了する。「書き換えたつもり」で済ませてはならない。
2. **書き換えた後に読み戻す**：新しい内容が入っているか grep するか、実際に一度動かして挙動が変わったか確認する。

⚠️ **コンパイラや linter の警告は、この種の失敗を検知する最も安価な信号であり、見過ごしてはならない。**

## プロセス境界で起きる三つの沈黙した失敗

`set -e`、`pipefail`、環境変数は**プロセスをまたぐ**ところで揃って牙を剥く。形はどれも「終了コードは正しいのに、判定基準が走っていない」である：

| 形態 | 実測 | どう書くか |
|---|---|---|
| `set -e` の下で `内側; rc=$?` と書く | 内側が赤と判定した途端、外側はその行で抜けてしまい、後片付けまで届かない——赤判定こそ最も結果を見たい場面なのに | 終了コードは `if` の中で取る：`if 内側; then rc=0; else rc=$?; fi` |
| `export X="$(cmd)"` / `local x="$(cmd)"` | `export` と `local` はコマンドであり、自身の終了コードがコマンド置換のそれを覆い隠す。`cmd` が失敗しても成功として扱われる | 先に代入し、それから `export` する。二行に分けて書く |
| ハンドシェイク用の環境変数が子プロセスに漏れる | 外側が内側へ渡した変数が環境に残り、内側が起こした三段目がそれを自分への入力として拾う——実測：ゲートの自己検査を入れ子で走らせたとき、偽の赤が二件 | 読んだらすぐ `unset` する。子プロセスを起こすときは `env -u` で消す |

**だから判定基準は「この値はプロセスを何段またいだか」**である：一段またいだら、次の段でまだ在るのか、在ってよいのかを問う。

## パイプの終了コードは、欲しいものではない

`cmd | head` の後に `$?` を取ると、得られるのは `head` の終了コードであって `cmd` のものではない。
`cmd | grep x && do_something` も同様——判定しているのは `grep` の成否である。

結果として**失敗が飲み込まれる**：`cmd` はすでに落ちているのに、スクリプトはそのまま先へ進み、
以降の各段階は存在しない結果を前提に動く。

**やり方**：前段の成否を判定するには `${PIPESTATUS[0]}` を使うか、
そもそもパイプでつながない——先に出力を変数かファイルへ落とし、終了コードを判定してから処理する。

## テストイメージは必ず一時ディレクトリに置く

リポジトリ内には置かない。
数 GB のイメージを誤って git に入れるのは取り返しのつかない厄介事である。
イメージのパスは環境変数から取り、既定は `${TMPDIR:-/tmp}` とする。

## 破壊的な操作は、動かす前に目で確かめる

`mkfs` / `dd` / `dmsetup remove` でデバイス名を打ち間違えれば実データが消える。
**対象デバイスは変数から取り、先に `lsblk` で印字して確認すること。**
`/dev/sdX` のリテラルをハードコードしてはならない。
