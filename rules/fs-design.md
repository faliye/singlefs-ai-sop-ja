# 設計規律

個別の設計決定はプロジェクトの `kb/decisions.md` に記す。
本書には**決定をまたいで効く規律**だけを書く。

## 機能からではなく、トランザクションから始める

書き込み経路の核心は COW のコミット機構であり、他のすべてはその上に乗る。
新しい機能はいずれも「新しい種類のトランザクション」である。
**トランザクション層を欠いた機能実装は一切受け取らない。**

帰結：最初に動くべき目標は「ファイルを作れる」ことではなく、
「トランザクションを正しくコミットできる」ことである——
ブロックを確保し、書き、コミットするだけで、
ディレクトリもツリーもなく、性能が最低でも構わない。

## 会計はトランザクションの副産物であり、事後の走査ではない

容量集計・クォータ・スナップショット使用量は、
**コミット時に増分的に維持**されなければならない。
「後から全部走査しないと出せない」会計設計は一律に却下する。

checker は走査してよい——**その職責はまさに、走査によって
増分会計が誤っていないかを検証することである。**
この対照関係が会計の正しさを検証する中核手段であり、両者を混同しない。

## メタデータブロックは自己記述的でなければならない

任意の一ブロックを単独で拾い上げた時、
「自分は誰か、誰に属すか、何世代目か」に答えられなければならない。
これは「全面走査による再構築」が物理的に可能であるための前提であり、
**フォーマット層でしか得られず、後から足すことはできない。**

## feature bit は三段階、かつ空きを残す

`incompat`（認識できなければマウント不可）／
`compat_ro`（認識できなければ読み取り専用でマウント）／
`compat`（認識できなくても通常どおり）。

## 異なるアドレス空間は異なる Rust 型でなければならない

論理アドレス、物理アドレス、デバイス内オフセット、世代番号、inode 番号——
すべて newtype とし、**取り違えたらコンパイルが通らないこと。**

これは一群の実行時バグをコンパイルエラーへ変えるものであり、
Rust を選ぶ主要な理由の一つである。
`u64` をあちこちに渡すのは、既存実装に実在するバグの発生源である。

## トランザクション層は一つ、すべての構造で共有する

特定の経路（fsync など）のために第二のトランザクション機構を設けない。
fsync 専用のログツリーを持つのはよくある手法であり、
同時によくある独立したバグの発生源でもある。

# 万能解を求めない：分岐してよいが、正しい借りを返すこと

性能・安全性・デバイス制約の三者に、単一の最適解が存在しないことは多い。
**万能解を無理に作るより、明示的に分岐せよ**——
規模が違えば、媒体が違えば、安全要求が違えば、実装も分ける。

## なぜ今は以前より細かく分けられるのか

従来のファイルシステムが単一の方式を好んだのは、
問題そのものが単純さを要求したからというより、
**一人の維持者が全体を頭に収める必要があった**からである：
記憶の負担、一件ずつの整理、N 本の経路の一貫性維持、
一箇所を直したらどこを同期させるか——これらは人間のボトルネックである。

この部分の費用は確かに解消された：論理の整理と一貫性の維持は機械の得意分野である。
**したがって本プロジェクトは「単純なほど良い」を前提とせず、状況に応じた細分を許す。**

これは `machine-first.md` の判定基準が設計層に現れた形である——
「設計は統一し概念は少なく」の元々の理由は維持者が収めきれるためであり、
その理由はもはや成立しない。

## しかし解消されていない費用が四つある

1. **検証は線形ではなく組み合わせ的である。**
   クラッシュ一貫性は分岐ごとではなく**相互作用ごと**に数える：
   操作の途中で条件が変わり、復旧時に別の分岐へ入れば、
   検証すべきは直積になる。これは誰がコードを書いたかでは小さくならず、
   **分岐同士が互いに隔離されているかどうか**でのみ小さくなる。
   → **操作中に変化しない入力の上でのみ分岐する。**
   デバイス種別は安定なのでよい。「現在の使用率」は操作の途中で閾値を跨ぎうるため、
   危険な分岐変数である。

2. **フォーマット上の分岐は恒久である。**
   コードの分岐は削除できるが、**ディスク配置の分岐は削除できない**——
   以後すべての読み手が、あらゆる過去の配置を永久に支え続けねばならない。
   → **挙動では分岐を許し、フォーマットでは分岐を惜しむ。**

3. **ゲートの実時間は現実の制約である。**
   分岐 × クラッシュ点は機械の時間だが、ゲートが八時間かかるなら
   人は提出前にそれを走らせなくなる——
   そして「手元で先に走らせ、リモートと同じ判定を得る」はこの設計全体の支点である。
   **ゲートの実行時間そのものが設計上の制約である。**

4. **稀な分岐は腐る。**
   千回に一回しか通らない分岐のバグは本番でしか現れない——
   テストがその分岐へ**強制的に**入れる場合を除いて。

## 五つの必須要件

1. **切り替えの判定基準は明示的・計算可能で、書き下されていること。**
   「感覚で」は不可であり、コードに埋め込まれた魔法の数値も不可である。
   判定基準を述べられない = その分岐はまだ考え切れていない。
2. **すべての分岐はテストから強制的に到達できること。**
   判定基準を無視して指定の分岐へ直接入るための、テスト専用のスイッチを残す。
   **入れなければテストしていないのと同じ**——
   運任せで通った分岐は、覆われていない。
3. **各分岐を個別に検証すること。クラッシュ点リプレイを含む。**
   「別の分岐はテスト済み」は数えない——
   分岐の意義は挙動が違うことであり、ならばクラッシュ時の意味も違いうる。
4. **分岐は観測可能であること**：実行時にどちらを通ったか分かること。
   **誤った分岐を通ることは性能の崖であり、崖はエラーを出さない**——
   観測手段がなければ永久に見つからない。
5. **分岐変数は操作の途中で変化してはならない。** 上の要件 1 を参照。

**逆に：判定基準が書けない時は一本だけ作る。しかも遅くて正しい方を先に作る。**
速い経路は最適化であり、遅い経路は下限である。まず下限を得てから最適化を語る。

## インデックス構造は多様でよいが、トランザクション層は多様であってはならない

データの種類によってアクセスパターンは大きく異なる
（逆引きインデックスは書き多く読み少なく、ディレクトリエントリは点検索、
extent は範囲検索）。アクセスパターンに応じて構造を選ぶことは許され、推奨されもする。
**唯一多様であってはならないのはトランザクション層である。**
