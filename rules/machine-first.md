# 機械優先：まず「読める」と「検証できる」を分ける

ソフトウェア工学の通行の指針の多くは、**「一人が全体を頭に収める」**という前提の上に育った。
その前提は失効しつつある：コードは人とモデルの協働で生まれ、
コードを読むという作業そのものもモデルに任せられる。

**本プロジェクトはこれらの指針を既定で継承しない。**
一条ごとに判定基準を通し直し、通らないものは捨てる。

## 姿勢：既定で従うのではなく、疑って継承する

既存の「ベストプラクティス」に対する既定の態度は**懐疑**であって、遵守ではない。

理由は単純である：**これらの指針の相当部分は、人間の認知能力が限られているという前提の下で、
工学品質の下限を支えるために存在する**。較正されているのは人間の限界である。
機械の処理能力はとうにその線を越えており、
**旧い限界に合わせて引いた下限は、低すぎる下限になる。**

すべてが誤りだという意味ではない——**理由を引き直せ**という意味であり、
「みんなそうしている」は理由にならない。

## この姿勢の前提と、その覆し方

「機械の処理能力はとうにその線を越えている」は方法論全体の土台である。
**これは反証可能な経験的主張であって、信条ではない。**
よってここに、それが依拠する二つの前提と、何を観測すればそれが覆るかを明記する——
**本ファイルに反論するなら、標的はこの二つの前提であって、以下の表ではない。**

### 前提一：コンテキスト窓は既に 2×10⁵ ～ 10⁶ トークンの桁にある

200K / 500K / 1M の三段。1M 段なら一つの crate をそのテスト・kb・決定記録ごと
一度に収められる。根拠：本リポジトリの今回の作業自体が 1M 段のセッションで走っている。
他社の数字はここに書かない——その場で確かめられない数字は証拠にならない。

**口径**：これは**公称の窓の上限**であって、「窓全体で同じ精度を保つ」ではない。
長いコンテキストの中盤での想起の減衰は既知の現象であり、
それがどの規模から効き始めるかを本プロジェクトは実測していない。

- **これが支えるもの**：「PR は小さく」「概念は少なく」「DRY を人手で同期」の三条の緩和。
  元の理由はいずれも「一度に収まらない」であり、1M 段ではその理由が自動的には成立しない。
- **これが支えないもの**：「推論範囲は有界に」は緩和の対象外である。
  窓は大きくなったが**依然として有限**であり、精度は距離とともに減衰する——
  だからモジュール境界と明示的な契約は、以前より価値が下がるのではなく上がる。

### 前提二：並行のインターリーブは既に網羅的に判定できる

「このバリアで足りるか」という類の判断に、**直観は再検証可能な答えを出せない。**
この作業は今や二つに分かれる：

| 誰が | 何を | 精度 |
|---|---|---|
| herd7 / LKMM | 与えられたメモリモデルの下で許されるインターリーブを**網羅**し、Never / Sometimes の判定を出す | 実際に書いたその litmus については完全 |
| モデル | コード中の同期パターンを litmus に翻し、問うべき場面を列挙する | **不完全——欠落はここにある** |

**口径**：精確なのはツールであってモデルではない。
ツールは書いた litmus にしか答えず、「問うべき場面を取りこぼしていないか」は何も保証しない。
だから `scripts/lkmm.sh` は両側の対照群を強制する：Never だけで Sometimes が無ければ、
バリアが止めたのか、そのパターンが元々当たらないのかを区別できない。

- **これが支えるもの**：「網羅性は機械検査できる」、およびそこから導かれる
  「網羅的な明示分岐を選ぶ」と「経路数が有界なら検証できる」。

### 前提が失効したら、どれを取り下げるか

前提は永久ではない。以下のいずれかを観測したら、対応する緩和をその場で取り下げる：

| 何を観測したら | 何を取り下げるか |
|---|---|
| 本プロジェクトの実規模でモデルが中盤の事実を落とす——窓に既にある制約を見落とす | 「PR は小さく」の緩和。収まる粒度で切り直す |
| 生成した重複コードが生成器と食い違う | 「DRY」の緩和。重複禁止に戻す |
| litmus の判定が実機ストレスの結論と矛盾する | 「網羅性は機械検査できる」。`lkmm.sh` は参考に降格し、ゲートから外す |

**この表が本ファイル自身の背理の一歩である**（`evidence-discipline.md`）：
「何を観測すれば覆るか」を言えない前提は前提ではなく、信仰である。

## 通行の指針に出会ったら、この手順を踏む

1. **それが元々どの問題を解いていたかを問う。** 言えないものは即座に捨てる——
   理由を言えない規則はどのみち守れない。
2. **その問題が今も存在するかを問う。** 解いていたのが「人が覚えきれない」
   「人が読み切れない」「レビュー帯域が足りない」であれば、たいてい既に存在しない。
3. **第二の理由があるかを問う。** 多くの規則は、人とは無関係な問題を
   たまたま併せて解いている（下の「残すもの」の表を参照）。
   あるなら残す。**そして理由をそちらへ書き換える。**
4. **書き換えた理由はゲートに落とせなければならない。** 落とせないものは助言に格下げし、
   規則としては書かない。

## 判定基準

> **この規則はコードを機械的に検証しやすくするのか、それとも人の目に優しくするだけなのか。**

- 人の目に優しいだけ → **捨ててよい**
- 検証を容易にする → **残す。ただし理由を書き換える**——
  「可読性」にぶら下げるのをやめる。可読性にぶら下がった規則は、
  次に誰かが「なぜ」と問うた時に守れない。

## 緩めるもの（人間の帯域の産物）

| 旧い指針 | 元々の理由 | 処置 |
|---|---|---|
| 設計は統一し概念は少なく | 維持者が収めきれるように | **緩める**——「一本の木にすべてを収める」の出所がまさにこれである |
| DRY、重複を避ける | 一箇所直すと複数箇所を同期させる必要がある | **緩める**：同期修正は機械の得意分野。ただし重複は**生成**するのであって手で写さない |
| PR は小さく | レビュー帯域 | **緩める**——二分可能・巻き戻し可能は依然として守る |
| 早すぎる最適化を避ける | 人間の時間予算 | 助言に格下げ |
| 関数は一画面に収める | 短期記憶と画面の高さ | **残す。理由を書き換え**：長さは「独立に検証できる一つのこと」で決まり、画面では決まらない |
| ネストは浅く | 人間の解析能力 | **緩める**：層数に上限は設けない。真の制約は**経路数**である——ループのネストは経路をほとんど増やさず、条件のネストは指数的に増やす。詳細は `engineering-philosophy.md` |
| 名前は自己説明的に | 次に読む人のため | **残す。理由を書き換え**：名前は装飾ではなく情報であり、省かれた意味はモデルにも補えない |

⚠️「関数は短く」「名前は自己説明的に」の二条は、本規則によって最も誤って削られやすい。
**緩めるのは「人間の頭に収めるための圧縮」であって、「意味を明示すること」ではない**——
後者はモデルにとっても利得である。
詳細は `engineering-philosophy.md` の「AI に優しい ≠ 読めない」を参照。

## 残すもの（誰がコードを読むかとは無関係）

| 指針 | 本当の理由（書き換え済み） |
|---|---|
| クラッシュ一貫性、不変条件 | 心理ではなく物理である |
| ディスクフォーマット互換 | 対外的な恒久契約であり、変えられない |
| テストの再現性 | あらゆる判断の前提であり、人にも機械にも当てはまる |
| 障害領域の隔離 | バグの影響範囲は誰がコードを読むかと無関係である |
| 二分可能・巻き戻し可能 | **変更量が大きいほどこの二つの価値は上がる**。下がるのではない |
| モジュール境界の明示的契約 | **契約がなければ一部分だけを単独で検証できない** |
| 推論範囲が有界であること | **増分的な検証は推論範囲が有界であることを要求する——コンテキストウィンドウもまた有限である** |

最後の二条が「可読性」として捨てられやすい。それらは可読性ではない。

## 帰結：ならばこう書くべきである

- 巧妙な汎用経路より**明示的な網羅分岐**を選ぶ——**網羅性は機械検査できるが**、
  「一つの関数で全ケースを捌く」はできない
- 制約をコメントで説明するより**型で不正な状態を表現不能にする**
- **不変条件は文書ではなくアサーションに書く**
- 重複は手で維持するより**生成する**
- コメントは「なぜこうなのか」を書き、「これが何をしているか」は書かない——
  後者は機械が自分で読める

## この二条の帰結はどう見えるか：コード例

最初の二つの帰結は最も議論になりやすいので、指させる形で書いておく。
議論はたいてい「この分岐は本当に必要か」から始まる——
**しかし判定基準は必要性ではなく、網羅性を誰が検査するかである。**

### 帰結その一：網羅的な明示分岐は、賢い汎用パスに勝る

```rust
// ✗ 汎用パス：新しい場合が増えても、コンパイラは何も言わない
fn node_size(dev: &Device) -> u32 {
    if dev.rotational { 64 * 1024 } else { 16 * 1024 }
}
```

```rust
// ✓ 網羅分岐：Zoned を足したら、ここを埋めるまでコンパイルが通らない
enum Medium {
    Rotational,
    Ssd,
    Zoned { zone_size: u32 },
}

fn node_size(m: &Medium) -> u32 {
    match m {                       // 要点は、**書かなかった** `_ =>` の腕にある
        Medium::Rotational          => 64 * 1024,
        Medium::Ssd                 => 16 * 1024,
        Medium::Zoned { zone_size } => (*zone_size).min(256 * 1024),
    }
}
```

**効いているのは、書かなかったワイルドカードの腕である。** `_ =>` を足すとコードは
短く「汎用的」に見えるが、実際にやったのはコンパイラの網羅性検査を切ることだ——
新しい場合は黙ってワイルドカードに落ち、誰も警報を上げないまま誤った挙動をする。

**したがって判定基準は「分岐が多いか」ではなく「ある場合を取りこぼしたとき、
先に気づくのは誰か」である**：コンパイラか、本番か。前者なら明示分岐、
後者はそれは汎用ではなく、検査を消しただけである。

### 帰結その二：型で不正な状態を表現不可能にする

```rust
// ✗ 一つの下層型が複数の意味を担う：取り違えてもコンパイルが通り、実行時に壊れる
fn read_block(addr: u64) -> Block;
fn free_extent(start: u64, len: u64);
// 呼び出し側が物理アドレスの位置に論理アドレスを渡しても、コンパイラは何も言えない
```

```rust
// ✓ newtype：取り違えるとコンパイルが通らない
#[derive(Clone, Copy, PartialEq, Eq)] pub struct Lba(pub u64);  // 論理アドレス
#[derive(Clone, Copy, PartialEq, Eq)] pub struct Pba(pub u64);  // 物理アドレス

fn read_block(addr: Pba) -> Block;
// read_block(Lba(x)) はコンパイルできない —— 実行時バグの一群が丸ごとコンパイルエラーになる
```

さらに一歩進めて、**「まだ検証していない」ことも型にする**と、
「検証を忘れた」という状態自体が書けなくなる：

```rust
// ✗ 状態を真偽値の欄で表す：確認を忘れてもコンパイラは関知しない
struct Node { bytes: Vec<u8>, checksum_ok: bool }

// ✓ 状態を型で表す：検証していないものは、検証済みの型になりようがない
struct RawNode(Vec<u8>);        // ディスクから読んだ直後、未検証
struct VerifiedNode(Vec<u8>);   // チェックサム照合済み

impl RawNode {
    fn verify(self, expect: Checksum) -> Result<VerifiedNode, CorruptBlock> { /* ... */ }
}

fn walk(node: &VerifiedNode) { /* ... */ }   // 検証を飛ばすと、そもそも引数が作れない
```

**この二条は同じ一つのことの両面である**：その一は「場合の取りこぼし」を
コンパイラに捕まえさせ、その二は不正な組み合わせを書けなくする。
**どちらも検査を人から機械へ移す**——それこそが本編の判定基準、
すなわち「機械的に検証しやすくなるか」である。

### 適用してはいけないとき

**この二条は「消せるもの」には無条件で成立し、「消せないもの」には別勘定が要る。**
誤ったコード分岐は消せる。しかし外部契約——ディスク形式、プロトコル、公開 API——に
書き込まれた分岐は消せず、以後すべての実装が永久に支え続けねばならない。
その側の判定基準は別に立てること。「明示分岐のほうが安全だ」の一言で押し通してはならない。

## 逆向きの注意：文書規律は放棄の対象ではない

`doc-discipline.md` の一式（本文は現状のみ、履歴は末尾へ、決定記録は kb へ）は
**人間の帯域の産物ではない。**

履歴が混ざった文書では、**どれが現行値かをモデルは人間以上に判別しにくい**——
「先週変えた覚えがある」という手がかりを持たず、書いてあることを丸ごと真に受けるしかない。
**古い、あるいは自己矛盾した文書がモデルに与える害は人間に与える害より小さくなく、むしろ大きい。**

同様に `kb/decisions.md` の価値も下がるのではなく上がっている：
後から来る者（人であれモデルであれ）に
**「この一条がなぜ今こうなっているのか、根拠は何か」を伝えられる唯一の場所**だからである。
