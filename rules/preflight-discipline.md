# 受付条件と実行条件：走らせてよいかを先に判定し、それから走らせる

**すべてのスクリプトは冒頭に、いつ呼ぶべきか・いつ呼んではならないかを書き、仕事を始める前にそれを判定する：条件を満たさなければ実行を拒否し、`--force` を付けたときだけそのまま走らせる。**

対象はすべてのスクリプト：本パッケージの `install.sh` と `scripts/`（`scripts/claude-hooks/`、`scripts/githooks/` を含む）、
プロジェクトの `.claude/gate.d/`、`.claude/scripts/`、`.claude/hooks/`、そしてプロジェクトが `.claude/preflight-dirs` に登録したディレクトリ——
実験スクリプトや実験バイナリのソースファイルがある場所を登録する。各ディレクトリはその階層だけを数え、サブディレクトリは別の行で登録する。
`.claude/preflight-dirs` は一行に一つ `<ディレクトリ>  # 何が置いてあるか`。実験のないプロジェクトもこのファイルを作り、そのことを一行のコメントで書く。

判定しないのは三種類：source または import されるライブラリ、サンプル、共有スクリプトを `exec` するだけのラッパー（install.sh が敷く数行。ほかのロジックが混じっていれば普通のスクリプトとして判定する）。
ライブラリとサンプルは一つずつ除外表に登録する：本パッケージのものは `scripts/preflight-lint.py` の `PACKAGE_EXCLUDED`、プロジェクトのものは `.claude/preflight-exclude`、
一行に一つ `<パス>  # 理由`、理由は 4 文字以上。まだ直していないスクリプトも一つずつそこに登録し、一つ直すたびに一行消す。除外表は縮むだけで、増やさない。

## 二種類の条件

| 条件 | 何に答えるか | 典型例 |
|---|---|---|
| 受付 `admission:` | いつ呼ぶべきか：今回呼ぶ意味があるか | コード・決定・事前登録が前回の成功以来変わっておらず、再実行しても新しいことは何も分からない |
| 実行 `run-condition:` | いつ呼んではならないか：環境が持ちこたえるか、結果を汚さないか | ツールがない、デバイスや権限がない、同じスクリプトの別インスタンスがすでに走っている |

どのスクリプトも二種類をそれぞれ少なくとも一行書く。何行か書いたなら、すべて満たしたときだけ満たしたことになる。実験の受付条件は `inputs-changed` とし、結果が依存する入力をすべて登録する：コード、決定、事前登録。

## 書き方

ファイル冒頭のコメントブロック（`#!` の後、最初のコード行の前。shell と python は `#`、Rust は `//` で、Rust の内部属性 `#![…]` は間に挟まってよい）に一行に一つ：

| 書き方 | 満たされる条件 |
|---|---|
| `admission: always <理由>` | 呼ぶたびに意味がある。理由には、なぜそう言えるかを書く。例えば、それが判定するのは今この時点のリポジトリ全体だから |
| `admission: inputs-changed <パス…> [env:<変数名>…] [arguments]` | スクリプト自身か登録した入力が、前回の成功以来変わった。パスはリポジトリのルートからの相対、`./` や `../` で始まるものはスクリプトのディレクトリからの相対。`env:<変数名>` と `arguments` は、環境変数と今回の引数を入力に数える。何行書いても一つの入力にまとめる |
| `admission: check <コマンド> :: <満たさないときどうするか>` | コマンドの終了コードが 0 |
| `run-condition: none <理由>` | 環境への要求がない |
| `run-condition: command <実行ファイル名…>` | すべて `PATH` 上にある |
| `run-condition: single-instance` | 同じスクリプトを走らせている別のプロセスがない |
| `run-condition: check <コマンド> :: <満たさないときどうするか>` | コマンドの終了コードが 0 |

`always`、`none` の理由と `check` の対処は 8 文字以上。
`check` のコマンドはリポジトリのルート（git リポジトリの外ならスクリプトのディレクトリ）で `bash -c` として走り、環境には `PREFLIGHT_SCRIPT` と `PREFLIGHT_SCRIPT_DIRECTORY` があり、呼び出し側の標準入力は読めない。
git リポジトリの外では入力が変わったかを判定できないので、そのまま走らせ、指紋も記録しない。
宣言の解析と判定は `scripts/preflight.py` の一か所にだけあり、書き方はその振る舞いが正とする。

## 冒頭でまず判定する

| 言語 | 書き方 |
|---|---|
| shell | `source lib.sh`（lib.sh を source しないフックは `preflight.sh` を source する）の後、最初に仕事をする行の前に、この一行をそのまま写す：`preflight "${BASH_SOURCE[0]}" "$@"; set -- ${PREFLIGHT_ARGUMENTS[@]+"${PREFLIGHT_ARGUMENTS[@]}"}`。その前に置けるのは `set <オプション>`、`shopt`、`source`、代入だけで引数を読まない行、`unset` だけ |
| python | 先に `sys.dont_write_bytecode = True` とし、それから本パッケージの `scripts/preflight.py` を import する。`if __name__ == '__main__':` の最初の文で `preflight(__file__)` を呼ぶ。このブロックがなければ、モジュールで最初に仕事をする文の前に置く。その前のトップレベルの文では、引数や標準入力を読んだり、サブプロセスを起こしたり、ファイルを開いたりしない |
| Rust とその他の言語 | `main` の最初の文で `preflight` という名前の関数を呼ぶ：それは `python3 <規範のコピー>/scripts/preflight.py check <ソースファイルの絶対パス> [--force] -- <引数…>` を（`sh -c` を経ずに）直接起こし、終了コードが 0 でなければそのコードで終了する。stdout のその行が `met` で始まれば最後の欄の指紋を覚えておき、`forced` で始まれば最後の欄の要約を `PREFLIGHT_FORCED` として扱う |

`inputs-changed` を書いたスクリプトは、成功して終了する前に `preflight_record_success` を呼ぶ（Rust は `preflight.py record <ソースファイル> --fingerprint <開始時の指紋> -- <引数…>` を実行する）。
記録するのは開始時に判定した指紋である。終わった時点で入力が変わっていた（走っている間に誰かが変えた）回、強制実行の回、失敗した回は記録しない。

## 条件を満たさないとき

- `--force` なし：満たさない条件とその対処を一つずつ出力し、終了コード 78 で終わり、それ以外は何もしない。`python3` がなければ条件を判定できず、これも満たさないものとして扱う。終了コード 78 はこの拒否にだけ使う。
- `--force` あり：そのまま走らせ、満たさない条件を一つずつ出力し、`PREFLIGHT_FORCED` にその要約を入れる。
  成果物を書くスクリプトは `PREFLIGHT_FORCED` を成果物に書き込む。その成果物を引用するときは強制実行だったことを明記する。
- 条件の書き方が壊れている（認識できない書き方、短すぎる理由）と判定できない：スクリプトは 1 で終わり、ゲートはそのステージを失敗と記録する。

## gate.sh の段取り

- 各ステージを起動する前にその条件を判定する。満たさなければそのステージを起動せず、まとめには「今回は未実行」（`本次未跑`）として、満たさない条件を並べる。
- `gate.sh --force` は、条件を満たさないステージに `--force` を渡す。そうして走ったステージはまとめで「強制実行済み」（`强制跑过`）と記録し、
  合格とは記録せず、未実装リストのどの項目を覆ったことにもならない。
- 起動するかどうかはゲートの判定だけで決める：起動した後に 78 で終わったステージは失敗と記録する。
- ステージが一つでも強制実行されたか、「入力が変わっていない」以外の理由で起動されなかったなら、今回は gate-ok を進めず、最後の一文も「すべて合格」とは言わない。
  ゲートの終了コードは、失敗したステージがあるかだけを表す。

## ゲートが受け持つ半分

ゲートステージ「受付条件と実行条件」（`准入与运行条件`、`scripts/preflight-lint.py`）が判定するのは：二種類の宣言がそろっているか、書き方を認識できるか、最初のコード行より前にあるか、
`inputs-changed` に登録したパスが存在するか、冒頭で `preflight` を先に呼んでいるか（shell ではその前に lib.sh か preflight.sh を source しているかも）、
`inputs-changed` を書いたものが `preflight_record_success` を呼んでいるか、除外表と登録表が実在するものを指しているか。
プロジェクトに `.claude/preflight-dirs` がなければ、まとめで実験スクリプトの類を「今回は未検査」とする。

判定できないこと：条件が正しく漏れがないか（`inputs-changed` に入力が一つ抜けている、`check` が本当に必要なことを判定していない）、
`always` と `none` の理由が成り立つか、成果物に強制実行の印があるか、`preflight` の行より後に書いた宣言（実行時にも認めない）。これらはレビューに任せる。
