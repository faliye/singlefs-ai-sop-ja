# すべての結論には三つの導出を要する：順推 / 逆推 / 照合

**いかなる結論も、口に出す前にこの三段を完了し、各段が何であったかを述べること。**
一段でも欠けていれば仮説として書き、結論として書かない。

| 段 | 何を問うか | これができなければ、やっていない |
|---|---|---|
| **順推** | 機構 / コード / データから結論へ導く | 「どのコマンド、どの数行、どのデータファイル」を言える |
| **逆推** | **この結論が偽なら、私は何を見ていたはずか。** そして実際に見に行く | **具体的で、今回実行可能な**観測を一つ挙げ、それが現れなかったと言える |
| **照合** | 独立した別経路で同じ判断を再現する | 二つの経路が同じコード・同じ採取・同じ道具を**共有していない** |

## 照合の経路そのものも、赤くなることを示さねばならない

被テスト対象に、第二の経路が**本来捕まえるべき既知の故障**を注入し、
実際に捕まえることを確認する。捕まえられないなら、その照合経路は飾りであり、
それまでの「二経路が一致した」という記録もろとも無効になる。
例：ブロック層カウンタでプログラム自身の I/O 計数を照合するなら、ダイレクト I/O を外すとブロック層の計数がゼロになり、プログラム側の計数は動かないことを見て初めて、両側の一致が証拠になる。

⚠️ **独立した計数が合計だけ一致しても、内訳の裏付けにはならない。**
ある計数で内訳を裏付ける前に、その計数器が分ける種類を区別できるかを問う。区別できなければ「矛盾しない」とだけ書き、内訳の出どころを明記し、もう一方の生の計数も突き合わせる。

## 多方独立論証に渡す背景資料は、渡す前に自分で確認する

複数の独立した情報源で一つの推論を照合するとき、各方に渡す「既知の事実」は、**外部の事実を一条ずつ、渡す前に提出者自身が確認しておく。**
「某実装はこうなっている」という類の文はすべて、書き込む前にその場で確認する。確認しきれないものは「未確認」と明記する。

## そのまま保存した証拠は、後から書き換えてはならない

モデルに渡したプロンプト、走らせて出てきた生の出力、そのときのログは、一巡の内では一文字も変えない。
プロンプトを直すなら再実行と一緒にしか直せない。説明を足したければ別のファイルを起こし、原本には触らない。

**凍結はこの一巡の内だけで、巡が終われば保管先はバージョン管理の履歴になる。** 一巡の証拠——プロンプト、各脚の報告、生の出力、保存した産物——は、その巡の内では一文字も変えない。
その巡をコミットしたら、次のコミットが**前回が残した分**を削り、今回の分はそのまま残す。削った分を調べたいときは、バージョン管理の履歴を読む。

⇒ **古い証拠は参考であって根拠ではない。** 以前の結論に疑いが出たら、古い証拠を掘り返すのではなく、もう一度検証する（`kb-discipline.md` 第 2 条「過去のデータはすべて参考にすぎない」）。
以前の結論を覆すには、プロジェクト自身の推論規律をもう一巡回す。古いファイルを突きつけはしない。

⇒ **本文に引いた産物行の検査は「今回の変更」を見る。リポジトリ全体は見ない。** その日に本文へ書いた数は、その日の産物と一字一句合っていなければならない。
以前に写し取った行は歴史的な参考として扱い、判定しない。

⇒ **ゲートもこの種のディレクトリを避けなければならない。** `scripts/doc-lint.sh` はこの一覧をプロジェクト根の `.claude/doc-lint-exclude` から読む。
一行に一件、**それぞれ理由を書くこと**。存在しないディレクトリを指す項目、
一件も除外できていない項目は赤とする。

## 結論に入る数は、まず測ったのか見積もったのかを問う

結論に入る速度・容量・比率は、まず「この数は測ったのか、見積もったのか」を問い、見積もりなら測りに行く。
ここで測れないもの（例えばエンタープライズ向けディスクの fsync 率）は条件付きで書く：「10⁵/秒なら 89 年。その帯は本機では測れないので、仮定のまま」——仮定を上限として書いてはならない。

## 他のプロジェクトのやり方は手掛かりであって、証拠ではない

**他プロジェクトの実装を直接の証拠にしてはならない。**
外部の実装が入ってよい場所は二つだけ——**仮説を立てる**、**どの経路を測るべきかを示す**。
三つの導出（順推 / 逆推 / 照合）のどれにも入れてはならず、照合の経路にもできない。
証拠にしたいなら、まず本プロジェクトで観測可能なデータとして再現し、そのデータを引く。その実装は引かない。

**引いてよい半分と、いけない半分を分ける**：

| よい | いけない |
|---|---|
| **事実**：「`XLOG_CONTINUE_TRANS` という定数が存在する」「ある関数が 22 ファイル 93 箇所に散っている」——確認可能、再実行可能 | **論証**：「XFS がこうしているから、こうするのが正しい」 |
| **反証**：ある方式が現役の実装に**一つも現れない**のは、説明を要求する信号 | **正証**：ある方式が現役の実装に現れることは、本プロジェクトに適することの根拠にならない |
| **機構**：他家のやり方を機構に分解し、その機構が本プロジェクトの前提の下で成立すると論証する | **移送**：書かれていない前提ごと結論を運んでくる |

⚠️ **「どの現役実装も X の道を通っていない」は X が誤りだと証明するものではないが、立証責任は X の側にある**：誰も通っていない道を行くなら、なぜ誰も通らなかったかを言えなければならない。

⚠️ **他家の実装を引くときは、それと本プロジェクトとの既知の相違を一つ必ず書き添える。** 相違を書けないなら、その引用は論証ではなく**移送**である。

**引用時は出所と「本プロジェクトでは未検証」を明記する**（`kb-discipline.md`「2. 一条ごとに出所と状態を添える」）。

## 仮説は観測によって否定されうるものでなければ、仮説ではない

仮説を書き留めたら、**まず「どんな現象がこれを覆すか」を問う。**
答えられなければ、その上に実験を組まない。

**仮説を排除するには、反証可能な観測を持つか、推論であると明言するかのいずれかが要る。**
「他の説明が思いつかない」は排除に当たらない。

## 先に結論を決めてからモデルを組んではならない

**判定基準（結論を書き留める前に自問する。答えられなければまだ終わっていない）**：

| 問い | 答えられなければ結論が先にあった |
|---|---|
| このモデルは私の傾きより**先に**存在したか | 「組んだ時点ではどちらに出るか知らなかった」と言える |
| **反対側**にも同じ真剣さの腕を組んだか | 相手の腕の最良の形が何か、それを測ったかを言える |
| 逆の結果を私は**受け入れる**か | 「逆の数が出たら結論をこう変える」と言える——この一文は走らせる**前に**書き留める |
| **一点だけ**で値を取っていないか | 一つの寸法、一つのパラメータ、一つの負荷から出た倍率は「最悪」とは呼ばない |
| 出した区間の反例が**同じ産物の中**に無いか | その区間が産物中の全標本点を覆っていると言えること |
| この数は**掃いていないどれかのパラメータ**の関数ではないか | この腕のコスト／利得が装置のどのつまみに依存するか、そのそれぞれを掃いたかを言える。どのパラメータの関数かを先に問うてから本文に書く |

⚠️ **旧い結論を覆すときは、確立するときよりも厳しく**、緩くではない。

⚠️ **藁人形の対照腕**：相手の道に誰も実際には採らない実装形態（「項目ごとに一件のレコード」といった類）をあてがい、それで測った酷さをその道の代価とすること。
**判定基準**：相手の腕の形態は、**その支持者が認めるものかどうか**。

⚠️ **ある腕の数値を引くときは、その腕の定義も一緒に持ってくること**
（`verify-before-claiming.md`「決まっているかと、実際に何と定義されているかは、別の問いである」の実験版）。

### 腕の定義も「走らせる前に固定する」対象——失敗条項が当たったとき何をするか

走らせる前に固定するのは判定基準・閾値・無効条項だけではない。**各腕が何であるか**も含む。
失敗条項が曖昧に書かれた腕に当たったとき、負けを一度記録しないまま腕を強い読み方へ「明確化」し、勝ちを宣言してはならない。

⇒ **許される手順は三つだけ。一つでも欠ければ新しい実験であり、走らせ直す**：

| 手順 | 中身 |
|---|---|
| **負けを一度記録する** | **最も弱い読み方**での失敗条項の判定をそのまま書く。この腕がその一点で誰に負けたのか |
| **厳しくする方向のみ** | 新しい形は**元の判定基準**で同等以上に厳しく判定されること。一文字も緩めない |
| **どこを厳しくしたか書く** | 新しい形が旧い形より**何を余分に要求する**のかを言えること。言えなければ緩和である |

⚠️ **腕の定義に「どうやるか」と「やるとどうなるか」を両方書いたら、前の文から後の文が導けることを先に示す。**
導けないなら「やるとどうなるか」を消すか、それが導けるやり方に変える。

**産物を走らせる前に腕や判定基準を改めるのは正当だが、記録を残すこと。** 単体テストは走らせたが産物は一度も走らせていない時点で、より強い腕や段の粒度の判定基準を足すなら、
走らせる前の登録に**何を変えたか、根拠はどの単体テストの読みか、時点は産物より前であること**を書き、元の判定基準はそのまま残し、二つの腕をそれぞれ判定する。

### 判定基準そのものも書き誤ることがある：当たったら、まずどの形かを判じる

| 形 | どう見えるか | どうするか |
|---|---|---|
| **当たりが腕を区別しない** | 一つのマスが全部の腕を一度に脱落させ、原因はすべての腕が共有する前提にある | それで腕を判定しない：その共有前提を別の負債として立てて先に直し、腕の判定は腕を区別できるマスだけで行う。「全部脱落 ⇒ ある腕に戻る」という条項を書くときは、全部の腕を一度に脱落させるマスをどう記録するかも併せて書く |
| **判別に使う量が観測できない** | 基準が判定対象のシステムに二つの状況の区別を求めるが、そのシステムが判断する時点で見えるものは、二つの状況で一項目ずつ同じである | 基準を直す——直したら新しい一巡である |
| **当たりを別の基準に分類している** | ある脚が「基準 X に当たった」と報告するが、起きたことは文言上、閾値の違う別の基準に属する | 当たりがどの基準のどの文節を満たしているかを一字ずつ確かめる |
| **直し方が当たったマスに届かない** | 走らせる前の逆向きの受け入れ条項が「当たり ⇒ 直し方 A と直し方 B のどちらかを選ぶ」と書き、そのうち一つの直し方が当たったマスでやはり当たる | 条項を書くとき、直し方ごとにどのマスを直すのかを書く。当たったら、まず当たったマスで直し方を一つずつ確かめ、まだ当たるものを渡すときは「このマスには効かない」と書く |

⇒ **基準が当たったら、まず四つを問う**：それは腕を区別するか。判定対象のシステムは、区別を求められているものをその時点で本当に見られるか。それは基準の文言のどの文節を満たしているか。走らせる前の条項が示す直し方の一つ一つは、当たったマスでまだ当たるか。四つとも通って初めて、走らせる前の条項どおりに判定する。

## 産物を引くときは行ごと写す

**産物はファイル名付きで行ごと写す**。要約は自分で計算した一格だけにする。

### 走らせ直したら本文に照らし返す。リプレイが緑でも本文が正しいことにはならない

産物を走らせ直したら、本文がそこから引いている数を一つずつ照らし返す。
**リプレイが全緑でも「本文の数が正しい」ことにはならない。**

⇒ 同じことが**コマンド一つで数えられる主張**にも当てはまる：「単体テスト N 件」
「ミューテーション M 件」「産物 K 行」。
**コマンド一つで数えられる数は、そのコマンドに数えさせる**こと。
書いた人が直しに戻るのを当てにしてはならない。

⚠️ **本文と産物の食い違いにはもう一つの形がある：数は正しく、限定詞が消えている。**
⇒ **判定基準**：結論が「A だけが買える／A に固有／A だけができる」と言っているときは、
産物に当たって**A 以外の腕を全てのパラメータ点で**読むこと。
本文のその表に**そのパラメータの列が無い**なら、射程が落ちており、その「だけ」は成立しない。

### 走査で得た極値が走査区間の端点に落ちたら、それは測った数ではない

走査で得た極値（「最小の成立値」「最大の安全値」）を報告する前に、それが走査区間の端点かどうかを見る。
端点なら「≤ 端点（走査の下端、境界は測っていない）」と書く。さもなければ区間を広げて走らせ直し、極値が区間の内側に落ちるまで続ける。

## 新しい判定基準を立てたら、洗い直す項目を記録し、次の段階同期でまとめて洗う

立て終えたらまず問う：**すでに登録済みの項目に対して、これは何と判定するのか。**
答えられないなら、まだ立て終えていない。

### 数や結論を撤回するときも、洗い直しリストに記録する

対象を撤回・書き換えられた数値や条項に替えても、同じく洗い直す。洗い直し自体はまとめて行う：新しく立てた判定基準や撤回した数は、それぞれ一行ずつプロジェクトの洗い直しリストに記録し、次の段階同期でまとめて洗う。一件ごとに個別に派遣しない。
**判定基準**：撤回したら「**このリポジトリでこの数をまだ使っているのは誰か**」と問い、
その一覧を出せて初めて撤回し終えたとする。範囲はリポジトリ全体であって、
「覚えている数箇所」ではない。

⚠️ **洗い出した一覧を一括で置き換えてはならない。一箇所ずつ、それが現状を述べているのか、その時に起きたことを述べているのかを先に見分ける。**
**判定：その文の古い値を新しい値に置き換えて、まだ真か。** 真なら現状を述べているので改める。偽ならその時のことを述べているので残す。

⚠️ **洗い出しは古い言い方で探す。新しい名前だけで探してはならない。**
洗い出す前に「このことが出来上がる前、リポジトリはそれをどう書いていたか」（X がない、X はまだ、Y しかない、N 件）を書き出し、その言い方でリポジトリ全体を探す。
この段階の diff で削除したり書き換えたりした現状の文も、一文ずつ、別の箇所にまだ残っていないか探す。

### 撤回の理由が崩れても、撤回された結論が自動的に戻るわけではない

撤回の理由が後から崩れても、撤回された結論は自動的には戻らない：戻すには**論証をやり直す**必要がある。

⇒ **撤回の理由が崩れているのを見つけたら、順に三つ問う**：

| 問い | 答えられないなら先へ進むな |
|---|---|
| 今この枠を支えている理由はどれか | それがどのファイルのどの段落にあるか言える |
| その理由自体は立つのか | 支点を一つずつ当たる。結論の一文だけ読んで済ませない |
| 撤回された方を復活させる論証は、実際にやったのか | やっていないものはやっていない。「理由が崩れた」で代替してはならない |
