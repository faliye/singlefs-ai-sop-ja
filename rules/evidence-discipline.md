# すべての結論には三つの導出を要する：順推 / 逆推 / 照合

**いかなる結論も、口に出す前にこの三段を完了し、各段が何であったかを述べること。**
一段でも欠けていれば、それは仮説である。仮説として書き、結論として書かない。

| 段 | 何を問うか | これができなければ、やっていない |
|---|---|---|
| **順推** | 機構 / コード / データから結論へ導く | 「どのコマンド、どの数行、どのデータファイル」を言える |
| **逆推** | **この結論が偽なら、私は何を見ていたはずか。** そして実際に見に行く | **具体的で、今回実行可能な**観測を一つ挙げ、それが現れなかったと言える |
| **照合** | 独立した別経路で同じ判断を再現する | 二つの経路が同じコード・同じ採取・同じ道具を**共有していない** |

逆推は最も飛ばされやすく、しかも最も価値がある段である：
順推が言えるのは「この説明で辻褄が合う」までであり、
「別の説明でも辻褄が合う」を排除できるのは逆推だけである。

## 照合の経路そのものも、赤くなることを示さねばならない

「独立した第二の経路で同じ判断を再現する」だけでは足りない——
**その第二の経路自体が飾りでありうる。**

二つの経路が一致したとき、それは「どちらも正しい」かもしれないし、
**第二の経路がそもそも見ていなかった**のかもしれない。
故障を注入しない限りこの二つは区別できず、**見た目は同一である——どちらも「一致」だ。**

**やり方**：被テスト対象に、第二の経路が**本来捕まえるべき既知の故障**を注入し、
実際に捕まえることを確認する。捕まえられないなら、その照合経路は飾りであり、
それまでの「二経路が一致した」という記録もろとも無効になる。

例：カーネルのブロック層カウンタでプログラム自身の I/O 計数を照合し、升目ごとに一致した。
その一致が証拠になるのは、**ダイレクト I/O を外すとブロック層の計数がゼロになり、
プログラム側の計数は微動だにしない**ことを併せて観測した後である——
そうでなければ、その一致は第二の経路が第一の経路を反響しているだけかもしれない。

**これは「あらゆる検証は失敗しうるものでなければならない」を照合経路に適用したものである**：
主たる検査が赤くなることを示すのと同じく、照合経路も赤くなることを示すこと。
**前者だけを示すのは、半分しかやっていない。**

## 仮説は観測によって否定されうるものでなければ、仮説ではない

仮説を書き留めたら、**まず「どんな現象がこれを覆すか」を問う。**
答えられなければ、それはまだ形になっていない。その上に実験を組まない。

**仮説を排除するには、反証可能な観測を持つか、推論であると明言するかのいずれかが要る。**
「他の説明が思いつかない」は排除に当たらない。

## ファイルシステム特有の逆推の穴

本プロジェクトで測る量の多くは**正しい / 正しくない**という二値である。
危険は測定精度ではなく、網羅にある：

- **「テストが全緑」は「実装が正しい」ではない。**
  クラッシュの窓は書き込み一回分の幅しかないこともあり、
  当たらなかったのは単にそのクラッシュ点を列挙しなかっただけかもしれない。
  「クラッシュ一貫性が成立する」と言うには、
  今回**そもそも当たりえたのか**を述べること——
  クラッシュ点をいくつ列挙したのか、それは全部だったのか。
- **「checker が何も報告しなかった」は「イメージが健全」ではない。**
  checker がその検査をまだ実装していないだけかもしれない。
  言う前に `kb/invariants.md` の該当項目の実装状態を見る。
