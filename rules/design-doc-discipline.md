# 設計文書の鉄則

**適用対象**：README、設計説明、`records/`——**人が通読するもの。**

この種の文書は経緯を語り、道理を説き尽くし、読みやすく書く。機械に道を譲らない。
モデルが検索する知識文書は `kb-discipline.md` に従って書く。

## 1. 本文は現状のみを書き、履歴はすべて末尾へ

本文に「元は X、今は Y に変えた」「以前は A と呼んでいた」といった履歴の記述を置かない。
残すべき履歴は末尾の「改訂履歴」節にまとめる：

```markdown
## 改訂履歴

### YYYY-MM-DD
- かつて X / 現在 Y / 変更の根拠：Z
```

**帰結**：
- 決定を変えたら**本文を直接書き換える。** 横に「（元は X）」と註記しない。
- 結論が覆ったら**本文から古い結論を削り**、「かつて X / 現在 Y / 覆した根拠」を末尾に書く。
- 本文に `~~取り消し線~~`、`〔廃止〕`、`（XX に置換済み）` といったその場註記を置かない。
- コードのコメントも同様：「今なぜこうなのか」を書き、「以前どうだったか」は書かない。
  **検査コードの落とし穴コメントは例外**（「この抜け道は実測で通ってしまった、だからこの検査がある」）。
  判定基準は指す先：
  **今このコードがこうである理由**を指す → 残す。
  **もう存在しない旧版**を指す → 消す。

`CLAUDE.md` と `rules/*.md` は別の鉄則に従う。`rules-discipline.md` を参照。

本文中の履歴記述と履歴節の位置は `scripts/doc-lint.sh` が強制するが、見るのは `.md` だけである。コードコメントの条はレビューに頼る。

## 2. 長さは変更の重さに見合わせる

判定基準も物差しも `writing-discipline.md` の「長さは変更の重さに見合わせる」の節にある。ここには写さない。

## 3. 説得すべきところは、きちんと説得する

設計文書が答えるべきは「なぜこうすべきか」と「どう着手するか」である。
この二つのために書く前置き・例・開いて示すトレードオフは、**いずれも冗長ではない。**

判定基準：この段落を削った後、読む人はまだ同意するか。まだ着手できるか。
できる → 削ってよい。できない → 残す。
