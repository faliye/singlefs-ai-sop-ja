# 設計文書の鉄則

**適用対象**：README、設計説明、`records/`——**人が通読するもの。**

叙述・論証・文脈はこの文書の職責であり、機械に道を譲る必要はない。
読みやすく書くことはここでは目標であって、妥協ではない。
知識文書には別の一式がある。`kb-discipline.md` を参照。

## 1. 本文は現状のみを書き、履歴はすべて末尾へ

本文に「元は X、今は Y に変えた」「以前は A と呼んでいた」といった履歴の記述を置かない。
残すべき履歴は末尾の「改訂履歴」節にまとめる：

```markdown
## 改訂履歴

### YYYY-MM-DD
- かつて X / 現在 Y / 変更の根拠：Z
```

**なぜか**：本文に履歴が混ざると、読む側はどれが現行値か一目で判別できない。
数回重なると「今はどうなっているのか」という最も基本的な問いすら
考古学的な作業を要するようになり、しかもその結論はしばしば誤っている。
本プロジェクトは数年続く。この費用は指数的に増える。

**帰結**：
- 決定を変えたら**本文を直接書き換える。** 横に「（元は X）」と註記しない。
- 結論が覆ったら**本文から古い結論を削り**、「かつて X / 現在 Y / 覆した根拠」を末尾に書く。
- 本文に `~~取り消し線~~`、`〔廃止〕`、`（XX に置換済み）` といったその場註記を置かない。
- コードのコメントも同様：「今なぜこうなのか」を書き、「以前どうだったか」は書かない。

`CLAUDE.md` と `rules/*.md` は**末尾の改訂履歴すら置かない。**
履歴は `CHANGELOG.md` へ外出しする——
これらは作業のたびに通読する規則であり、履歴が混ざると薄まるからである。

`scripts/doc-lint.sh` が強制する。

## 2. 長さは変更の重さに見合わせる

論証がどれほど堅牢でも、それを全部書き出す理由にはならない。
自分で「ここが効いている」と感じた段落こそ、たいてい削るべき段落である。
細則は `writing-economy.md` にある。

## 3. 説得すべきところは、きちんと説得する

設計文書が答えるべきは「なぜこうすべきか」と「どう着手するか」である。
この二つには前置きが要り、例が要り、トレードオフを開いて示す必要がある——
**これらはいずれも冗長ではない。**

判定基準：この段落を削った後、読む人はまだ同意するか。まだ着手できるか。
できる → 削ってよい。できない → その段落は効いている。
