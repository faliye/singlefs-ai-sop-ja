# コーディング規律：machine-first の実施細則

コードを書くときはこれに従う。旧来の規則を吟味する手順は `machine-first.md` にある。総則は `engineering-philosophy.md` の「AI に優しい ≠ 読めない」である：
緩めるのは人間の頭に収めるための圧縮だけで、意味を明示することは一切緩めない。

**過去のベストプラクティスに代わりに決めさせない。** 流行りのやり方を一条ずつ吟味した結果は「一条ずつ吟味した流行りのやり方」にある。
ここに挙がっていない指針は、使う前に `machine-first.md` の手順を一度通す。既定は懐疑であって、遵守ではない。

対象は本プロジェクトで自分たちが書くコードすべて：製品コード、テスト、実験コード、スクリプト。
ゲートがどこまで検査するかは「ゲートが見るのはどちら半分か」を見よ。

## 名前：名前だけで、それが何で何をするかが言える

**判定基準：コメントも呼び出し箇所も実装も見ずに、その名前だけで、それが何で、何をし、何をしないかが言えるか。**
言えないなら名前を変える。そういう名前が付けられないときは、まずそのコードが何をするのかを定める。

対象は**自分たちが宣言するすべての名前**：変数、引数、関数、メソッド、型、フィールド、列挙子、定数、
モジュール、ファイル、ジェネリック引数、ライフタイム、クロージャ引数、ループ変数、テスト関数、マクロ。
外部が決めた名前はこちらの管轄ではない：`Display` を実装するならメソッド名は `fmt` である。

| 規則 | 細則 |
|---|---|
| **長さに上限を設けない** | 「名前は短く」という規則はない |
| **略語を使わない** | `cnt`、`idx`、`buf`、`tmp` はすべて書き切る。例外は登録済みのドメイン略語だけ（「略語登録表」を見よ） |
| **一文字の名前を使わない** | ループ変数、クロージャ引数、ジェネリック引数、ライフタイム、エラーの束縛もすべて対象：`i` → `stripe_index`、`T` → `Key`、`'a` → `'journal`、`Err(e)` → `Err(error)` |
| **事前条件と作用範囲を名前に書く** | `write_node` は何も言っていない。`append_verified_node_to_journal` は三つのことを言う：上書きではなく追記、引数は検証済み、書き先はジャーナル領域 |
| **単位を明記する** | 型で表せるなら型に任せる（`LogicalAddress`、`Duration`）。表せないなら名前に書く：`offset` ではなく `offset_in_blocks` |
| **真偽値は述語として書く** | どちら側が真かを言う：`flag`、`status`、`ok` ではなく `is_checksum_verified` |
| **テスト名にはシナリオと期待結果を書く** | `test_commit` や `it_works` ではなく `crash_between_data_write_and_commit_keeps_previous_generation` |
| **一つの意味概念にはリポジトリ全体で一つの名前** | 単位は意味概念であって語ではない：同じ概念をここでは `generation`、あちらでは `epoch` と呼んではならない。二つの概念は、下層の意味が近くても（ディスクに記録された世代番号と、トランザクションのライフサイクル上の世代番号）名前を共有してはならず、それぞれ役割を付ける：`committed_generation`、`transaction_generation` |
| **名前は単独で成り立たせ、モジュールパスで補わない** | `block::Address` ではなく `block::BlockAddress` と書く。その結果、型名が手作りの名前空間になる（`BlockAddress`、`JournalAddress`、`LogicalAddress`……）が、そのとおりに書く |
| **意味が変わったら名前を変える** | 同名のシャドーイングは意味が変わらないときだけ使う。生データが検証済みデータになった、バイト数がブロック数になった、というときは新しい名前を付ける |

### 略語は使わない。判定基準は権威ある定義が一箇所にあるか

**判定基準は「権威ある定義が一箇所にあるか」であって、「みんなが分かるか」ではない。**
Rust のキーワードと基本型の名前（`mut`、`fn`、`str`、`u64`）は略語に数えない。言語仕様がそれらの唯一の定義である。
プロジェクト固有のドメイン略語（`lba`、`crc`）は登録して初めて使える。

### 略語登録表

プロジェクト直下の `.claude/abbreviations`。一行一項目で、`#` の後に正式名と意味を書く：

```text
lba  # logical block address：論理ブロックアドレス。ファイルシステムがブロックに振る番号
crc  # cyclic redundancy check：巡回冗長検査
```

登録表がその略語の唯一の権威ある定義であり、他の箇所はそれに従い、二つ目の定義を書かない。
**一文字は登録できない。**

**プロジェクト自身の番号**（kb に登録された実験番号や決定番号の類）を名前の一区切りとして使うときは、「文字と数字」という一つの類として登録する：

```text
e<数字>  # 実験番号。.claude/kb/experiments.md に登録
```

（`<数字>` は lint が書かれたとおりに読む書式である。）
登録すれば `e57_field_authority` の `e57` は一文字に数えない。名前の中の番号も簡称を伴わせる
（`kb-discipline.md` 第 5 条）：裸の `e57` ではなく `e57_field_authority` と書く。

### 意味の置き場所：コメント < 名前 < 型

同じことの三つの書き方、悪い順から：

```rust
// 一、意味をコメントに置く —— 最も悪い
// dim0: 民族  dim1: 性別  dim2: 年齢層
pop[i][j][k]

// 二、意味を名前に置く
number_of_china_people[han][woman][teenager_18_to_24]

// 三、意味を型に置く —— 最善。次元を取り違えるとそもそもコンパイルが通らない
number_of_china_people[Ethnicity::Han][Gender::Woman][AgeBand::Teenager18To24]
```

**型で表せる制約は型に、型で表せないものは名前に置き、いずれもコメントには書かない。**

## 分岐：網羅して書き切り、ワイルドカードアームを書かない

```rust
enum Medium {
    Rotational,
    SolidState,
    Zoned { zone_size_in_bytes: u32 },
}

fn node_size_in_bytes(medium: &Medium) -> u32 {
    match medium {                                  // `_ =>` のアームを書かない：Medium を一つ足したら、ここを埋めるまでコンパイルが通らない
        Medium::Rotational                   => 64 * 1024,
        Medium::SolidState                   => 16 * 1024,
        Medium::Zoned { zone_size_in_bytes } => (*zone_size_in_bytes).min(256 * 1024),
    }
}
```

**判定基準は「分岐が多いか」ではなく「ある場合を取りこぼしたとき、先に気づくのは誰か」である**：本番ではなく、コンパイラが先に気づくようにする。

- **閉じた集合の列挙型では、`match` に `_ =>` を書かない。** 自前の列挙型は既定で閉じた集合である：場合がいくつあるかはこちらが決める。
- **意味上、未知の値を許すもの**（ディスクから読んだもの、プロトコルで受け取ったもの、将来も新しい値が増える符号）は、「未知」を明示的な列挙子
  （`Unrecognized(raw_code)`）にし、`match` はそのまま網羅する。ワイルドカードアームもやはり書かない。
- **本当に開いているのは二種類だけ**：外部の列挙型（他のクレートのもの、`#[non_exhaustive]` 付きのもの）と、対外的に約束し、
  将来の進化の余地を残す公開 API（「適用しないとき」を見よ）。ワイルドカードアームが本当に必要なら、
  その箇所に `#[allow(clippy::wildcard_enum_match_arm, reason = "…")]` を書く。
- **ワークスペース内部で使う列挙型には `#[non_exhaustive]` を付けない。**
- **閉じた集合（場合がいくつあるかはこちらが決める）は `enum` と網羅的な `match` で書き、トレイトオブジェクトにしない。**
  二つの場合の相互作用（状態遷移、二つずつの比較）はタプルに対する網羅的な `match` として書ける。開いた集合（プラグイン、テストダブル）は従来どおりトレイトを使う。
- **実装が一つしかないトレイトは抽出しない。** 本物の実装が少なくとも二つ（モデル対照テストに使うモデルも一つに数える）あって初めてトレイトを抽出する。
  「後で差し替えやすいように」では抽出しない。
- **網羅的な `match` のアームの数は複雑さに数えない。** 上限を設けるべきは互いに独立な条件の数である。

## 型：不正な状態を書けなくする

```rust
#[derive(Clone, Copy, PartialEq, Eq)] pub struct LogicalAddress(pub u64);
#[derive(Clone, Copy, PartialEq, Eq)] pub struct PhysicalAddress(pub u64);
fn read_block(address: PhysicalAddress) -> Block;   // read_block(LogicalAddress(value)) はコンパイルできない

struct RawNode(Vec<u8>);        // ディスクから読んだ直後、未検証
struct VerifiedNode(Vec<u8>);   // チェックサム照合済み
impl RawNode {
    fn verify(self, expected_checksum: Checksum) -> Result<VerifiedNode, CorruptBlock> { /* ... */ }
}
fn walk(node: &VerifiedNode) { /* ... */ }   // 検証を飛ばすと、そもそも引数が作れない
```

- 一つの下層型が異なる意味を担うなら（論理アドレス、物理アドレス、世代番号。バイト数、ブロック数）、意味ごとに newtype を一つ与える。
- 「検証したか」「永続化したか」のような状態は型にし、真偽値のフィールドにしない。**境界で一度だけ検証し**、証明を携えた型に変えたら、
  そこから内側は型を信じ、層ごとに検査し直さない。
- **真偽値の引数は列挙型に置き換える**：`write(node, true)` は `write(node, Durability::Synced)` と書く。
- **不変条件を持つフィールドは private にし**、検査する構築関数からしか入れないようにする。
  不変条件のないフィールドはそのまま公開し、定型の getter / setter を書かない。
- **不変条件を持つ型は `Default` を実装しない。**
- **自前の構造体を構築するときは、すべてのフィールドを書き出し**、`..Default::default()` を使わない。
  必須のフィールドを builder に任せて実行時に検査させず、構築関数の引数にする。本当に省略可能なものだけを builder に入れる。
- **値を失いうる数値変換に `as` を使わない**：値を失いうる方向では `try_from` を使って失敗を処理し、失わない方向では `from` を使う。

## エラー：回復できるものは型に書き、不変条件の破れはアサートする

- **回復できる失敗**（I/O エラー、ディスク上のデータの破損、資源不足）**は `Result` で返す。** エラー列挙型の列挙子は**呼び出し側が下す判断ごとに分け**、
  下層の原因ごとには展開しない：例えば上位が振り分けるのが「見つからない」「データ破損」「空き容量不足」「その他の I/O エラー」の数種類だけなら、
  下層の数十種類の OS エラーは「その他の I/O エラー」の列挙子に source として持たせる。
- **判定基準は、呼び出し側が本来下せるはずの判断を失うかどうかである。** ライブラリの公開境界では `anyhow` や `Box<dyn Error>` のような統一エラー型を使わない。
  下層の失敗の一つ一つを各層でそれぞれ列挙子に展開し直すこともしない。テストとコマンドラインツールは統一エラー型を使ってよい。
- **不変条件の破れはバグであり、アサートする**。壊れた状態のまま先へ進まず、ましてディスクには書かない。
- **`unwrap()` は書かず、`expect` を書く**。メッセージにはどの不変条件に依拠しているかを書く：
  `expect("journal ヘッダは open() で検証済み。ここで None なら検証が飛ばされている")`。

## 関数とネスト：「独立に検証できる」単位で切り、経路数で縛る

**関数の長さは「独立に検証できる一つのこと」で決め、画面の高さでは決めない。** 一つのことなら三百行でもよい。
二つのことが二十行に詰め込まれていれば分ける。

**ネストの層数には上限を設けず、縛るのは経路数である。** 早期脱出のないループのネストは経路をほとんど増やさず（`break`、`continue`、`?` はそれぞれ一本ずつ足す）、
条件のネストは指数的に増やす（独立した 12 層の `if/else` は 2¹² 本）。
層数は自由で、二つを満たせばよい：経路数が言えて、かつ有界であること。
各層の反復対象に名前と型があり、`a[i][j][k][l]` ではないこと。

**経路数が測るのは制御フローだけであり、検証の難しさのすべてではない。** 経路数が上限を超えたら分ける。超えていないからといって検証しやすいとは限らない。ループはさらに三つのことを明記する：
反復回数の上限、回をまたいで持ち越す状態とその不変条件（アサーションとして書く）、すべての早期脱出。
**「経路は一本しかない」は、検証の難しいアルゴリズムの弁護には使えない。**

- **引数の個数には上限を設けない。** 各引数に名前と型があればよい。いくつかの引数がそれ自体で不変条件を持つ一つの概念をなすときに限り、
  一つの型にまとめる。シグネチャを短くするためだけに構造体を寄せ集めない。
- **結果は戻り値の型に入れ**、`&mut` の出力引数では返さない。
- **副作用は端へ押しやり、中核は純粋関数として書く。** I/O を伴う外殻は薄いほどよい。問い合わせと変更の両方を行う関数は、名前で両方を言う。
- **早期リターンは自由に使ってよい。**

## コメント、アサーション、定数、重複

- **コメントは「なぜこうなのか」だけを書き**、「これが何をしているか」は書かない。
  制約は型・名前・アサーションに書き、コメントには書かない。
- **ドキュメントコメントには型で表せない契約を書く**：どのエラーを返すか、いつ panic するか、`unsafe` が呼び出し側に何を求めるか。
  名前を言い直しているだけのドキュメントコメントは消す。
- **すべての `unsafe` ブロックの上に `// SAFETY:` を書き**、なぜ安全かを述べる。
- **不変条件はアサーションとして書き**、文書に書くだけで済ませない。
- **マジックナンバーは名前付き定数にする**：一つの数の定義は一箇所だけとし、名前か型に単位を持たせる。
- **重複は生成し、手で写さない。** マクロと `build.rs` は生成の正道であり、生成だけを行い、ロジックを隠さない。
  生成物にはテストを張り付ける。
- **使わないコードは消し**、コメントアウトしたコードも消す。
  コンパイラの `never used` はエラーとして扱う（`command-safety.md`：警告はただで手に入る信号である）。
- **`TODO` には何が欠けていて、なぜ今やらないのかを書く。** 借りている検査はプロジェクトの kb の借り検査表に記し、コードからそこを指す。

## 一条ずつ吟味した流行りのやり方

どれも `machine-first.md` の手順で吟味した。**処置**は六種類しかない：廃止、緩める、書き換え、残す、ツールに任せる、助言に格下げ。

### 全体の姿勢

| 流行りのやり方 | 出典 | 処置 | こちらの書き方 |
|---|---|---|---|
| コードは書かれるより読まれる回数が多い。読む人のために最適化せよ | 『Clean Code』ほか | **書き換え** | 機械検証と情報量のために最適化する。人の注意はテストが正しいか、不変条件が正しいか、根拠が成立するか、トレードオフを受け入れるかに使う（`engineering-philosophy.md`） |
| 賢いコードを書くな | 通説 | **残す** | そのとおりにする |
| KISS、単純に保て | 通説 | **書き換え** | 単純とは制御フローの経路が少なく、検証すべき状態が少なく、どの経路も書き出されていることであって、行数が少ないことではない |
| YAGNI、使わないものは書くな | エクストリーム・プログラミング | **残す** | 使わないコードは書かない |
| 驚き最小の原則 | 通説 | **残す** | 名前と型に十分な情報を持たせ、モデルに挙動を正しく推測させる |
| 設定より規約 | Rails ほかのフレームワーク | **廃止** | 暗黙の既定の挙動に頼らない：必要な値はすべて書き出す |
| 関心の分離、高凝集・低結合 | 通説 | **残す** | 境界を明確にし契約を明示して、各部分を単独で検証できるようにする |
| ファイルやモジュールを長くするな | 通説 | **緩める** | モジュールは契約で切り、行数では切らない |

### 命名

| 流行りのやり方 | 出典 | 処置 | こちらの書き方 |
|---|---|---|---|
| 名前は短く、宣言に近いほど短く | Go Code Review Comments、Linux カーネルのコーディングスタイル | **廃止** | 長さに上限なし（「名前」を見よ） |
| ループカウンタは `i`、一時変数は `tmp` | Linux カーネルのコーディングスタイル | **廃止** | それが何かで名付ける：`stripe_index`、`unflushed_block` |
| ジェネリック引数は `T`、`U`、ライフタイムは `'a` | Rust の慣習 | **廃止** | 役割で名付ける：`Key`、`Value`、`'journal` |
| 誰でも知っている略語なら使ってよい | 通説 | **廃止** | 書き切る。ドメイン略語は登録して初めて使える |
| 名前は発音できるように | 『Clean Code』 | **残す** | 要るのは曖昧でないことと検索できること |
| 名前は検索できるように | 『Clean Code』 | **残す**、しかもより強く | 一つの意味概念に一つの名前にし、リポジトリ全体を一度検索すれば全部見つかるようにする |
| ハンガリアン記法、`m_` 接頭辞、インタフェース名の `I` | C / C++ / C# の旧い慣習 | **廃止**。それがやりたかったことは型に任せる | 意味が違えば別の newtype。型で表せない単位は名前に書く |
| `Manager`、`Helper`、`Data`、`Info` のような雑音語を使うな | 『Clean Code』ほか | **残す** | それを消しても名前から何も減らないなら、使わない |
| モジュール名を型名で繰り返すな（`block::Address`） | clippy の `module_name_repetitions`、Go のパッケージ命名の慣習 | **廃止** | 名前は単独で成り立たせる：`BlockAddress` と書く |
| getter に `get_` を付けない | Rust API ガイドライン C-GETTER | **残す** | C-GETTER のとおりに書く |
| 変換メソッドは `as_`、`to_`、`into_` で名付ける | Rust API ガイドライン C-CONV | **残す** | `as_` は借用から借用で、規約上ほぼ無コスト。`to_` は規約上コストがあり、たいてい新しい値を生むが、`to_str` のように借用から借用のものもある。`into_` は所有権を消費する。C-CONV の表を基準とし、実装は名前が約束した種類のコストを守る |
| 真偽値の名前は `is_`、`has_` で始める | 通説 | **残す** | どちら側が真かを言う |
| 型は名詞、メソッドは動詞 | 『Clean Code』 | **残す** | 名詞はそれが何かを、動詞はそれが何をするかを言う |
| Rust の大文字小文字の規約（`snake_case`、`CamelCase`） | Rust の慣習、rustc の既定の警告 | **残す** | 規約のとおりに書く |
| 同名のシャドーイング（`let text = text.trim()`）は慣用句 | Rust の慣習 | **書き換え** | 意味が変わらないならシャドーイングしてよい。意味が変わったら名前を変える。無関係な意味でのシャドーイングは clippy が止める |
| テスト関数は `test_<被テスト関数>` と呼ぶ | 通行の慣習 | **廃止** | シナリオと期待結果を書く |

| 関数は短く：一、二画面、できれば 20 行未満 | 『Clean Code』、Linux カーネルのコーディングスタイル | **残す** | 「独立に検証できる一つのこと」で切り、行数では切らない |
| 一つのことだけをする | 『Clean Code』 | **残す** | 一つの関数に、独立に検証できる契約を一つ |

| 上から下へ読む（段落ちルール） | 『Clean Code』 | **廃止** | 関数を呼び出し順に上から下へ並べることは求めない |
| 引数は三つまで | 『Clean Code』 | **緩める** | 各引数に名前と型があればよい。概念をなすときだけ一つの型にまとめる |

| 出力引数を使わない | 『Clean Code』 | **残す** | 結果は戻り値の型に入れる |

| 問い合わせと変更を分ける | Bertrand Meyer（CQS） | **残す** | 問い合わせと変更の両方を行う関数は、名前で両方を言う |

| 循環的複雑度をある値以下に | McCabe、各種静的解析ツール | **書き換え** | 網羅的な `match` のアームは数えない。縛るのは互いに独立な条件の数 |

### 型、データ、カプセル化

| 流行りのやり方 | 出典 | 処置 | こちらの書き方 |
|---|---|---|---|
| 基本型の代わりに値オブジェクトを使う | 『リファクタリング』（基本データ型への執着） | **残す**、しかもより強く | 意味が違えば別の型 |
| 不正な状態を表現できなくする | Yaron Minsky | **残す** | 「型」を見よ |
| 検証するのではなく、パースせよ | Alexis King | **残す** | 境界で一度だけ検証し、証明を携えた型に変え、内側では型を信じる |
| フィールドは private にし、getter / setter を付ける | Java 系のカプセル化の慣習 | **書き換え** | 不変条件のあるものは private、ないものはそのまま公開 |
| 既定で不変 | Rust の慣習、関数型プログラミング | **残す** | そのとおりにする |
| グローバルな可変状態を使わない。シングルトンを使わない | 通説、『デザインパターン』の反面教師 | **残す** | 使わない |
| derive できるなら `Default` を derive する | Rust の慣習 | **書き換え** | 不変条件を持つ型は `Default` を実装しない |
| 構造体更新構文 `..Default::default()` | Rust の慣習 | **自前の構造体では廃止** | すべてのフィールドを書き出す |
| フィールドが多ければ builder | Rust API ガイドライン C-BUILDER | **書き換え** | 必須のものは構築関数の引数にする。本当に省略可能なものだけを builder に入れる |
| 数値変換に `as` を使う | C 系の慣習 | **値を失いうる方向では廃止** | `try_from` を使って失敗を処理する。clippy が止める |
| 構造体を typedef で別名にするな | Linux カーネルのコーディングスタイル | **廃止** | newtype はそのまま使う：包むのは意味であって、構造を隠すのではない |
| マジックナンバーに名前を付ける | 通説 | **残す** | 一つの数の定義は一箇所だけとし、名前か型に単位を持たせる |

### 分岐と抽象化

| 流行りのやり方 | 出典 | 処置 | こちらの書き方 |
|---|---|---|---|
| 条件分岐をポリモーフィズムで置き換える | 『リファクタリング』 | **閉じた集合では廃止** | `enum` と網羅的な `match`（「分岐」を見よ） |
| 開放閉鎖原則 | SOLID | **閉じた集合では廃止** | 場合を一つ足したら、コンパイラに旧いコードのすべての箇所を見直させる |
| 単一責任 | SOLID | **残す** | 一部分には独立に検証できる契約が一つだけ |
| リスコフの置換 | SOLID | **残す** | トレイトの契約はすべての実装で成り立つ：契約テストをすべての実装に対して走らせる（`test-discipline.md` の「陽性対照は被検の**全ての**アームに対して走らせなければならない」と同じ） |
| インタフェース分離 | SOLID | **残す** | トレイトは小さく切る |
| 依存性逆転：具体ではなく抽象に依存せよ | SOLID | **書き換え** | 本物の実装が少なくとも二つあって初めてトレイトを抽出する。モデル対照テストに使うモデルも一つに数える |
| デメテルの法則：直接の友人とだけ話せ | ノースイースタン大学の Demeter プロジェクト | **緩める** | モジュール内部では自由に連鎖してよい。モジュールをまたいで他人の内部を貫くのは禁止 |
| デザインパターン：ファクトリ、ストラテジー、ビジター | 『デザインパターン』 | **書き換え** | 閉じた集合上のストラテジーやビジターは `match` で書く。パターンのために一層を足さない |
| DRY、重複を避ける | 『達人プログラマー』 | **緩める** | 重複は生成するのであって手で写さない |
| 重複が三回現れてから抽象化する | 『リファクタリング』（Don Roberts） | **残す** | 重複はまず生成器に任せ、網羅性検査を食いつぶす汎用パスには抽出しない |
| `default:` / `_ =>` で受けておくほうが堅牢 | 防御的プログラミング | **閉じた集合では廃止** | 取りこぼした場合はコンパイラに捕まえさせる。未知の値を許すなら「未知」を明示的な列挙子にする |

### エラー処理

| 流行りのやり方 | 出典 | 処置 | こちらの書き方 |
|---|---|---|---|
| 早く失敗せよ | 『達人プログラマー』 | **残す** | 不変条件が破れたらアサートし、壊れた状態をディスクに書かない |
| ライブラリのコードは panic せず、常に `Result` を返す | Rust の慣習 | **書き換え** | 回復できるものは `Result`。不変条件の破れはバグであり、アサートする |

| 絶対に失敗しないと分かっていれば `unwrap()` | Rust の慣習 | **廃止** | `expect` を使い、メッセージにどの不変条件に依拠しているかを書く |

## 適用しないとき

**これらの細則は「消せるもの」には無条件で使い、「消せないもの」には別勘定が要る。**
対外的な約束——ディスク形式、プロトコル、公開 API——に書き込まれたものは、判定基準を別に立てる。「明示のほうが安全だ」の一言で押し通してはならない。

## ゲートが見るのはどちら半分か

| 細則 | 誰が検査するか |
|---|---|
| 一文字の名前、よくある略語 | `scripts/naming-lint.sh`（ゲート段階「命名規律」）：プロジェクト内のすべての `.rs` を走査し、自分たちが宣言した名前だけを見る |
| 閉じた集合の列挙型に `_ =>` を書かない | clippy の `wildcard_enum_match_arm`。開いていると宣言したものは、その箇所で allow し reason を書く |
| `#[allow]` には `reason = "…"` を書く | clippy の `allow_attributes_without_reason` |
| 値を失いうる `as` 変換 | clippy の `cast_possible_truncation`、`cast_sign_loss`、`cast_possible_wrap` |
| `unsafe` ブロックには `// SAFETY:` | clippy の `undocumented_unsafe_blocks` |
| 無関係な意味での同名のシャドーイング | clippy の `shadow_unrelated` |
| 警告はエラーとして扱う | clippy の `-D warnings` |
| 名前が十分に言っているか、一つの概念が一つの名前か、関数が一つのことだけをしているか、コメントが「なぜ」を書いているか、エラーの列挙子が呼び出し側の判断で分かれているか、ループの状態が書き出されているか、`..Default::default()` | レビュー |
| シェルスクリプトの名前 | **まだ検査になっていない**。`gate.sh` が未実装の段階に挙げている。⚠️ この規律はシェルにも同じく効くが、`scripts/` の既存のスクリプトは洗い直していないので、手本にしてはならない |

clippy の分は `scripts/check.sh` の中で走る。つまりゲートの「ビルドと単体テスト」段階であり、プロジェクト直下に `Cargo.toml` がなければこの段階は走らない。

`naming-lint.sh` の略語リストは最もよくあるものだけを挙げている。**リストにない略語も違反であることに変わりはなく**、ゲートに見えないだけである。
見分けられない形（行をまたぐパターン、マクロ展開から出てくる名前）は判定せずレビューに回す。見分けられないことは通過したことではない。
トレイト実装のメソッド名と関連型、および `extern` ブロックの宣言は外部が名付けたものであり、検査しない。

プロジェクト側の設定ファイルは二つ。一行一項目で、`#` の後に理由を書き、理由は省けない：

| ファイル | 何を管理するか |
|---|---|
| `.claude/abbreviations` | 登録済みのドメイン略語。書式は「略語登録表」を見よ |
| `.claude/naming-lint-exclude` | 走査しないディレクトリ、または単独の `.rs` ファイル。なぜ除外するかを書く。存在しないパスを指す項目、`.rs` を一つも除外しない項目は赤になる。旧いコードを洗い直すときは、まだ直していないファイルを一つずつ並べ、直すたびに一行消す：除外は縮むだけで広がらず、新しいファイルは検査される |

外部が決めたその他の名前（外部書式のフィールド名の類）は、その行に `// naming-lint:external <なぜこの名前はこちらが決めるものではないか>` を書く。
免除されるのはその一行だけで、理由はやはり省けない。
