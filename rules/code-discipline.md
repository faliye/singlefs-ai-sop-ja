# コーディング規律：machine-first の実施細則

`machine-first.md` は旧来の規則をなぜ吟味し直すのか、どう吟味するのかを述べる。本編はその吟味の結果であり、
コードを書くときはこれに従う。
総則は `engineering-philosophy.md` の「AI に優しい ≠ 読めない」である：緩めるのは人間の頭に収めるための圧縮だけで、
意味を明示することは一切緩めない。

**原則は一つだけ：過去のベストプラクティスに代わりに決めさせない。**
流行りのやり方は出典ごとにまとめて吟味した。結果は「一条ずつ吟味した流行りのやり方」の節にあり、それより前の節は吟味を経た後の書き方である。
ここに挙がっていない指針は、使う前に `machine-first.md` の手順を一度通す。既定は懐疑であって、遵守ではない。

対象は本プロジェクトで自分たちが書くコードすべて：製品コード、テスト、実験コード、スクリプト。
ゲートがどこまで検査するかは末尾の「ゲートが見るのはどちら半分か」を見よ。

## 名前：名前だけで、それが何で何をするかが言える

**判定基準：コメントも呼び出し箇所も実装も見ずに、その名前だけで、それが何で、何をし、何をしないかが言えるか。**
言えないなら名前を変える。そういう名前が付けられないときは、たいていそのコードの仕事自体がまだ定まっていない。

`fn f(a: u64, b: u64)` と `fn commit_transaction(generation: Generation, root: LogicalAddress)`
の差は意味が丸ごと一層分であり、モデルは実装を読んでもそれを補えない。

対象は**自分たちが宣言するすべての名前**：変数、引数、関数、メソッド、型、フィールド、列挙子、定数、
モジュール、ファイル、ジェネリック引数、ライフタイム、クロージャ引数、ループ変数、テスト関数、マクロ。
外部が決めた名前はこちらの管轄ではない：`Display` を実装するならメソッド名は `fmt` である。

| 規則 | 細則 |
|---|---|
| **長さに上限を設けない** | 「名前は短く」という規則はない。十文字増やして意味が一層増えるなら、機械の側では常に割に合う |
| **略語を使わない** | `cnt`、`idx`、`buf`、`tmp` はすべて書き切る。例外は登録済みのドメイン略語だけ（「略語登録表」を見よ） |
| **一文字の名前を使わない** | ループ変数、クロージャ引数、ジェネリック引数、ライフタイム、エラーの束縛もすべて対象：`i` → `stripe_index`、`T` → `Key`、`'a` → `'journal`、`Err(e)` → `Err(error)` |
| **事前条件と作用範囲を名前に書く** | `write_node` は何も言っていない。`append_verified_node_to_journal` は三つのことを言う：上書きではなく追記、引数は検証済み、書き先はジャーナル領域 |
| **単位を明記する** | 型で表せるなら型に任せる（`LogicalAddress`、`Duration`）。表せないなら名前に書く：`offset` ではなく `offset_in_blocks` |
| **真偽値は述語として書く** | どちら側が真かを言う：`flag`、`status`、`ok` ではなく `is_checksum_verified` |
| **テスト名にはシナリオと期待結果を書く** | `test_commit` や `it_works` ではなく `crash_between_data_write_and_commit_keeps_previous_generation` |
| **一つの意味概念にはリポジトリ全体で一つの名前** | 単位は意味概念であって語ではない：同じ概念をここでは `generation`、あちらでは `epoch` と呼んではならない。二つの概念は、下層の意味が近くても（ディスクに記録された世代番号と、トランザクションのライフサイクル上の世代番号）名前を共有してはならず、それぞれ役割を付ける：`committed_generation`、`transaction_generation` |
| **名前は単独で成り立たせ、モジュールパスで補わない** | `block::Address` ではなく `block::BlockAddress` と書く：`use` した後の呼び出し箇所には `Address` しか残らず、モデルにはパスが見えない。これは**意図して名前に名前空間の情報を担わせる**ことであり、代償として型名が手作りの名前空間になる（`BlockAddress`、`JournalAddress`、`LogicalAddress`……）。その代償は引き受ける。理由は検索結果や呼び出し箇所ではパスが見えないことであって、「長い名前ほどよい」からではない |
| **意味が変わったら名前を変える** | 同名のシャドーイングは意味が変わらないときだけ使う。生データが検証済みデータになった、バイト数がブロック数になった、というときは新しい名前を付ける |

### なぜ略語は純粋な損失なのか

節約できるのは文字数で、失われるのは意味であり、モデルにはそれが補えない——さらに悪いことに、モデルは補ってしまう。
`cnt` はある箇所ではブロック数、別の箇所ではリトライ回数を指す。その一方を検索で引いたモデルは「読めない」とは言わず、
最もありふれた解釈で先へ進む。ファイルシステムでは `ext` は extent のことも extension のこともあり、
`gen` は generation のことも generator のこともある。

**判定基準は「権威ある定義が一箇所にあるか」であって、「みんなが分かるか」ではない。**
だから Rust のキーワードと基本型の名前（`mut`、`fn`、`str`、`u64`）は略語に数えない。言語仕様がそれらの唯一の定義である。
プロジェクト固有のドメイン略語（`lba`、`crc`）は登録して初めて使える。

### 略語登録表

プロジェクト直下の `.claude/abbreviations`。一行一項目で、`#` の後に正式名と意味を書く：

```text
lba  # logical block address：論理ブロックアドレス。ファイルシステムがブロックに振る番号
crc  # cyclic redundancy check：巡回冗長検査
```

登録表がその略語の唯一の権威ある定義であり、他の箇所はそれに従い、二つ目の定義を書かない。
**一文字は登録できない**：一文字には唯一の意味がない。

**プロジェクト自身の番号**（kb に登録された実験 E57、判断 D22 の類）を名前の一区切りとして使うときは、「文字と数字」という一つの類として登録する：

```text
e<数字>  # 実験番号。.claude/kb/experiments.md に登録
```

（`<数字>` は lint が書かれたとおりに読む書式である。）
登録すれば `e57_field_authority` の `e57` は一文字に数えない。名前の中の番号も簡称を伴わせる
（`kb-discipline.md` 第 5 条）：裸の `e57` ではなく `e57_field_authority` と書く。

### 意味の置き場所：コメント < 名前 < 型

同じことの三つの書き方、悪い順から：

```rust
// 一、意味をコメントに置く —— 最も悪い
// dim0: 民族  dim1: 性別  dim2: 年齢層
pop[i][j][k]

// 二、意味を名前に置く —— 従来は冗長と嫌われたが、機械はこれを好む
number_of_china_people[han][woman][teenager_18_to_24]

// 三、意味を型に置く —— 最善。次元を取り違えるとそもそもコンパイルが通らない
number_of_china_people[Ethnicity::Han][Gender::Woman][AgeBand::Teenager18To24]
```

一つ目は人間の頭に収めるための圧縮である：名前を最短に切り詰め、意味をコメントへ移す。
行幅も画面も限られていた時代にはそれが妥当だったが、コメントはコードから乖離し、名前は乖離しない——名前はコード自体だからである。
二つ目は各次元が自己記述的であり、**文脈なしにそのアクセスの正否を判断できる。**
三つ目は情報を「読める」から「検査できる」へ押し上げる。次元を入れ違えればコンパイルが通らない。

**型で表せる制約は型に、型で表せないものは名前に置き、いずれもコメントには書かない。後ろほど実装から乖離しにくい。**

## 分岐：網羅して書き切り、ワイルドカードアームを書かない

```rust
// ✗ 汎用パス：新しい場合が増えても、コンパイラは何も言わない
fn node_size_in_bytes(device: &Device) -> u32 {
    if device.is_rotational { 64 * 1024 } else { 16 * 1024 }
}
```

```rust
// ✓ 網羅分岐：Zoned を足したら、ここを埋めるまでコンパイルが通らない
enum Medium {
    Rotational,
    SolidState,
    Zoned { zone_size_in_bytes: u32 },
}

fn node_size_in_bytes(medium: &Medium) -> u32 {
    match medium {                                  // 要点は、**書かなかった** `_ =>` のアームにある
        Medium::Rotational                   => 64 * 1024,
        Medium::SolidState                   => 16 * 1024,
        Medium::Zoned { zone_size_in_bytes } => (*zone_size_in_bytes).min(256 * 1024),
    }
}
```

**効いているのは、書かなかった `_ =>` である。** ワイルドカードアームを足すとコードは短く「汎用的」に見えるが、
実際にやったのはコンパイラの網羅性検査を切ることだ：新しい場合は黙ってワイルドカードに落ち、
誰も警報を上げないまま誤った挙動をする。**判定基準は「分岐が多いか」ではなく「ある場合を取りこぼしたとき、先に気づくのは誰か」である**：
コンパイラか、本番か。

- **閉じた集合の列挙型では、`match` に `_ =>` を書かない。** 自前の列挙型は既定で閉じた集合である：場合がいくつあるかはこちらが決める。
- **意味上、未知の値を許すもの**（ディスクから読んだもの、プロトコルで受け取ったもの、将来も新しい値が増える符号）は、「未知」を明示的な列挙子
  （`Unrecognized(raw_code)`）にし、`match` はそのまま網羅する。このときもワイルドカードアームは同じく有害である：後で既知の列挙子を一つ足すと、
  `_ =>` はそれを黙って「未知」のアームへ送り込む。プロトコルの進化で最も起きやすいのがまさにこの誤りである。
- **本当に開いているのは二種類だけ**：外部の列挙型（他のクレートのもの、`#[non_exhaustive]` 付きのもの）と、対外的に約束し、
  将来の進化の余地を残す公開 API（「適用しないとき」を見よ）。ワイルドカードアームが本当に必要なら、
  その箇所に `#[allow(clippy::wildcard_enum_match_arm, reason = "…")]` を書く。
- **ワークスペース内部で使う列挙型には `#[non_exhaustive]` を付けない**：ワークスペースの他のクレートのすべての `match` にワイルドカードアームを強いることになり、
  網羅性検査を丸ごと切るのと同じである。
- **閉じた集合（場合がいくつあるかはこちらが決める）は `enum` と網羅的な `match` で書き、トレイトオブジェクトにしない。**
  列挙型はすべての場合を一箇所に並べるので、経路数を言える。二つの場合の相互作用（状態遷移、二つずつの比較）も
  タプルに対する網羅的な `match` として書け、組み合わせを一つ落とせばコンパイルが通らない。一方、トレイトの既定メソッドはワイルドカードアームに等しい：
  実装を一つ足すと、上書きしなかったメソッドは黙って既定の挙動を引き継ぐ。開いた集合（プラグイン、テストダブル）は従来どおりトレイトを使う。
- **実装が一つしかないトレイトは抽出しない。** 本物の実装が少なくとも二つ（モデル対照テストに使うモデルも一つに数える）あって初めてトレイトを抽出する。
  「後で差し替えやすいように」だけで抽出した一層は、誰も検証しない開いた集合である。
- **網羅的な `match` のアームの数は複雑さに数えない。** 数えるのはコンパイラである。上限を設けるべきは互いに独立な条件の数で、それが経路を指数的に増やす。

## 型：不正な状態を書けなくする

```rust
// ✗ 一つの下層型が複数の意味を担う：取り違えてもコンパイルが通り、実行時に壊れる
fn read_block(address: u64) -> Block;
fn free_extent(start: u64, length_in_blocks: u64);
// 呼び出し側が物理アドレスの位置に論理アドレスを渡しても、コンパイラは何も言えない
```

```rust
// ✓ newtype：取り違えるとコンパイルが通らない
#[derive(Clone, Copy, PartialEq, Eq)] pub struct LogicalAddress(pub u64);
#[derive(Clone, Copy, PartialEq, Eq)] pub struct PhysicalAddress(pub u64);

fn read_block(address: PhysicalAddress) -> Block;
// read_block(LogicalAddress(value)) はコンパイルできない —— 実行時バグの一群が丸ごとコンパイルエラーになる
```

さらに一歩進めて、**「まだ検証していない」ことも型にする**と、「検証を忘れた」が書けなくなる：

```rust
// ✗ 状態を真偽値のフィールドで表す：確認を忘れてもコンパイラは関知しない
struct Node { bytes: Vec<u8>, is_checksum_verified: bool }

// ✓ 状態を型で表す：検証していないものは、検証済みの型になりようがない
struct RawNode(Vec<u8>);        // ディスクから読んだ直後、未検証
struct VerifiedNode(Vec<u8>);   // チェックサム照合済み

impl RawNode {
    fn verify(self, expected_checksum: Checksum) -> Result<VerifiedNode, CorruptBlock> { /* ... */ }
}

fn walk(node: &VerifiedNode) { /* ... */ }   // 検証を飛ばすと、そもそも引数が作れない
```

- 一つの下層型が異なる意味を担うなら（論理アドレス、物理アドレス、世代番号。バイト数、ブロック数）、意味ごとに newtype を一つ与える。
- 「検証したか」「永続化したか」のような状態は型にし、真偽値のフィールドにしない。**境界で一度だけ検証し**、証明を携えた型に変えたら、
  そこから内側は型を信じ、層ごとに検査し直さない。
- **真偽値の引数は列挙型に置き換える**：`write(node, true)` は呼び出し箇所で何も言っていないが、`write(node, Durability::Synced)` は言っている。
- **カプセル化は不変条件を守るためのものであって、隠すためのものではない。** 不変条件を持つフィールドは private にし、検査する構築関数からしか入れないようにする。
  不変条件のないフィールドはそのまま公開し、定型の getter / setter を書かない。
- **不変条件を持つ型は `Default` を実装しない**：検査を経ずに作られた値こそ、その型が締め出すべきものである。
- **自前の構造体を構築するときは、すべてのフィールドを書き出し**、`..Default::default()` を使わない。
  それはフィールドに対するワイルドカードアームである：フィールドを一つ足すと、書かなかった箇所は黙って既定値を受け取る。すべて書き出せば、一つ落とすとコンパイルが通らない。
  必須のフィールドを builder に任せて実行時に検査させず、構築関数の引数にする。本当に省略可能なものだけを builder に入れる。
- **値を失いうる数値変換に `as` を使わない。** `as` は切り詰めも符号の喪失も桁あふれも黙って行う。値を失いうる方向では `try_from` を使って失敗を処理し、
  失わない方向では `from` を使う。

**分岐と型は同じ一つのことの両面である**：一方は「場合の取りこぼし」をコンパイラに捕まえさせ、もう一方は「不正な組み合わせ」を書けなくする。
どちらも検査を人から機械へ移す。

## エラー：回復できるものは型に書き、不変条件の破れはアサートする

- **回復できる失敗**（I/O エラー、ディスク上のデータの破損、資源不足）**は `Result` で返す。** エラー列挙型の列挙子は**呼び出し側が下す判断ごとに分け**、
  下層の原因ごとには展開しない：上位が実際に振り分けるのは「見つからない」「データ破損」「空き容量不足」「その他の I/O エラー」の数種類だけかもしれず、
  下層の数十種類の OS エラーは「その他の I/O エラー」の列挙子に source として持たせる。呼び出し側はそれを `match` し、一つでも処理し忘れればコンパイルが通らない。
- **判定基準は、呼び出し側が本来下せるはずの判断を失うかどうかである。** ライブラリの公開境界では `anyhow` や `Box<dyn Error>` のような統一エラー型を使わない：
  それは「再試行する」「破損を報告する」「空き不足を報告する」を一塊にしてしまい、呼び出し側は振り分けられない。これはエラーに対するワイルドカードアームである。
  逆に、下層の失敗の一つ一つを各層でそれぞれ列挙子に展開し直すのも誤りである：列挙子が増えるほど、肝心の数種類が埋もれる。
  テストとコマンドラインツールは統一エラー型を使ってよい。
- **不変条件の破れはバグであり、アサートする**。壊れた状態のまま先へ進まず、ましてディスクには書かない。
- **`unwrap()` は書かず、`expect` を書く**。メッセージにはどの不変条件に依拠しているかを書く：
  `expect("journal ヘッダは open() で検証済み。ここで None なら検証が飛ばされている")`。それが名前付きのアサーションになる。

## 関数とネスト：「独立に検証できる」単位で切り、経路数で縛る

**関数の長さは「独立に検証できる一つのこと」で決め、画面の高さでは決めない。** 一つのことなら三百行でもよい。
二つのことが二十行に詰め込まれていれば分ける。

**ネストの層数には上限を設けず、縛るのは経路数である。** 「ネストは三層まで」は測る対象を間違えている：

| | 経路数 | テストできるか |
|---|---|---|
| 12 次元構造を巡る 12 層の `for` | **1** | 制御フローとしては完全にテスト可能。ループ本体の状態は別途検証する |
| 独立した 12 層の `if/else` | **2¹²** | テストしきれない |
| 独立した 3 層の `if/else` | 8 | かろうじて |

早期脱出のないループのネストは経路をほとんど増やさず（`break`、`continue`、`?` はそれぞれ一本ずつ足す）、条件のネストは指数的に増やす。
旧規則が両者をまとめて縛ったのは、人間にとってはどちらも同じように読みづらいからである——それは人間の制約であって、検証の制約ではない。
したがって層数は自由で、次の二つを満たせばよい：経路数が言えて、かつ有界であること。
各層の反復対象に名前と型があり、`a[i][j][k][l]` ではないこと。あの書き方の問題は深さではなく、情報を持たないことである。

**経路数が測るのは制御フローだけであり、検証の難しさのすべてではない。** ループが何回回るか、ある回から次の回へ持ち越す状態、早期脱出、
入れ子のループどうしのデータ依存は、どれも経路を一本も増やさずに検証すべき空間を大きくしうる。
だから経路数は制御フローの複雑さの硬い指標である：上限を超えたら分ける。超えていないからといって検証しやすいとは限らない。ループはさらに三つのことを明記する：
反復回数の上限、回をまたいで持ち越す状態とその不変条件（アサーションとして書く）、すべての早期脱出。
**「経路は一本しかない」は、検証の難しいアルゴリズムの弁護には使えない。**

- **引数の個数には上限を設けない。** 各引数に名前と型があればよい。いくつかの引数がそれ自体で不変条件を持つ一つの概念をなすときに限り、
  一つの型にまとめる。シグネチャを短くするためだけに構造体を寄せ集めない。
- **結果は戻り値の型に入れ**、`&mut` の出力引数では返さない：データがどこへ流れるかをシグネチャに書く。
- **副作用は端へ押しやり、中核は純粋関数として書く。** 純粋関数は網羅でき、モデルと対照テストできる。I/O を伴う外殻はクラッシュ点リプレイでしか検証できないので、
  薄いほどよい。問い合わせと変更の両方を行う関数は、名前で両方を言う。
- **早期リターンは自由に使ってよい。** 単一出口は人間が制御フローを追うためのものだった。こちらが数えるのは経路であって、出口ではない。

## コメント、アサーション、定数、重複

- **コメントは「なぜこうなのか」だけを書き**、「これが何をしているか」は書かない。後者は機械が自分で読める。
  制約は型・名前・アサーションに書き、コメントには書かない：コメントは実装から乖離するが、名前と型は乖離しない。
- **ドキュメントコメントには型で表せない契約を書く**：どのエラーを返すか、いつ panic するか、`unsafe` が呼び出し側に何を求めるか。
  名前を言い直しているだけのドキュメントコメントは消す。
- **すべての `unsafe` ブロックの上に `// SAFETY:` を書き**、なぜ安全かを述べる。これは型に書けない不変条件であり、コメントにしか書けない。
- **不変条件はアサーションとして書き**、文書に書くだけで済ませない。
- **マジックナンバーは名前付き定数にする**：一つの数の定義は一箇所だけとし、名前か型に単位を持たせる。
- **重複は生成し、手で写さない。** 複数箇所の同期修正は機械の得意分野だが、それはそれらの箇所が同じ一つの生成器から出ていることが前提である：
  生成した重複は分岐しないが、手で写した重複は分岐する。マクロと `build.rs` は生成の正道だが、生成だけを行い、ロジックを隠さない。
  生成物にはテストを張り付ける——マクロ展開から出てくる名前は命名検査には見えない。
- **使わないコードは消し**、コメントアウトしたコードも消す：git から取り戻せる。残っているのは誰も走らせない経路である。
  コンパイラの `never used` はエラーとして扱う（`command-safety.md`：警告はただで手に入る信号である）。
- **`TODO` には何が欠けていて、なぜ今やらないのかを書く。** 借りている検査はプロジェクトの kb の借り検査表に記し、コードからそこを指す。
  「TODO: あとで直す」の一言だけでは、誰も戻ってこない。

## 一条ずつ吟味した流行りのやり方

どれも `machine-first.md` の手順を一度通した：それは元々どの問題を解いていたか、その問題は今も存在するか、
第二の理由はあるか。**処置**は六種類しかない：廃止、緩める、書き換え、残す（理由を書き換え）、ツールに任せる、助言に格下げ。

### 分岐と抽象化

| 流行りのやり方 | 出典 | 元々解いていた問題 | 処置 | こちらの書き方 |
|---|---|---|---|---|
| 条件分岐をポリモーフィズムで置き換える | 『リファクタリング』 | 場合を一つ足しても旧いコードを変えない | **閉じた集合では廃止** | `enum` と網羅的な `match`（「分岐」を見よ） |
| 開放閉鎖原則 | SOLID | 機能を足しても旧いコードを変えない | **閉じた集合では廃止** | こちらが欲しいのはまさにその逆：場合を一つ足したら、コンパイラが旧いコードのすべての箇所を見直させる |
| 単一責任 | SOLID | クラスが変わる理由は一つ | **残す（理由を書き換え）** | 一部分には独立に検証できる契約が一つだけ |
| リスコフの置換 | SOLID | 子クラスが親クラスの代わりになる | **残す（理由を書き換え）** | トレイトの契約はすべての実装で成り立つ：契約テストをすべての実装に対して走らせる。陽性対照を被検のすべてのアームに対して走らせるのと同じことである（`test-discipline.md`） |
| インタフェース分離 | SOLID | 使わないメソッドへの依存を強いられない | **残す（理由を書き換え）** | トレイトが小さいほど、各実装が検証すべき契約は小さく、既定メソッド（ワイルドカードアーム）は少ない |
| 依存性逆転：具体ではなく抽象に依存せよ | SOLID | 差し替えやすく、モックしやすい | **書き換え** | 本物の実装が少なくとも二つあって初めてトレイトを抽出する。モデル対照テストに使うモデルも一つに数える |
| デメテルの法則：直接の友人とだけ話せ | ノースイースタン大学の Demeter プロジェクト | 構造を変えたときの波及が少ない | **緩める** | モジュール内部では自由に連鎖してよい。モジュールをまたいで他人の内部を貫くのは禁止——それは契約を迂回している |
| デザインパターン：ファクトリ、ストラテジー、ビジター | 『デザインパターン』 | 決まった構造を再利用する | **書き換え** | 閉じた集合上のストラテジーやビジターはただの `match` である。パターンのためのパターンで増えた一層は、誰も検証しない開いた集合である |

| 流行りのやり方 | 出典 | 元々解いていた問題 | 処置 | こちらの書き方 |

| エラーコードか例外か | 言語をまたぐ論争 | それぞれに代償がある | **型に任せる** | 失敗を戻り値の型に書き、コンパイラに処理を強制させる |

### コメントと文書

| 流行りのやり方 | 出典 | 元々解いていた問題 | 処置 | こちらの書き方 |
|---|---|---|---|---|
| コメントを多く書く | 初期の慣習 | 人が読むため | **書き換え** | コメントは「なぜ」だけを書く |
| コメントは失敗である。良いコードにコメントは要らない | 『Clean Code』 | コメントは古くなる | **書き換え** | 「何であるか」は名前と型に任せる——この半分には同意する。「なぜこうなのか」は書く。それは名前には収まらない |
| 公開項目にはすべてドキュメントコメントを書く | rustc の `missing_docs` | 使う人が理解できる | **書き換え** | 名前を言い直しているだけのものは消し、型で表せない契約だけを書く |
| `unsafe` ブロックに `// SAFETY:` を書く | Rust の慣習 | なぜ安全かを述べる | **残す。clippy が止める** | 型に書けない不変条件だからである |
| コメントアウトしたコードを後のために残す | 通行のやり方 | 消すと取り戻せないのが怖い | **廃止** | git から取り戻せる。残っているのは誰も走らせない経路である |
| コメントに変更履歴と作者を記録する | 旧い慣習 | 誰が変えたか分かる | **廃止** | 履歴は git と CHANGELOG に（`design-doc-discipline.md`） |
| `TODO` コメント | 通行のやり方 | 後で戻る心覚え | **書き換え** | 何が欠けていて、なぜ今やらないのかを書く。借りている検査は kb に記す |

### 書式

| 流行りのやり方 | 出典 | 元々解いていた問題 | 処置 | こちらの書き方 |
|---|---|---|---|---|
| 一行 80 桁まで | Linux カーネルのコーディングスタイル、PEP 8 ほか | 端末の幅 | **ツールに任せる** | `rustfmt` の既定値に従う。名前が長ければ改行し、行幅のために名前を縮めない |
| 8 桁のインデントでネストを浅く保たせる | Linux カーネルのコーディングスタイル | 深いネストは人が追えない | **廃止** | 層数に上限なし（「関数とネスト」を見よ） |
| 縦の空白、関連する行は近くに置く | 『Clean Code』 | 人がすばやく目を通せる | **ツールに任せる** | 手で調整しない |

### テストコード

| 流行りのやり方 | 出典 | 元々解いていた問題 | 処置 | こちらの書き方 |
|---|---|---|---|---|
| 一つのテストにアサーションは一つ | 『Clean Code』 | どれが赤くなったか一目で分かる | **廃止** | 一つのテストに一つのシナリオ。アサーションは複数でよく、それぞれのメッセージに何を期待するかを書く |
| カバレッジをある割合に到達させる | 通行のやり方 | テストが足りているかを定量化する | **書き換え** | カバレッジは正しさではない。経路数とミューテーションリストで語る（`test-discipline.md`） |
| 依存はすべてモックする | 通行のやり方 | 速い、隔離できる | **書き換え** | モックはテストを書く人の想定を書き込んだものであり、自分で自分に答えを渡すのと同じである。モデル対照テストのモデルと本物の実装を優先する |
| テストピラミッド：単体テストを最も多く | Mike Cohn | 速さ | **書き換え** | 単体テストは速い折り返しである。受け入れの根拠はモデル対照テスト、クラッシュ点リプレイ、QEMU ストレス（`show-me-test.md`） |
| テストコードも DRY に | 通行のやり方 | 書く量を減らす | **緩める** | 各テストはそれ自体でシナリオが読めること。準備は補助関数にまとめてよいが、アサーションは中に隠さない |
| 不安定なテストは何回か走らせれば通る | 通行のやり方 | パイプラインを止めない | **廃止** | 不安定なら不安定とそのまま言い、緑になるまで走らせ直さない（`test-discipline.md`） |
| テストを先に書く | Kent Beck（TDD） | 使い方から設計を逆算する | **残す（理由を書き換え）** | 先に赤くなるのを見てこそ、赤くなりうることが証明される（`show-me-test.md`） |

### 変更の仕方

| 流行りのやり方 | 出典 | 元々解いていた問題 | 処置 | こちらの書き方 |
|---|---|---|---|---|
| ボーイスカウトの規則：通りがかりについでに片付ける | 『Clean Code』 | コードは放っておくと腐る | **書き換え** | ついでの片付けは別のコミットにする。機能のコミットに混ぜると、二分探索も巻き戻しも難しくなる |
| 割れ窓を許さない | 『達人プログラマー』 | 小さな問題がさらなる問題を招く | **残す。ゲートで実施する** | コンパイラと clippy の警告はエラーとして扱う |
| 早すぎる最適化を避ける | Knuth | 人の時間が足りない | **助言に格下げ** | — |

設計と工程のレベルの指針（設計の統一、PR は小さく、および誰がコードを読むかと無関係なために残したもの）は `machine-first.md` にある。

## 適用しないとき

**これらの細則は「消せるもの」には無条件で使い、「消せないもの」には別勘定が要る。**
コードの名前・分岐・型の誤りは直せる。しかし対外的な約束——ディスク形式、プロトコル、公開 API——に書き込まれたものは直せず、
以後すべての実装が永久に支え続けねばならない。その側の判定基準は別に立てる。「明示のほうが安全だ」の一言で押し通してはならない。

## ゲートが見るのはどちら半分か

| 細則 | 誰が検査するか |
|---|---|
| 一文字の名前、よくある略語 | `scripts/naming-lint.sh`（ゲート段階「命名規律」）：プロジェクト内のすべての `.rs` を走査し、自分たちが宣言した名前だけを見る |
| 閉じた集合の列挙型に `_ =>` を書かない | clippy の `wildcard_enum_match_arm`。開いていると宣言したものは、その箇所で allow し reason を書く |
| `#[allow]` には `reason = "…"` を書く | clippy の `allow_attributes_without_reason` |
| 値を失いうる `as` 変換 | clippy の `cast_possible_truncation`、`cast_sign_loss`、`cast_possible_wrap` |
| `unsafe` ブロックには `// SAFETY:` | clippy の `undocumented_unsafe_blocks` |
| 無関係な意味での同名のシャドーイング | clippy の `shadow_unrelated` |
| 警告はエラーとして扱う | clippy の `-D warnings` |
| 名前が十分に言っているか、一つの概念が一つの名前か、関数が一つのことだけをしているか、コメントが「なぜ」を書いているか、エラーの列挙子が呼び出し側の判断で分かれているか、ループの状態が書き出されているか、`..Default::default()` | レビュー。機械には判断できないか、まだ既成の検査がない |
| シェルスクリプトの名前 | **まだ検査になっていない**。`gate.sh` が未実装の段階に挙げている |

clippy の分は `scripts/check.sh` の中で走る。つまりゲートの「ビルドと単体テスト」段階であり、プロジェクト直下に `Cargo.toml` がなければこの段階は走らない。

`naming-lint.sh` の略語リストは最もよくあるものだけを挙げている。**リストにない略語も違反であることに変わりはなく**、ゲートに見えないだけである。
見分けられない形（行をまたぐパターン、マクロ展開から出てくる名前）は判定せずレビューに回す。見分けられないことは通過したことではない。
トレイト実装のメソッド名と関連型、および `extern` ブロックの宣言は外部が名付けたものであり、検査しない。

プロジェクト側の設定ファイルは二つ。一行一項目で、`#` の後に理由を書き、理由は省けない：

| ファイル | 何を管理するか |
|---|---|
| `.claude/abbreviations` | 登録済みのドメイン略語。書式は「略語登録表」を見よ |
| `.claude/naming-lint-exclude` | 走査しないディレクトリ、または単独の `.rs` ファイル。除外すると、その中の名前は誰も見なくなるので、なぜかを書く。存在しないパスを指す項目、`.rs` を一つも除外しない項目は赤になる。旧いコードを洗い直すときは、まだ直していないファイルを一つずつ並べ、直すたびに一行消す：除外は縮むだけで広がらず、新しいファイルは検査される |

外部が決めたその他の名前（外部書式のフィールド名の類）は、その行に `// naming-lint:external <なぜこの名前はこちらが決めるものではないか>` を書く。
免除されるのはその一行だけで、理由はやはり省けない。
