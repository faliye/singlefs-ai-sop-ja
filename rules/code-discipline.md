# コーディング規律

コードを書くときはこれに従う。緩めるのは人間の頭に収めるための圧縮だけで、意味を明示することは一切緩めない。

対象は本プロジェクトで自分たちが書くコードとテキストすべて。言語もディレクトリも問わない：製品コード、テスト、実験コード、スクリプト、設定ファイルとビルドファイル、そして文書（README、設計説明、kb、規則、skill、agent 定義、コミットメッセージ、ゲートの失敗メッセージ）。
例は Rust で書く。ほかの言語も同じ判定基準に従い、その言語での対応する書き方にする。
文書が従うのは二つ：触れる名前は「名前」の節に従って付け、文は「コメントに略語を書かず、符号で物を指さない」の一条に従って書く。
ゲートがどこまで検査するかは「ゲートが見るのはどちら半分か」を見よ。

## 名前：名前だけで、それが何で何をするかが言える

**判定基準：コメントも呼び出し箇所も実装も見ずに、その名前だけで、それが何で、何をし、何をしないかが言えるか。**
言えないなら名前を変える。そういう名前が付けられないときは、まずそのコードが何をするのかを定める。

対象は**自分たちが宣言するすべての名前**：変数、引数、関数、メソッド、型、フィールド、列挙子、定数、
モジュール、ファイル、ジェネリック引数、ライフタイム、クロージャ引数、ループ変数、テスト関数、マクロ。
外部が決めた名前はこちらの管轄ではない：`Display` を実装するならメソッド名は `fmt` である。

| 規則 | 細則 |
|---|---|
| **長さに上限を設けない** | 「名前は短く」という規則はない |
| **略語を使わない** | `cnt`、`idx`、`buf`、`tmp` はすべて書き切る。例外は登録済みのドメイン略語だけ（「略語登録表」を見よ） |
| **一文字の名前を使わない** | ループ変数、クロージャ引数、ジェネリック引数、ライフタイム、エラーの束縛もすべて対象：`i` → `stripe_index`、`T` → `Key`、`'a` → `'journal`、`Err(e)` → `Err(error)` |
| **事前条件と作用範囲を名前に書く** | `write_node` は何も言っていない。`append_verified_node_to_journal` は三つのことを言う：上書きではなく追記、引数は検証済み、書き先はジャーナル領域 |
| **単位を明記する** | 型で表せるなら型に任せる（`LogicalAddress`、`Duration`）。表せないなら名前に書く：`offset` ではなく `offset_in_blocks` |
| **真偽値は述語として書く** | どちら側が真かを言う：`flag`、`status`、`ok` ではなく `is_checksum_verified` |
| **テスト名にはシナリオと期待結果を書く** | `test_commit` や `it_works` ではなく `crash_between_data_write_and_commit_keeps_previous_generation` |
| **一つの意味概念にはリポジトリ全体で一つの名前** | 単位は意味概念であって語ではない：同じ概念をここでは `generation`、あちらでは `epoch` と呼んではならない。二つの概念は、下層の意味が近くても（ディスクに記録された世代番号と、トランザクションのライフサイクル上の世代番号）名前を共有してはならず、それぞれ役割を付ける：`committed_generation`、`transaction_generation` |
| **名前は単独で成り立たせ、モジュールパスで補わない** | `block::Address` ではなく `block::BlockAddress` と書く。その結果、型名が手作りの名前空間になる（`BlockAddress`、`JournalAddress`、`LogicalAddress`……）が、そのとおりに書く |
| **番号や位置を名前にしない** | 関数、変数、引数、型、フィールド、定数、モジュール、ファイル、どの名前も同じ：`layer0`、`stream_0`、`step2`、`phase_1`、`first_item` のように「何番目か」しか言わない名前は使わない。何をするか、何を扱うかを書く：`stream_0` → `metadata_journal_stream`、`layer0` → `checksum_verification_layer`。本当に位置だけが違う複数の実体は一つのコレクションに入れ、型付きの添字で区別する（`stream_index: StreamIndex`）。一つずつ番号付きの名前を付けない。登録済みのプロジェクト番号は略称付きでそのまま使う。「略語登録表」を見よ |
| **意味が変わったら名前を変える** | 同名のシャドーイングは意味が変わらないときだけ使う。生データが検証済みデータになった、バイト数がブロック数になった、というときは新しい名前を付ける |
| **一つのスコープで一つの名前は一度だけ定義する** | 一つのファイルの同じスコープ（モジュール、クラス本体、関数本体。shell はファイル全体）で、関数・メソッド・クラスを同じ名前で二度定義しない。定義を足す前に、そのファイルでその名前を検索する。ぶつかったら片方を改名するか、片方を消す。property の setter、`@overload`、singledispatch の `register` は数えない |

### 略語は使わない。判定基準は権威ある定義が一箇所にあるか

**判定基準は「権威ある定義が一箇所にあるか」であって、「みんなが分かるか」ではない。**
Rust のキーワードと基本型の名前（`mut`、`fn`、`str`、`u64`）は略語に数えない。言語仕様がそれらの唯一の定義である。
プロジェクト固有のドメイン略語（`lba`、`crc`）は登録して初めて使える。

### 略語登録表

プロジェクト直下の `.claude/abbreviations`。一行一項目で、`#` の後に正式名と意味を書く：

```text
lba  # logical block address：論理ブロックアドレス。ファイルシステムがブロックに振る番号
crc  # cyclic redundancy check：巡回冗長検査
```

登録表がその略語の唯一の権威ある定義であり、他の箇所はそれに従い、二つ目の定義を書かない。
**一文字は登録できない。**

**プロジェクト自身の番号**（kb に登録された実験番号や決定番号の類）を名前の一区切りとして使うときは、「文字と数字」という一つの類として登録する：

```text
e<数字>  # 実験番号。.claude/kb/experiments.md に登録
```

（`<数字>` は lint が書かれたとおりに読む書式である。）
登録すれば `e57_field_authority` の `e57` は一文字に数えない。名前の中の番号も簡称を伴わせる
（`kb-discipline.md` 第 5 条「番号は索引にしかならず、呼び名にはならない」）：裸の `e57` ではなく `e57_field_authority` と書く。

### 意味の置き場所：コメント < 名前 < 型

同じことの三つの書き方、悪い順から：

```rust
// 一、意味をコメントに置く —— 最も悪い
// dim0: 民族  dim1: 性別  dim2: 年齢層
pop[i][j][k]

// 二、意味を名前に置く
number_of_china_people[han][woman][teenager_18_to_24]

// 三、意味を型に置く —— 最善。次元を取り違えるとそもそもコンパイルが通らない
number_of_china_people[Ethnicity::Han][Gender::Woman][AgeBand::Teenager18To24]
```

**型で表せる制約は型に、型で表せないものは名前に置き、いずれもコメントには書かない。**

## 分岐：網羅して書き切り、ワイルドカードアームを書かない

```rust
enum Medium {
    Rotational,
    SolidState,
    Zoned { zone_size_in_bytes: u32 },
}

fn node_size_in_bytes(medium: &Medium) -> u32 {
    match medium {                                  // `_ =>` のアームを書かない：Medium を一つ足したら、ここを埋めるまでコンパイルが通らない
        Medium::Rotational                   => 64 * 1024,
        Medium::SolidState                   => 16 * 1024,
        Medium::Zoned { zone_size_in_bytes } => (*zone_size_in_bytes).min(256 * 1024),
    }
}
```

**判定基準は「分岐が多いか」ではなく「ある場合を取りこぼしたとき、先に気づくのは誰か」である**：本番ではなく、コンパイラが先に気づくようにする。

- **閉じた集合の列挙型では、`match` に `_ =>` を書かない。** 自前の列挙型は既定で閉じた集合である：場合がいくつあるかはこちらが決める。
- **意味上、未知の値を許すもの**（ディスクから読んだもの、プロトコルで受け取ったもの、将来も新しい値が増える符号）は、「未知」を明示的な列挙子
  （`Unrecognized(raw_code)`）にし、`match` はそのまま網羅する。ワイルドカードアームもやはり書かない。
- **本当に開いているのは二種類だけ**：外部の列挙型（他のクレートのもの、`#[non_exhaustive]` 付きのもの）と、対外的に約束し、
  将来の進化の余地を残す公開 API（「適用しないとき」を見よ）。ワイルドカードアームが本当に必要なら、
  その箇所に `#[allow(clippy::wildcard_enum_match_arm, reason = "…")]` を書く。
- **ワークスペース内部で使う列挙型には `#[non_exhaustive]` を付けない。**
- **閉じた集合（場合がいくつあるかはこちらが決める）は `enum` と網羅的な `match` で書き、トレイトオブジェクトにしない。**
  二つの場合の相互作用（状態遷移、二つずつの比較）はタプルに対する網羅的な `match` として書ける。開いた集合（プラグイン、テストダブル）は従来どおりトレイトを使う。
- **実装が一つしかないトレイトは抽出しない。** 本物の実装が少なくとも二つ（モデル対照テストに使うモデルも一つに数える）あって初めてトレイトを抽出する。
  「後で差し替えやすいように」では抽出しない。
- **網羅的な `match` のアームの数は複雑さに数えない。** 上限を設けるべきは互いに独立な条件の数である。

## 型：不正な状態を書けなくする

```rust
#[derive(Clone, Copy, PartialEq, Eq)] pub struct LogicalAddress(pub u64);
#[derive(Clone, Copy, PartialEq, Eq)] pub struct PhysicalAddress(pub u64);
fn read_block(address: PhysicalAddress) -> Block;   // read_block(LogicalAddress(value)) はコンパイルできない

struct RawNode(Vec<u8>);        // ディスクから読んだ直後、未検証
struct VerifiedNode(Vec<u8>);   // チェックサム照合済み
impl RawNode {
    fn verify(self, expected_checksum: Checksum) -> Result<VerifiedNode, CorruptBlock> { /* ... */ }
}
fn walk(node: &VerifiedNode) { /* ... */ }   // 検証を飛ばすと、そもそも引数が作れない
```

- 一つの下層型が異なる意味を担うなら（論理アドレス、物理アドレス、世代番号。バイト数、ブロック数）、意味ごとに newtype を一つ与える。
- 「検証したか」「永続化したか」のような状態は型にし、真偽値のフィールドにしない。**境界で一度だけ検証し**、証明を携えた型に変えたら、
  そこから内側は型を信じ、層ごとに検査し直さない。
- **真偽値の引数は列挙型に置き換える**：`write(node, true)` は `write(node, Durability::Synced)` と書く。
- **不変条件を持つフィールドは private にし**、検査する構築関数からしか入れないようにする。
  不変条件のないフィールドはそのまま公開し、定型の getter / setter を書かない。
- **不変条件を持つ型は `Default` を実装しない。**
- **自前の構造体を構築するときは、すべてのフィールドを書き出し**、`..Default::default()` を使わない。
  必須のフィールドを builder に任せて実行時に検査させず、構築関数の引数にする。本当に省略可能なものだけを builder に入れる。
- **値を失いうる数値変換に `as` を使わない**：値を失いうる方向では `try_from` を使って失敗を処理し、失わない方向では `from` を使う。

## コメント、アサーション、定数、重複

- **コメントは「なぜこうなのか」だけを書き**、「これが何をしているか」は書かない。
  制約は型・名前・アサーションに書き、コメントには書かない。
- **コメントで別のファイルの位置を指すときは、関数名、見出し、一意なアンカー文字列を書き、行番号は書かない。**
- **コメントに略語を書かず、符号で物を指さない。** 略語は書き下す。例外は登録済みのドメイン略語だけ（「略語登録表」を見よ）。
  `a`、`b`、`c`、`layer0`、`stream_0`、「層 0」「一つ目の項目」のように文字、番号、位置しか言わない呼び方は使わず、いくつかの物を「a b c」と略して並べることもしない：
  一つずつ、それが何で何をするかを書く。たとえば「一つ目の項目」は「チェックサムの項目」と書く。
- **ドキュメントコメントには型で表せない契約を書く**：どのエラーを返すか、いつ panic するか、`unsafe` が呼び出し側に何を求めるか。
  名前を言い直しているだけのドキュメントコメントは消す。
- **すべての `unsafe` ブロックの上に `// SAFETY:` を書き**、なぜ安全かを述べる。
- **不変条件はアサーションとして書き**、文書に書くだけで済ませない。
- **マジックナンバーは名前付き定数にする**：一つの数の定義は一箇所だけとし、名前か型に単位を持たせる。
- **重複は生成し、手で写さない。** マクロと `build.rs` は生成の正道であり、生成だけを行い、ロジックを隠さない。
  生成物にはテストを張り付ける。
- **使わないコードは消し**、コメントアウトしたコードも消す。
  コンパイラの `never used` はエラーとして扱う。
- **`TODO` には何が欠けていて、なぜ今やらないのかを書く。** 借りている検査はプロジェクトの kb の負債表に記し、コードからそこを指す。

## 適用しないとき

**これらの細則は「消せるもの」には無条件で使い、「消せないもの」には別勘定が要る。**
対外的な約束——ディスク形式、プロトコル、公開 API——に書き込まれたものは、判定基準を別に立てる。「明示のほうが安全だ」の一言で押し通してはならない。

## ゲートが見るのはどちら半分か

| 細則 | 誰が検査するか |
|---|---|
| 一文字の名前、よくある略語 | `scripts/naming-lint.sh`（ゲート段階「命名規律」）：プロジェクト内のすべての `.rs` を走査し、自分たちが宣言した名前だけを見る |
| 閉じた集合の列挙型に `_ =>` を書かない | clippy の `wildcard_enum_match_arm`。開いていると宣言したものは、その箇所で allow し reason を書く |
| `#[allow]` には `reason = "…"` を書く | clippy の `allow_attributes_without_reason` |
| 値を失いうる `as` 変換 | clippy の `cast_possible_truncation`、`cast_sign_loss`、`cast_possible_wrap` |
| `unsafe` ブロックには `// SAFETY:` | clippy の `undocumented_unsafe_blocks` |
| 無関係な意味での同名のシャドーイング | clippy の `shadow_unrelated` |
| `.py` と `.sh` の同じスコープで同名を二度定義する | `scripts/duplicate-definitions.py`（ゲート段階「同名定义」）：リポジトリ全体を走査し、凍結した証拠は走査しない。shell は行頭に書いた定義だけを判定する。後の定義で前の定義を上書きするのが意図どおりなら、後の定義の行に `# duplicate-definitions:allow <理由>` を書く。代入による関数の上書き、import した名前を def で上書きすること、ファイルをまたぐ同名は見分けられず、レビューに依る |
| 警告はエラーとして扱う | clippy の `-D warnings` |
| 名前が十分に言っているか、一つの概念が一つの名前か、関数が一つのことだけをしているか、コメントが「なぜ」を書いているか、コメントが別のファイルの行番号を引いていないか、名前やコメントが番号や位置を呼び名にしていないか、コメントに略語がないか、エラーの列挙子が呼び出し側の判断で分かれているか、ループの状態が書き出されているか、`..Default::default()` | レビュー |
| `.rs` 以外のコード（シェル、python など）と文書にある名前、略語、符号による呼び名 | **まだ検査になっていない**。`gate.sh` が未実装の段階に挙げている（キー「命名纪律（shell）」） |

clippy の分は `scripts/check.sh` の中で走る。つまりゲートの「ビルドと単体テスト」段階であり、プロジェクト直下に `Cargo.toml` がなければこの段階は走らない。

`naming-lint.sh` の略語リストは最もよくあるものだけを挙げている。**リストにない略語も違反であることに変わりはなく**、ゲートに見えないだけである。
見分けられない形（行をまたぐパターン、マクロ展開から出てくる名前）は判定せずレビューに回す。見分けられないことは通過したことではない。
トレイト実装のメソッド名と関連型、および `extern` ブロックの宣言は外部が名付けたものであり、検査しない。

プロジェクト側の設定ファイルは二つ。一行一項目で、`#` の後に理由を書き、理由は省けない：

| ファイル | 何を管理するか |
|---|---|
| `.claude/abbreviations` | 登録済みのドメイン略語。書式は「略語登録表」を見よ |
| `.claude/naming-lint-exclude` | 走査しないディレクトリ、または単独の `.rs` ファイル。なぜ除外するかを書く。存在しないパスを指す項目、`.rs` を一つも除外しない項目は赤になる。旧いコードを洗い直すときは、まだ直していないファイルを一つずつ並べ、直すたびに一行消す：除外は縮むだけで広がらず、新しいファイルは検査される |

外部が決めたその他の名前（外部書式のフィールド名の類）は、その行に `// naming-lint:external <なぜこの名前はこちらが決めるものではないか>` を書く。
免除されるのはその一行だけで、理由はやはり省けない。
