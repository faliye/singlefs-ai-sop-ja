# 受入の鉄則：Show me test

> **Make every submitted patch review-worthy.**
>
> 提出されたすべてのパッチを、レビューに値するものにする。

## 判定基準はテストである

**パッチの採否は自動検証が決める。** 通れば通る、通らなければ通らない。

## テストのないパッチは一切受け取らない

**`crates/*/src/` か `crates/*/build.rs` を変えたらテストを伴わなければならない。**
例外なし。「これは簡単すぎる」「次のパッチで足す」も通らない。
文書とスクリプトの変更、それに `.rs` のコメントだけを変えたものは対象外（コメントと空白を除いたコードが変更前とトークン単位で同じときだけをコメントだけの変更とみなす。doctest としてコンパイルされる文書コメント内のコードブロックと、文書コメントや `// SAFETY:` コメントの追加・削除はコードとして扱う。判定は `scripts/comment-only-change.py`）。

`scripts/show-me-test.sh` が強制する（`gate.sh` は段階として呼ぶ）。

## 最終的な判定基準はプロジェクトが決める

単体テストのような検査は速いフィードバックであって、**受入基準ではない。**
受入基準は被検対象と結びついている：どんな環境を立ち上げ、どんな負荷を走らせ、どんな故障を注入するか——
どれもプロジェクトが自分で決め、自分でテストし、自分で検証する。装置とそのゲート段階はプロジェクトに置き、共有ゲートは持たない。
未実装一覧には常に「最终判据」（最終判定基準）が載っている。このキーを書く前に、受入基準をプロジェクト自身の kb に書いておく：どんな環境を立ち上げ、どんな負荷を走らせ、どんな故障を注入するか。
段階がそのすべてを満たしたときだけ冒頭に `# gate-covers: 最终判据` と書き、一部だけのものは書かない。
一覧のほかの項目を覆う段階も同じく `# gate-covers: <その項目>` と書く（キーは `gate.sh` の綴りのまま写す）。
その段階がこの回に走って通ったときだけ、`gate.sh` はその項目を未実装一覧から「どの段階が覆っているか」へ移す。

## ゲートは通ったふりをしてはならない

未実装のゲート段階は**未実装であると明示的に報告**しなければならず、
黙って飛ばしてはならない。

**プロジェクト固有段階がこの回に判定対象を持たないときは、終了コード 77 を返す**：
`gate.sh` は「今回は走らず」と記録し、通過にも覆いにも数えない。
`exit 0` で飛ばすと集約では「判定して通った」と見分けがつかない。そこは段階を書く人にかかっている。
共有段階も同じ決まりに従う：判定対象がなければ 77 で終わり（`Show me test` と命名規律は 3）、`gate.sh` は 77 を解する起こし方でそれらを起こす。

**段階が一部しか走らなかったときは、飛ばした部分を一項ずつ集約に報じる**：ツールが無くて飛ばしたケース、この言語で未実装のサンプル、サンプルの無いローカル段階は、
`lib.sh` の `report_not_run` で報じ（`lib.sh` を source しない段階は `$GATE_NOT_RUN_FILE` に一行追記する。この変数が無いときは書かない：単独で走らせたときとサンプルを流すときは無い）、
`gate.sh` がそれを集約の「今回は走らず」に集める。段階の出力で warn を一言出すだけでは報じたことにならない。報じた回は「前回の成功」として記録しない（`rules/preflight-discipline.md`）。
報じたローカル段階は、`# gate-covers:` のその項目を覆ったことにもならない。

**記録しなかった・飛ばした・無効にした項目は一件ずつログに出す**：成功の一文や集約で「記録せず N」「飛ばした N」「無効 N」のような数を報じたら、同じ出力にその項目を一件ずつ出す（多ければ先頭 N 件、残りは件数）。後始末で消える一時ファイルにだけ書いたのは出したことにならない。

**0 件しか走査していないのも通過ではない。**
対象群を走査する検査は、成功の一文に**何件検査したか**を出すこと。
`gate-lint.sh` がこれを判定する：判定するのはスクリプト中の最後の成功の一文で、
そこにはスクリプトの中で数えた量（加算した変数、配列の長さ、`wc -l` / `grep -c` の結果）が入っていなければならない。本当に対象を走査しないスクリプトは、独立した一行のコメント
`# gate-lint:nocount <理由>` を書き、理由は 8 文字以上とする。

**「何件検査したか」を報じるだけでは足りない。「検査しなかったのはどれか」も一件ずつ挙げ、その一覧はその場で算出する。**
**スキップ一覧は走査対象の集合と同じデータから、その場で算出する**。成功の一文は「<件数> 件走らせた。<件数> 件は走らせていない：一つずつ名前を挙げる」を併せて報じる。
`gate-lint.sh` が半分を判定する（`.sh` だけ）：出力で「飛ばした N」「記録せず N」「無効 N」「走らせず N」のような数（照合する語は `跳过`、`没记`、`作废`、`没跑`、`未跑`）を報じるスクリプトは、同じスクリプトの中に項目を一件ずつ出す出力の行がなければならない。ファイルに書く行は数えない。
項目をよそで一件ずつ出していて、それが認識できない書き方なら、数を報じる行の行末に `# gate-lint:skip-listed <理由>` を書く。理由は 8 文字以上とする。
一覧が走査対象の集合と同じデータからその場で算出されているか、一件ずつ出したものが数えたものと同じかは判定しないので、段階を書く人が自分で守る。

**プロジェクト固有の段階も共有段階と同じ規則に従い**、`gate-lint` と `shell-lint` の対象になる：`gate.sh` が
プロジェクトが登録した門番段階ディレクトリ（デフォルト `.claude/gate.d/`）を両方の lint に渡す。

**届く範囲はプロジェクトが登録した門番段階ディレクトリまでである。** プロジェクトのほかの場所のスクリプト（研究用スクリプト、hook）は、この二つの lint の範囲には入らない。
プロジェクトにこの種のディレクトリがあれば、その登録済みディレクトリにローカル段階を一つつなぎ、それらをこの二つの lint に渡す。二つともつなぐこと：
呼ぶときは `GATE_LINT_DIR` と `SHELL_LINT_DIR` をそれぞれ対象ディレクトリに向ける。

## 区間の計時は被測プロセスの中で取り、出力を中継するループの中で取らない

ラッパーが子プロセスを起動し、その出力行を読んで一行ずつ中継するとき、**各行を読んだ時刻を区間の時計として使ってはならない**。

**やり方**：被測プロセスの中で自分で計時し、その数を結果行に書く。到着時刻でどうしても区切るなら、子プロセスの出力を最後まで読み切ってから中継する。
外側と内側の二つの数があるときは包含の自己検査を報告する：外側の区間は内側の区間を包まねばならず、包まない回は統計に入れない。

ゲート段階「転送計時」（`转发计时`、`scripts/relay-timing-lint.py`）が判定する：プロジェクトの `.rs` と `.py` で子プロセスの出力を読むループ（どのディレクトリを走査するかはそのスクリプトに従う）が、行に時刻を打ちつつ行を中継してはならない。

## 破壊スイッチはどれも必ず赤くなる

破壊スイッチとは、自己検証のためだけにあり、オンにするとわざと一か所を壊すスイッチのこと。

- スイッチを一つずつオンにして自己検証を走らせる：自己検証は 0 以外で終わり、スイッチ表が名指しするそのセルで赤くならなければならない。
- オンにしても赤くならない、あるいは名指しのセル以外で赤くなるスイッチはその場で直す：自己検証を直してそのセルで赤くするか、スイッチを直して名指しの箇所を本当に壊すようにする。どちらも直せなければそのスイッチを削除する。赤くならないスイッチは残さない。
- スイッチを足した、スイッチ表を変えた、スイッチが壊すコードを変えたときは、影響を受けるスイッチを一つずつ走らせ直す。

python で書いたゲートとフックは、`--selftest` の最後に `scripts/break-switch-selftest.py` のやり方でスイッチを一つずつオンにして確かめる。shell で書いたものは、`scripts/selftest.sh` にスイッチごとに必ず赤くなるケースを一つ書く。
