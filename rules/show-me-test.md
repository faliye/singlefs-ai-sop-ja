# 受入の鉄則：Show me test

> **Make every submitted patch review-worthy.**
>
> 提出されたすべてのパッチを、レビューに値するものにする。

## 判定基準はテストである

**パッチの採否は自動検証が決める。** 通れば通る、通らなければ通らない。

## テストのないパッチは一切受け取らない

**`crates/*/src/` を変えたらテストを伴わなければならない。**
例外なし。「これは簡単すぎる」「次のパッチで足す」も通らない。
文書とスクリプトの変更は対象外。

`scripts/show-me-test.sh` が強制する（`gate.sh` は段階として呼ぶ）。

## 新しいテストは、まず赤くなることを示さねばならない

**あらゆる「検証」は失敗しうるものでなければならない。** 手順：**被検コードをわざと壊し、テストが赤くなることを確認し、元に戻す。**
赤くなることを示せないテストは、書いていないのと同じである。

スクリプトに見えるのは「テストがあるか」だけで、この一段は検証できない：**どうやって赤くなることを確認したかをコミットメッセージに書く**——
どの行を壊し、どのアサーションが落ちるのを見たか。書けないなら、やっていない。

ミューテーションの仕掛けがあるリポジトリでは、さらに一歩進める：
「どこを壊したら → どのアサーションが赤くなるか」を**リポジトリに入れたミューテーションリスト**にし、
再実行ゲートに繰り返し検証させる。コミットメッセージの記述は
仕掛けが無い場合の代替であって第一選択ではない。

**設計上の論証も同じようにする**：対抗ラウンドで突かれた各点は、まずモデル上に
**必ず非ゼロを報告する世界**として作り、それからルールを直す。

## 踏んだ落とし穴は、注意書きではなく失敗する検査にする

立てる時機は `sop-first.md` の「境界」の節に従う：まず負債として記録してまとめて立てる。今まさに繰り返し起きているものはその場で立てる。

新しい落とし穴を見つけた時の第一反応は「これをどうゲートの赤い一項に変えるか」であり、
「これをどの文書に書くか」ではない：その場で実行を拒否する検査にし、「X の時に Y をしないよう注意」のような注意書きにはしない。

### その前に、この落とし穴がどの層にあるかを問う：装置の中か、計測条件か

**判定基準は「この落とし穴を赤くなる検査にしたか」ではなく、
「この落とし穴はどの層にあるか」である**：

| 落とし穴の在り処 | 検査を立てる場所 |
|---|---|
| あるコードの挙動の中 | そのコードの隣で足りる |
| **モデル化の計測条件**（同じ量をどう数えるか、境界を含めるか、単位は何か） | **装置と装置の間**：二つの装置が同じ量を計算するなら、同じ数に落ちることを強いる検査を置き、食い違えば赤にする |

**手早い判定基準**：別の装置を立てて同じことを一からやり直したとき、また踏むか。踏むなら、それは計測条件の層にあり、検査は装置をまたいで立てる。

**装置をまたぐ検査は「この名前がどの量を指すか」を釘付けにする**：量が二つなら名前を二つ登録し、それぞれの値を釘付けにする
（`code-discipline.md`「一つの意味概念にはリポジトリ全体で一つの名前」）。

## 最終的な判定基準はプロジェクトが決める

単体テストのような検査は速いフィードバックであって、**受入基準ではない。**
受入基準は被検対象と結びついている：どんな環境を立ち上げ、どんな負荷を走らせ、どんな故障を注入するか——
どれもプロジェクトが自分で決め、自分でテストし、自分で検証する。装置とそのゲート段階はプロジェクトに置き、共有ゲートは持たない。
未実装一覧には常に「最终判据」（最終判定基準）が載っている。このキーを書く前に、受入基準をプロジェクト自身の kb に書いておく：どんな環境を立ち上げ、どんな負荷を走らせ、どんな故障を注入するか。
段階がそのすべてを満たしたときだけ冒頭に `# gate-covers: 最终判据` と書き、一部だけのものは書かない。
一覧のほかの項目を覆う段階も同じく `# gate-covers: <その項目>` と書く（キーは `gate.sh` の綴りのまま写す）。
その段階がこの回に走って通ったときだけ、`gate.sh` はその項目を未実装一覧から「どの段階が覆っているか」へ移す。

## ゲートは通ったふりをしてはならない

未実装のゲート段階は**未実装であると明示的に報告**しなければならず、
黙って飛ばしてはならない。

**プロジェクト固有段階がこの回に判定対象を持たないときは、終了コード 77 を返す**：
`gate.sh` は「今回は走らず」と記録し、通過にも覆いにも数えない。
`exit 0` で飛ばすと集約では「判定して通った」と見分けがつかない。そこは段階を書く人にかかっている。
共有段階も同じ決まりに従う：判定対象がなければ 77 で終わり（`Show me test` と命名規律は 3）、`gate.sh` は 77 を解する起こし方でそれらを起こす。

**段階が一部しか走らなかったときは、飛ばした部分を一項ずつ集約に報じる**：ツールが無くて飛ばしたケース、この言語で未実装のサンプル、サンプルの無いローカル段階は、
`lib.sh` の `report_not_run` で報じ（`lib.sh` を source しない段階は `$GATE_NOT_RUN_FILE` に一行追記する。この変数が無いときは書かない：単独で走らせたときとサンプルを流すときは無い）、
`gate.sh` がそれを集約の「今回は走らず」に集める。段階の出力で warn を一言出すだけでは報じたことにならない。報じた回は「前回の成功」として記録しない（`rules/preflight-discipline.md`）。
報じたローカル段階は、`# gate-covers:` のその項目を覆ったことにもならない。

**バッチスクリプトは各回の失敗を飲み込んではならない**（`|| true` の類）。
出力先を回をまたいで使い回してもならない。
判定基準は「この出力がこの回に生まれたと証明できるか」である：
走らせる前に古い出力を消し、走らせた後にこの回でしか出ないはずの完了印を確認する。

**0 件しか走査していないのも通過ではない。**
対象群を走査する検査は、成功の一文に**何件検査したか**を出すこと。
`gate-lint.sh` がこれを判定する：判定するのはスクリプト中の最後の成功の一文で、
そこにはスクリプトの中で数えた量（加算した変数、配列の長さ、`wc -l` / `grep -c` の結果）が入っていなければならない。本当に対象を走査しないスクリプトは、独立した一行のコメント
`# gate-lint:nocount <理由>` を書き、理由は 8 文字以上とする。

**「何件検査したか」を報じるだけでは足りない。「検査しなかったのはどれか」も一件ずつ挙げ、その一覧はその場で算出する。**
**スキップ一覧は走査対象の集合と同じデータから、その場で算出する**。成功の一文は「N 件走らせた。M 件は走らせていない：一つずつ名前を挙げる」を併せて報じる。
これはまだ検査になっていない：件数を報じるスクリプトがスキップした項目も併せて挙げているかを `gate-lint` は見ないので、段階を書く人が自分で守る。

# 変更をリポジトリ全体へ一度に行き渡らせないときは、外した一つひとつを登記する

規範であれ操作であれ変更であれ、一部のファイルにしか行き渡らせていないなら、**行き渡らせなかった分を除外表に一行ずつ登記する**。
一行一件、`#` の後ろに行き渡らせない理由を書く。**除外表が無いということは、リポジトリ全体を変えるという意味になる。**

判定基準は「直すのが面倒か」ではなく「直すとその一文が偽になるか、どこかの関門が効かなくなるか」である。
他プロジェクトの用語と原文引用、ある検査自身の入力、道具自身のパターン表、この変更そのものを述べている一文——
これらは直すと誤りになるので登記する。それ以外はすべて直す。

除外表の**存在しない経路を指す項目は赤にする**。表は一つのコマンドで読めるようにする。

**成功の一文で報じる数そのものも、何かで釘付けにしておく。** `gate-lint` はこれを見ないので、段階を書く人が守る。

**プロジェクト固有の段階も共有段階と同じ規則に従い**、`gate-lint` と `shell-lint` の対象になる：`gate.sh` が
`.claude/gate.d/` を両方の lint に渡す。

**届く範囲は `.claude/gate.d/` までである。** プロジェクトのほかの場所のスクリプト（研究用スクリプト、hook）は、この二つの lint の範囲には入らない。
プロジェクトにこの種のディレクトリがあれば、`.claude/gate.d/` にローカル段階を一つつなぎ、それらをこの二つの lint に渡す。二つともつなぐこと：
呼ぶときは `GATE_LINT_DIR` と `SHELL_LINT_DIR` をそれぞれ対象ディレクトリに向ける。

# ゲートが証明できること・できないこと

> **Gate proves evidence requirements, not semantic correctness.**
>
> ゲートが証明するのは根拠要件の充足であって、意味的な正しさではない。

## 全段階を通過してなお誤っている場合

| 状況 | ゲートが届かないところ |
|---|---|
| テストが契約ではなく実装をテストしている | 数えるのは「テストがあるか」だけで、「テストが正しいか」は判定しない |
| 宣言そのものが誤っている | 宣言と実測が一致すれば「一致」と判定するが、その宣言が誤っている。**対照群がなければ**何も証明していない |
| 不変条件そのものが誤っている | 検査は誤った規則を忠実に判定し、しかも全緑になる |
| 覆っているのが壊れる経路ではない | カバレッジは正しさではない |
| 本文が引く数が、その本文自身の産物と食い違っている | リプレイの**区間**言明が留めるのは結論がどの帯に落ちるかだけで、本文のその数ではない：区間が広いだけ本文はずれられる |
| 二つの装置が同じ量について異なる数を出す | 言明もミューテーションも**一つの装置の内側**でしか効かず、装置をまたいで突き合わせるものは何も無い |
| 設計の層で誤っている | ゲートはこの層に届かない |

## 帰結

1. **ゲートが緑でも、コードを読まなくてよいことにはならない。** 人は**「そのテストは正しい対象をテストしているか」**を見る。

2. **意味的な正しさは `kb/decisions.md` と `kb/invariants.md` に住んでいて、
   ゲートには住んでいない。** ゲートが保証するのはこの二つが
   **書かれ、実装され、コードと同期していること**だけであり、
   その中身が正しいかどうかは人が担う。

3. **ゲートは下限であって上限ではない**（`rules/sop-first.md`）。

4. **未実装の段階は常に明示的に列挙する。** `gate.sh` が毎回この一覧を印字する。
   プロジェクトの段階がある項目を覆うと宣言しても（`# gate-covers:`）、
   その段階がこの回に走って通ったときだけ、その項目は一覧から外れる。

5. **返された一覧が機械で漏れなく確認できても、判定が正しいことにはならない。**
   サブエージェントが一項目ずつ判定する仕事（洗い出し、再確認）で検査にできるのは「どの項目にも判定がある、判定は認められた数種類のどれかである、理由がその項目の原文を引いている」までであり、
   これは「抜き取りで十分」「組ごと素通し」は止められるが、判定の誤りは止められない。だから漏れなく確認した後も、**すべての判定の種類**にわたって抜き取りで判定し直し、誤判定に当たった区間はやり直してからもう一度抜き取る。

## 出所で分類せず、根拠だけを見る

本プロジェクトは**出所による類別を設けず**、
どの類にも個別の規則を書かない。区分はただ一つ：
**根拠を伴う提出と、伴わない提出である。**
