# 締め：毎回の作業の終わりに必ず行うこと

## 0. 進捗を報告する——最初に置き、省略しない

一行に三つの数：**今どのマイルストーンにいるか / ゲートは通るか / まだ足りない根拠は何か。**
ゲートの欄には、直近のコミット前ゲートの判定と日付（その `gate.sh --staged` の要約）を引く。進捗報告のためにゲート全体を走らせ直さない：ゲートはコミット時にだけ走らせる。
マイルストーンと根拠の二欄はその場で確認し（記録と成果物を読む）、前回のメモから写さない。

**同時に、今回その数をいくつ進めたかを述べる。** ゼロ結論が出た、決定を一つ覆した、
あるいはまだ取れない根拠があると判明しただけなら、**0 と書く。** 他の回の成果を今回に数え入れない。

## 1. 今回叩いたスクリプトやコマンドで、`scripts/` へ収めるべきものはあるか

判定基準は「**二度目に写されるか**」であって、「よく書けているか」ではない。

**踏んだ落とし穴は、注意書きではなく、実行を拒否する検査にする。** いつ立てるかは `sop-first.md` の「境界」の節に従う：まず負債として記録し、まとめて立てる。

逆向きにも一度見る：もう誰も使っていないものはないか。あれば削る。

## 2. 今回使った skill や規則で、直すべきものはあるか

記憶で支えていた手順はなかったか。判定基準を後付けしなかったか。
同じ雛形を三度目に写していないか。
**あればその場でそのファイルを直す。**「次回」に回さない。

どこを直すかは、それが何を扱っているかで決める：

- **協働を扱う**（証拠、文書、決定の置き場所、ゲートの返し方）
  → singlefs-ai-sop を直し、`VERSION` を上げる
  （どのパスで上げる必要があるかは `scripts/version-discipline.sh` の `GOVERNED`）
- **ファイルシステムの設計を扱う** → プロジェクト側の `kb/`、`.claude/rules/`、
  またはプロジェクトの `CLAUDE.md` を直す

**迷ったらプロジェクト側に置く。**「他のプロジェクトも必要とするか」は判定基準にならない。

**セッション私有の記憶（たとえば Claude Code の memory）には書かない。** ほかの人がぶつかりうる落とし穴や取り決めは、プロジェクトかこの規範に書く。
私有の記憶に置くのはユーザー個人の好み（いつコミットするか、何語で返事をするか、など）だけにする。

## 3. 決定に変更はあったか

今回いずれかの設計決定を覆した、あるいは確定したなら、
**その場で `kb/decisions.md` に書く。** 根拠を添えて。

**論証の末に下した判定も、一度の決定変更である。** 検討の結果として
「これは今決めるべきでない」「現行案を維持する」といった結論を出したとき、
それが実質的に `kb/decisions.md` に既に書かれた一文を覆しているなら、
それは覆しである。その場で根拠つきで記録すること。

## 4. 同じリポジトリで別のセッションが動いていないか

複数のセッションが並行して作業するとき、締める前に一つずつ確かめる：

- **「作業ツリーにあるものは全て自分のもの」は成り立たない。** コミット前に変更を
  「今回のもの / 今回でないもの」に仕分け、自分の分だけをコミットする。
- **「ゲートが赤い＝自分が壊した」は成り立たない。** 赤が出たら、まず失敗が指す
  ファイルが今回の変更に含まれるかを見る。含まれないなら
  「赤いが今回のものではない」と正直に報告し、ついでに直さない。
  見分けがつかないときは `bash .claude/scripts/gate.sh --staged` を走らせる。一時的な worktree で
  HEAD とステージ済みの変更だけに対してゲート全体を走らせるので、そこで赤くなったものが、このコミットが持ち込んだものである。
  `--staged` なしで走らせるとき、`gate.sh` は開始時と終了時に作業ツリーの指紋を取り、食い違えば赤にする。
  **編集が止まってから走らせるか、`--staged` を使う。**
- **共有の採番は先着順である。** 履歴項目の番号や実験番号のような共有の採番は、
  取る前に既存の最大番号を調べる。共有ファイルは定点置換だけで直し、
  全文を書き直さない。
- **「新しくファイルを作っても誰のものも上書きしない」は成り立たない。**
  新しいファイルは排他的に作り
  （`set -o noclobber`、`open(パス, 'x')`）、番号は最初のファイルを書くのと同じコマンドの中でその場で調べる。
  ツールの層で止められる（書き込み前のフックが未追跡ファイルの上書きを拒む）なら、ツールの層で止める。
- **「このパスだけをコミットする」は `git commit -- <パス>` ではない。** パスを渡したコミットは、そのパスの**作業ツリー**の中身をコミットするのであって、ステージの中身ではない。
  ステージする前に `git diff --cached --name-only` が空であることを確かめ、ステージした後・コミットする前にもう一度一覧と各ファイルの cached diff を確かめてから、パスを付けずに `git commit` する。

番号が衝突したなら、赤くなる検査にできるものは検査にする
（`rules/show-me-test.md`「踏んだ落とし穴は、注意書きではなく失敗する検査にする」）。
プロジェクト側では、履歴ファイルが既に使っている採番の形に倣えばよい。

## 5. サブ agent は返す前に、自分で作ったビルドディレクトリとリポジトリの複製を消す

サブ agent が作業用ディレクトリにコピーしたリポジトリの複製と、自分の `CARGO_TARGET_DIR` でビルドしたビルドディレクトリは、返す前にそのサブ agent 自身が消す：

- **消す**：今回自分で作ったビルドディレクトリ（`target`、`CARGO_TARGET_DIR` が指すディレクトリ、そのほか `CACHEDIR.TAG` を持つキャッシュ）とリポジトリの複製（clone、コピーしたリポジトリ、git worktree）。
  worktree はその元のリポジトリで `git worktree remove --force <パス>` で消し、元のリポジトリ側の登録も一緒に消す。残りは `rm -rf`。
- **消さない**：報告、コミットする成果物、メイン agent がまだ確かめる再実行の材料。前任者、メイン agent、別の agent が作ったものは、同じ作業用ディレクトリにあっても消さない。
  プロジェクトルートの中のもの（プロジェクト自身の `target`、Claude Code がプロジェクト内に作った worktree）はメイン agent のものである。
- 消す前に `du -sh` で大きさを控え、返す報告に、何を消したか・それぞれどれだけの大きさかを一行書く。
- 消さなかったものは、返す報告に一つずつ一行「削除していない <フルパス>：<理由>」と書く。パスを出典として引くだけ（「… の複製で走らせた」）では数えない。

これはフック `scripts/claude-hooks/handback-scratch-check.sh` が見る。掛ける場所は二つ：

- 返却ツール（`SubagentHandback`）の PreToolUse：返す前に止める。一時ディレクトリの中にあり、このサブ agent 自身のいずれかのツール呼び出しがまだ終わっていない間に作られ、
  その呼び出しの中で触れられたビルドディレクトリ、worktree、リポジトリの複製がまだ残っていて、今回返す報告にその一行が無ければ、返却を拒んで一覧を渡す。
- SubagentStop：返却ツールを通らずに終わったときの受け皿。届いた返却報告にその一行があれば止めない（拒まれた回は数えない）。
  止められた後、返答か書いた報告にその一行を書いてから終われば通す（du、ls、Read を一度するだけでは数えない）。

プロジェクトは `.claude/settings.json` にこの二か所を登録する。書き方はそのフックの冒頭にある。
これが見分けられないものも、やはり消す：変数の中にしかないパス、スクリプトの内部で作られて呼び出しに現れないディレクトリ、自分で作ったディレクトリから二階層以上下にあるもの、
`.git` を持たずその中でビルドもしていないソースの複製、呼び出しが返った後に切り離されたプロセス（`nohup`、`setsid`、`&`）が作ったもの。報告にその一行を書いたかどうかは見ない。
