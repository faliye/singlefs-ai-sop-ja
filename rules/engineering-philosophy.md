# エンジニアリング理念

> **実装は AI に優しく、レビューは人間に優しく。**

これは二つの目標の折衷ではない。**もともと分けるべきだった二つの軸**である。

従来この二つは一本にまとめられていた——コードを書く人と読む人が同一だったため、
「書きやすい」と「読みやすい」は同じ一つのことでなければならなかった。
**もうそうではない。**

## なぜ旧来の金科玉条を引き直すのか

現行のソフトウェア工学のベストプラクティスは、そのほとんどが一つの暗黙の前提の
上に育った：**エンジニアリング品質の上限は人間の認知能力で決まる。**

関数は短く、ネストは浅く、概念は少なく、設計は統一し、重複は排除する——
表向きは別々のことを言っているが、実際に解いている問題は一つ：
**限られた人間の頭に収める**ことである。
これらは誤りではない。**その制約に合わせて較正されている**だけだ。

そしてその制約は緩みつつある。論理の整理、一貫性の維持、網羅的なカバー——
いずれも機械の得意分野であり、その処理能力はとうに人間の上限を越えている。

**旧い上限に合わせて引いた下限は、低すぎる下限になる。**

したがって本プロジェクトの既存ベストプラクティスに対する姿勢は、
**既定で従うのではなく、吟味して従う**である。
一条ごとに問い直す：それは元々どの問題を解いていたのか、その問題は今も存在するのか。
手順は `machine-first.md` にある。

## 二つの軸がそれぞれ最適化するもの

| | **実装面：AI に優しく** | **レビュー面：人間に優しく** |
|---|---|---|
| 誰が使うか | モデルが書き、モデルが直し、機械が検証する | 人が判断し、人が責任を負う |
| 何を最適化するか | 機械検査可能・網羅可能・強制到達可能・巻き戻し可能 | 判断可能・信頼できる・トレードオフが見える |
| 具体的には | 明示的な網羅分岐が巧妙な汎用経路に勝る／型で不正な状態を表現不能にする／不変条件はアサーションにする／重複は手で維持せず生成する | 決定には根拠を添える／ゲートの失敗には次の一手を添える／数値には計測条件を添える／未検証のものは明示する |

## AI に優しい ≠ 読めない

**モデルにとって優しい方向は「より明示的」であって、「より難解」ではない。**

名前も型もなく七層にネストしたコードを読むモデルの立場は、人間より良くはない——
得られる情報は少なく、誤りは増え、しかもその誤りは見つけにくい。
**可読性を削っても実装が AI に優しくなることはなく、両方が悪くなるだけである。**

緩めるものはただ一つ：**人間の頭に収めるために行っていた圧縮**——
「一つの仕組みで全部を賄う」「概念は少ないほどよい」といった設計レベルの統一性要求である。

**緩めないもの**（可読性に見えるが、実体は検証可能性か情報量である）：

| 項目 | 残す理由 |
|---|---|
| 命名 | **名前は装飾ではなく情報である。** `fn f(a: u64, b: u64)` は `fn commit_txn(gen: Generation, root: Logical)` より意味が丸ごと一層少なく、モデルにもそれは補えない |
| 関数の責務は一つ | 関数は**独立に検証できる**一つのことを行う——長さはそれで決まり、画面の高さでは決まらない |
| **経路数が有界であること** | このコードを網羅するのに何ケース要るか？ 言えて、かつ有界なら検証可能。**ネストの層数ではなく経路数である**（下記参照） |
| 規約の一貫性 | 規約が揺れると機械検査が効かなくなる——「設計の統一性」とは別物なので混同しない |

**判定基準は同じ一つ**：それは検証を容易にするのか、それとも人の目に優しいだけなのか。
上の四項はいずれも前者なので残す——ただし**理由は検証可能性と情報量に書き換え、
もはや「可読性」にぶら下げない。**

### ネストの層数そのものに上限は設けない

「ネストは三層まで」といった規則は測る対象を間違えている。
検証可能性を実際に決めるのは**経路数**である：

| | 経路数 | テストできるか |
|---|---|---|
| 12 次元構造を巡る 12 層の `for` | **1** | 完全にテスト可能。深さは問題にならない |
| 独立した 12 層の `if/else` | **2¹²** | テストしきれない |
| 独立した 3 層の `if/else` | 8 | かろうじて |

**ループのネストは経路をほとんど増やさず、条件のネストは指数的に増やす。**
旧規則が両者をまとめて縛ったのは、人間にとってはどちらも同じように読みづらいからである——
それは人間の制約であって、検証の制約ではない。

したがって：**層数は自由。ただし（一）経路数が言えて有界であること、
（二）各層の意味が明示的であること。**
（二）は各層の反復対象に名前と型があるという意味であり、`a[i][j][k][l]` ではない——
あの書き方の問題は深さではなく、**情報を持たないこと**であり、
「名前は情報である」と同じ一条である。

### 例：意味はどこに置くべきか

同じことの三つの書き方、悪い順から：

```rust
// 一、意味をコメントに置く —— 従来のやり方であり、最も悪い
// dim0: 民族  dim1: 性別  dim2: 年齢層
pop[i][j][k]

// 二、意味を名前に置く —— 従来は冗長と嫌われたが、機械はこれを好む
num_china_people[han][woman][teenager_18_to_24]

// 三、意味を型に置く —— 最善。次元を取り違えるとそもそもコンパイルが通らない
num_china_people[Ethnicity::Han][Gender::Woman][AgeBand::T18to24]
```

一つ目は**人間の頭に収めるための圧縮**である：名前を最短に切り詰め、意味をコメントへ移す。
人間の時代には妥当だった——行幅も画面も限られていた。
しかし**コメントはコードから乖離しうるが、名前は乖離しない。** 名前はコード自体だからである。

二つ目はかつて「長すぎる、三次元配列だと見れば分かる、なぜ書き切るのか」と言われた。
それは人間の美意識である。機械にとっては純粋な利得だ：各次元が自己記述的であり、
**文脈なしにそのアクセスの正否を判断できる。**

三つ目は情報を「読める」から「検査できる」へ押し上げる——**次元を入れ違えればコンパイルが通らない。**
これは `machine-first.md` の「制約をコメントで説明するより、型で不正な状態を表現不能にする」
と同じ一条であり、本プロジェクトで既に定めた newtype 規律
（論理アドレス／物理アドレス／世代番号をそれぞれ別の型にする）と同根である。

**判定基準**：この意味はコメントにあるか、名前にあるか、型にあるか。
**後ろへ行くほど良い。後ろほど実装から乖離しにくいからである。**

## 帰結：人間の注意はどこに使うべきか

**人間の注意はこの体系で最も高価な資源であり、コードを読むことに使うべきではない**——
それはモデルに任せられる。

使うべきなのは、機械には判断できない次の四つである：

1. **このテストは正しい対象をテストしているか**
2. **この不変条件そのものは正しいか**
3. **この決定の根拠は成立しているか**
4. **このトレードオフを受け入れるか**

四つとも実装を通読する必要はないが、四つとも
**人間に提示される側が人間に優しいこと**を要求する。

したがって：ゲートの出力、kb の結論、決定記録、失敗メッセージ——
**これらは人間向けに、しかも従来より強く最適化されねばならない。**
今やそれらが人間の見る唯一のものだからである。
コードが読みにくいのは受け入れられる代償だが、この四つが判断しにくいのは受け入れられない。

## 二つの軸の境界線

> **Gate proves evidence requirements, not semantic correctness.**

この一文が境界である：**機械は根拠要件を証明し、人間は意味的な正しさを判断する。**
