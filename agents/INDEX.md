# 共有 subagent 定義

**この層は統治下に入っているが、現在は空である。** 空は**状態**であって手落ちではない——
明示して書くのは、「無い」と「忘れた」がディレクトリ上では見分けがつかないからである
（`rules/kb-discipline.md`：空白は誤りより危険）。

## この層に何を置くか

**複数回の作業にわたって繰り返し委譲され、判定基準が固定されている subagent。**
`skills/` との境界：

| | どこに置くか | なぜ |
|---|---|---|
| 人や主モデルがなぞる手順 | `skills/` | それは**読まれる**もので、独立した文脈を要らない |
| 独立した文脈で走らせ、結論だけ返す仕事 | `agents/` | それは**委譲される**もので、その途中生成物で本線を埋めるべきでない |
| ある一つのプロジェクトでしか成立しない委譲 | プロジェクトの `.claude/agents/` | 上流に上げない（`CLAUDE.md` の分担基準） |

**迷ったらプロジェクト側に置く。** 上流に上げるべきでなかった subagent は、
以後どの回の作業でも迂回し続けることになる。

## 書き方

subagent 一つにつきファイル一つ `agents/<名前>.md`。YAML frontmatter が先頭
（第 1 行から始めること）：

```markdown
---
name: <小文字とハイフン。ファイル名と一致させる>
description: <いつ委譲すべきか。この一文が主モデルの唯一の選択根拠なので、
             発動条件を書く>
---

<本文：その責務、判定基準、そして**返す形式**。>
```

**`description` が正しく使われるかどうかを決める。**「コードを審査する」ではいつ呼べば
よいか誰にも分からない。「ミューテーション実行後、どの盲点が等価ミュータントかを判定する」
なら選べる。

## 三つの規律

1. **出力形式を決め打ちにする。** 長い散文で返ってくる subagent は、整理の手間を本線へ
   押し付けている。何を、どの順で、各項目にどの証拠を添えて返すかを書く。
2. **走らせた結果だけを報告し、推測は報告しない。** 委譲した仕事は途中を誰も見ていない。
   だから報告は自前で証拠を持つ必要がある（どのコマンド、どのファイル、どの出力）——
   これは `rules/evidence-discipline.md` と同じ規律を委譲に当てたものである。
3. **自分が何をしなかったかを言えること。** 走らせられなかったもの、検証していないものを
   明示的に列挙する（`rules/show-me-test.md`：未実装の段階は明示して並べる）。

## つなぎ方

`skills/` と同じ形。プロジェクト側は**スタブ**、本文は一箇所だけ。

| 層 | つなぎ方 |
|---|---|
| 共有定義 | 本ディレクトリの `agents/<名前>.md` |
| プロジェクト側 | `.claude/agents/<名前>.md` はスタブ：frontmatter と共有本文への案内 |

スタブは `install.sh` が生成する。中に本文は書かない——書けば第二の写しができ、
二つの写しはいずれ別のことを言い出す。

## ゲート

- ディレクトリが空のあいだ、`scripts/manifest.sh` は「統治下にあり現在は空」と明示する。
  黙って通過させない。
- `agents/*.md` はそれぞれ `name` と `description` を持ち、`name` はファイル名と一致すること。
- `rules/` と同律：マニフェストに入り、一篇ずつ翻訳し、一篇ずつ来歴を追う。
  変えたら `VERSION` を上げる。
